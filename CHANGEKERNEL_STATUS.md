## Research findings

### Hermes: three different automation mechanisms

Pinned source: `NousResearch/hermes-agent` at `bac0c45d8593ed9d53a8e3fcacecdc920b71a2c4`.

- [Cron](https://github.com/NousResearch/hermes-agent/blob/bac0c45d8593ed9d53a8e3fcacecdc920b71a2c4/website/docs/developer-guide/cron-internals.md) owns time-based triggers, missed-occurrence/catch-up policy, run claims and delivery. Jobs use JSON storage; execution attempts have a separate SQLite ledger. Runs normally start a fresh conversation with supplied prompts/skills, rather than requiring an immortal chat session. Execution success and delivery success differ.
- [Persistent goals](https://github.com/NousResearch/hermes-agent/blob/bac0c45d8593ed9d53a8e3fcacecdc920b71a2c4/website/docs/user-guide/features/goals.md) continue one session toward an objective, with a judge, bounded turns, explicit pause/wait and optional shell gates. A goal does not implicitly create board work. Judge failure deliberately means continue within the turn budget; that advisory progress policy cannot replace ChangeKernel's mandatory fail-closed assessments. Resume can reset the goal's turn counter; that is not a durable aggregate spending policy for our Work tree.
- [Kanban](https://github.com/NousResearch/hermes-agent/blob/bac0c45d8593ed9d53a8e3fcacecdc920b71a2c4/website/docs/user-guide/features/kanban.md) is the closer analogue for unattended backlog: persistent tasks, dependencies, delayed readiness, per-attempt rows, comments/artifact handoffs, separate OS workers, review/changes-requested routing, cooldowns and failure circuit breakers. Blocking on an unfinished dependency differs from needing human input. A typed terminal handoff matters; a process exit or a prose claim is not automatically completion.
- Source inspection of `hermes_cli/kanban_db_dispatch.py::_terminate_reclaimed_worker` and `detect_stale_running` confirmed PID/start-fingerprint checks and retaining a claim when a local worker survives attempted termination. It is not merely “TTL expired, always spawn again.” These are useful mechanisms, not proof of descendant/provider quiescence or external-effect absence.
- The Kanban documentation explicitly describes a trusted local-user, single-host threat model and says its PR acceptance guard is not OS isolation against direct DB writes. Environment-selected board/tool scope is not ChangeKernel's custody privilege boundary. Its use of “workspace” for an execution directory is not our persistent Workspace identity.
- [State DB recovery](https://github.com/NousResearch/hermes-agent/blob/bac0c45d8593ed9d53a8e3fcacecdc920b71a2c4/website/docs/developer-guide/state-db-recovery.md) separates corrupt derived search indexes from canonical transcript corruption. Canonical corruption quarantines the handle and calls for explicit guarded repair. This supports selective degradation, not an inference that arbitrary storage incidents recover automatically.

### OpenClaw: owned runtime and explicit recovery ownership

Pinned source: `openclaw/openclaw` at `e4e485225184f418636d34cfd05c66a7b5ebd06c`. Its manifest reports `2026.9.6`; this research pinned source, not a qualified released artifact.

- The user's ownership observation is substantiated: [runtime architecture](https://github.com/openclaw/openclaw/blob/e4e485225184f418636d34cfd05c66a7b5ebd06c/docs/agent-runtime-architecture.md) places the built-in loop in owned `@openclaw/agent-core`, with owned session/provider layers. Manifest inspection and `packages/agent-core/src/agent-loop.ts` corroborate that boundary. The retained Pi dependency is `@earendil-works/pi-tui`; this is no longer merely embedding the external Pi agent framework. The inspected core is TypeScript, so this demonstrates progressive runtime ownership, not that Rust is inherently required.
- [Restart recovery](https://github.com/openclaw/openclaw/blob/e4e485225184f418636d34cfd05c66a7b5ebd06c/docs/gateway/restart-recovery.md) separates persisted input, admitted turns, child outcomes, queued deliveries and restart continuations. It drains before managed restart, retains recovery claims and charged attempt budgets, correlates terminal delivery receipts, and reconciles interrupted children through their parent rather than blindly launching them again. Code inspection of `resolveMainSessionResumePolicy` confirms distinct complete/resume/restricted-tool cases, including pending delivery.
- [Queue semantics](https://github.com/openclaw/openclaw/blob/e4e485225184f418636d34cfd05c66a7b5ebd06c/docs/concepts/queue.md) separate session serialization from capacity across sessions/background work. Persisting an input does not necessarily mean scheduling it autonomously after restart: the in-memory input queue is not replayed; some interrupted input depends on explicit resend or the Control UI's reconnecting outbox. ChangeKernel's server-owned unattended backlog must not depend on a browser or terminal returning.
- [Automation recovery](https://github.com/openclaw/openclaw/blob/e4e485225184f418636d34cfd05c66a7b5ebd06c/docs/automation/cron-jobs/how-it-works.md) distinguishes recorded terminal results from fresh payload execution and missed schedule occurrences. The inspected `src/cron/service/run-recovery.ts` rechecks owner/configuration policy before committing repair. Documentation also acknowledges that receipt revocation cannot undo already-started external effects.
- Recovery policy is not our acceptance policy by default. OpenClaw's documented and implemented Full Access path can retain ordinary tools during ambiguous-effect reconciliation; it does not automatically replay the old call, but our mandatory unknown-effect/authority guards must still remain outside model discretion. Its persisted/transcript repair and same-user deployment do not qualify ChangeKernel's protected accepted-prefix or native isolation requirements.

### Pi/Jaz: separate the good ideas from ownership of the whole product

Installed Pi 0.87.1 documentation and SDK examples were read; the project's retained adapter version is a different, unchanged dependency subject. Pi already exposes explicit session managers, context reconstruction, custom tools/resources, abort and settled events through its SDK/RPC boundary. A Rust supervisor can therefore own durable Work while initially delegating bounded reasoning to Pi. Its session tree/compaction is context continuity, not authoritative Change acceptance or restoration of an execution pointer. `agent_end`, `agent_settled`, retained output and proven process/provider quiescence must remain distinct.

Prior Jaz source pin `0803d4971be785e95b80054b02259664d70fa3da` was rechecked, not updated or installed. Named inputs, programmatic access to supplied history, recursive invocations and shared budget ideas are useful. Its inspected replay hook reuses model replies while code executes again; its hook dispatcher logs ordinary hook exceptions and continues; its budget pool resets in-memory aggregates by scope. Those are not our recovery, mandatory-enforcement or durable-budget contracts. A Rust-written runtime can support programmable strategies without requiring the model to generate Rust or building a new language interpreter. The code-execution language and containment mechanism remain separate decisions.

## Manager recommendation — proposed, not adopted

**Persistent Work and accountable attempts should own continuity; a worker process or chat session should not own the backlog.** Interpret “lights-off factory” as an operating mode of Workspace/Change/Work and the host, not a revival of a public Factory resource or a new lifecycle stage.

Compose these responsibilities before choosing a witness backend or committing to a whole runtime rewrite:

1. **Durable intake and triggers:** current-authorized, deduplicated admission independent of an open UI. Timers/webhooks request work; they do not grant permission. Each recurring schedule needs explicit missed-occurrence/coalescing/backfill policy and bounded backlog behavior.
2. **Planning and readiness:** dependencies, exact intent/plan/Kernel/runtime bindings, required assessments, current source rights and authority determine eligibility. Scheduling chooses among eligible Work; priority or a wakeup never bypasses admission.
3. **Rust-owned scheduling/supervision:** exact durable attempt claim before launch, aggregate spending/occupancy accounting, fairness/backpressure, deadlines, current authority and qualified isolation. Avoid placing untrusted inference/code, the scheduler and the custody writer in one undifferentiated failure domain. Separation does not itself prove safe host restart.
4. **Replaceable bounded agent execution:** Pi can remain the initial/reference worker. A narrow Rust inner loop is a serious candidate for control over event ordering, context, recursive delegation and cancellation. It must use the same controlled tool/effect interfaces; Rust memory safety alone does not create isolation, durable effects or a correct permission model.
5. **Retention, completion and delivery:** preserve exact results/grounds before dependent use; correlate retries and late results without relaunch. Applicable Checks/outcome Review decide progression, not “the model stopped.” Delivery retry is not another model run. Changed configurations create newly admitted bindings without rewriting old attribution.
6. **Qualified recovery and escalation:** reconstruct authorized context, observe surviving work, deliver retained results, reconcile unknown effects, then admit only genuinely eligible new work. Keep automatic retry budgets across restarts. Back off temporary provider failures; do not convert revoked credentials, missing authority, required-Check failure or true storage uncertainty into an infinite retry loop. Continue unaffected work only where the failure boundary is actually established.

The first unattended scenario should cover an overnight intake batch with dependent coding/review tasks and a fixed shared budget: one worker crashes; one task waits for CI; one result is retained but not referenced/delivered; one publication has an unknown response. The host should reuse qualified retained results, wait without wasting inference, reconcile publication rather than create a duplicate, and continue independent eligible Work. Reboot must not reset spending, discard accepted intake or depend on the initiating terminal reconnecting. Unscopable custody/storage damage still stops the affected domain and raises a visible recovery obligation. “Unattended” does not mean pretending unavailable authority exists.

For runtime ownership, the recommended progression is **own the Rust operational core and runtime contract, then evaluate a small owned agent loop**. Do not make a full Pi/Jaz clone a prerequisite to the first supported path. Benefits to test include explicit launch/settlement boundaries, lower semantic translation overhead and tighter integration with Work. Costs include provider streaming/tool-call quirks, authentication, context/compaction fidelity, cancellation, multimodal payloads, plugin compatibility, updates and ongoing maintenance. No Rust speed/cost/safety superiority or framework performance ranking was measured here.

A future bounded comparison should use the same captured inputs/tools/limits, initially with deterministic provider fixtures for lifecycle behavior; any live model comparison needs separate authorization and matched models/budgets. Limit a Rust candidate to the actual first workload rather than all Pi interfaces, all providers or OpenClaw's channel ecosystem. No such prototype is released by this note. Reusable self-improvement still requires assessment of exact candidates and separate qualification/activation/controller handoff; agents may not weaken their evaluator to remain productive.
