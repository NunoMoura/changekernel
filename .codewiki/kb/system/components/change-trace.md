# Change Trace

A Change carries one accountable intention from accepted Knowledge State `S0` to intended state `S1`; its Change Trace is the append-only canonical operation history for that intent carrier. Knowledge remains authoritative for current accepted desired state, while Change records why and how that state was proposed, judged, confirmed, implemented, completed, or reversed. Decision confirmation may commit `S1` before project artifacts satisfy it, and Trace preserves the resulting gap rather than conflating accepted meaning with completed work or Delivery. Strict canonical bytes, typed operations, parent identity, authority binding, preconditions, and deterministic reduction make replay and synchronization verifiable. Change Trace Protocol `12.0.0` binds each authority-bearing operation to one accountable `actorId` and one proof-backed `authenticatedIdentityRef`; Client transport identity remains request provenance rather than canonical actor identity.

Each immutable Change revision binds bounded human problem and objective summaries, rationale, alternatives, outcomes, acceptance requirements, stable Knowledge subject or facet targets, and either one complete reducible Knowledge transition or explicit unchanged-Knowledge references. Summaries explain intent but cannot copy current Knowledge bytes or substitute for exact Effects. A transition contains a canonical atomic set of `set` or `retire` Effects. `set` stores one complete bounded post-state artifact once inline; `retire` preserves target identity through a tombstone. Expected prior state or absence is bound by exact identity rather than copied prose. Paths, headings, model-owned offsets, fuzzy replacement instructions, generated propagation lists, and repeated current bytes are not semantic transition authority.

At Decision Candidate checkpoint, Project Server binds the exact revision and Effects to the observed Knowledge State, accepted active Changes, compiler identity, deterministic application plan, projected Knowledge State, and projected Markdown or YAML identity. Only an authorized confirmed `approve` operation admits those unchanged Effects into accepted Knowledge reduction. Project Server commits Decision confirmation, Change Trace operation, resulting Knowledge identity, and WorkState commitment atomically under expected-head compare-and-swap. Rejected, deferred, withdrawn, failed, or merely passed Candidates remain history but never alter accepted Knowledge. Committed history is never reversed or erased; semantic reversal is another explicit Change. Global synchronized operation order and per-target prior-state checks permit byte-reproducible reconstruction and conflict detection without treating generated projections as independent truth.

Backend v1 canonical history also binds immutable Change-scoped Planning deltas through typed `planning.delta_accepted` operations, singly owned Work Units, exact Knowledge Effect, unchanged-Knowledge, and acceptance-requirement coverage, explicit amendment lineage, their Candidates and Gates, and Project Server-owned scheduling admission. A canonical Work Unit Claim binds the exact WorkState and Work Graph heads, Worker Offer, scheduling policy, source base, scope, obligations, budget, lease, and assigned Workbench. Its atomic Assignment binds the same Claim, Worker Offer, isolated Workbench, and assignment digest. An Implementation attempt then records one exact Work Unit Candidate, shared stage policy, Evidence, independently completed Results, Gate Report, and `gate_failed` or `integration_pending` route without treating Gate passage as integration. Typed `integration.candidate_admitted` operations persist exact Private Integration Receipt `1.0.0` artifacts and reduce Private Change Integration Lineage `1.0.0` under lineage-head and Change-tail compare-and-swap. Typed `implementation.aggregate_frozen` records Implementation Aggregate `1.0.0` only after every required unit, dependency, accepted Effect, unchanged-Knowledge target, and acceptance requirement is covered. Git stores exact private commits and trees; Trace records their semantic admission; derived WorkState records current lineage and aggregate. No separate object store or per-unit protected merge is canonical authority. Aggregate Review then records one exact Review Attempt `5.0.0`, its fresh `review:<change-id>:<lineage-digest>` producer continuity and Run receipt, Project Context Snapshot, Check Pack, Evidence, Results, typed failure ownership, Gate Report, and fixed Project Server route. A failed route invalidates delivery authority and reopens only affected Implementation, explicit Planning amendment, or Decision. Typed `delivery.applied` history binds one exact passed current Review, Delivery Authority `1.0.0`, protected target, expected target head, delivered commit, and delivered tree after target-head compare-and-swap. Trace therefore connects accepted Knowledge meaning to everything that later satisfies the Change while remaining a Change dossier rather than a second current-state encyclopedia.

Mutable allocation does not alter immutable Change meaning. Reviewer, contributor, Stage Producer, Implementation Worker, and machine identities live in policy-bound requirements, Claims, Assignments, producer attempts, and operations rather than Change revisions. A Review Requirement binds one exact revision, review class, scope, minimum approvals, independence rule, and policy digest. A Review Claim records current responsibility without implying approval. A Review Submission immutably binds one authenticated `approve | request_revision | defer | reject` disposition, rationale, Evidence references, Claim, delegation where applicable, and Project Server-owned time.

Human Review Submissions are optional inputs to the Review Stage Loop unless the user's Review Checks require them. Actor Profile, expertise, job title, CODEOWNERS, repository access, Agent or model identity, and Client kind cannot grant review or delivery authority. Project Server admits any Review Submission only when one exact Authority Grant and current policy authorize the actor for that requirement and revision. Archive remains a storage or lifecycle consequence after explicit semantic disposition; it never hides or substitutes for rejection, deferral, revision request, or approval.

Pull requests are delivery and recurring intake membranes, not proof of acceptance. Project Server normally creates or updates one integrated PR per Change only after every required Work Unit has a current passing Implementation Gate, all required outputs integrate, dependency closure holds, and one exact aggregate lineage head is frozen. It retrieves authenticated reviews and provider Checks, correlates them to that head, and starts Review. Automated Code and independently isolated Model Checks may provide the complete basis when policy permits. A passed Review Gate permits guarded merge only under current authority, provenance, freshness, branch policy, and expected-head compare-and-swap. Failed Review feedback normally reopens affected Work Unit Implementation; decomposition and meaning defects require explicit Planning or Decision operations. Out-of-scope findings enter Change Intake. Provider metadata alone grants no provenance, approval, Result, or merge authority.

Backend v1 keeps one dossier per Change at `.codewiki/traces/TRACE-CHG-<id>.jsonl`; terminal retention may replace its hot file with a verified stub backed by an immutable Git restore ref, and hydration is read-only. No generic `.codewiki/changes.log` exists. Execution Ledgers, raw DSH sessions, delegated child traces, prompts, query calls, Compaction Checkpoints, provider memory, and scratch remain receipt-bound execution evidence outside Change Trace unless a semantic operation cites their immutable Receipt.

Semantic Kernel target advances Change Trace to `13.0.0` and moves each dossier to `.codewiki/changes/TRACE-CHG-<id>.jsonl`. This is the sole semantic Change representation: immutable header, then bounded typed canonical-JSON operations with unique operation IDs in file order. Every new Git blob preserves its predecessor as an exact byte prefix. Every proposal commit first-parents current canonical; later versions second-parent prior managed tip. It appends complete `change.proposed` plus optional Item changes. Its OID is version; first-parent/tree identity derives Wiki change. No record-digest chain, custom tip, Change snapshot, peer Wiki Update, authored impact union, or shadow operation exists.

Project Server alone writes deterministic `refs/codewiki/changes/**` refs that retain active proposal history. Target traces are never compacted, truncated, replaced, deleted, or stubbed. Reachable Git history stays canonical. WorkState, rehydration projections, and lossy summaries bind exact source commit/path/blob/range and remain non-authoritative; future segmentation requires a separately qualified Git-backed layout. Trace stores accountability meaning, not every incidental execution event.

Confirmation revalidates Actor, Candidate, Gate, exact proposal commit, active Changes, expected canonical commit, derived Wiki tree, and managed-ref tip. It creates one disposition commit whose first parent is expected canonical and second parent is that exact tip. Acceptance uses proposed Wiki; rejection/defer/withdraw retains first-parent Wiki. Terminal Trace binds proposal/branch OIDs, changed/retired Item IDs, judgment, authority, and frozen requirements without containing-commit self-reference. Canonical-ref CAS makes disposition atomic and ancestry retains all proposal bytes. Empty requirements complete only with non-empty Wiki diff; empty-diff repair requires Item-targeted work. Fresh Sessions reduce exact Git commits and fixed-path Wiki/Trace blobs, never conversation or summary authority. Compensation/supersession uses a new Change proposal; accepted history remains.
