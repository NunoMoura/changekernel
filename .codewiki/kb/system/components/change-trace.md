# Change Trace

A Change carries one accountable proposed transition from accepted Knowledge State `S0` to intended state `S1`; its Change Trace is the append-only canonical operation history for that intent carrier. Knowledge remains authoritative for current accepted desired state, while Change records why and how that state was proposed, judged, confirmed, realized, or reversed. Strict canonical bytes, typed operations, parent identity, authority binding, preconditions, and deterministic reduction make replay and synchronization verifiable. Change Trace Protocol `12.0.0` binds each authority-bearing operation to one accountable `actorId` and one proof-backed `authenticatedIdentityRef`; Client transport identity remains request provenance rather than canonical actor identity.

Each immutable Change revision binds bounded human problem and objective summaries, rationale, alternatives, outcomes, acceptance requirements, stable Knowledge subject or facet targets, and either one complete reducible Knowledge transition or explicit unchanged-Knowledge references. Summaries explain intent but cannot copy current Knowledge bytes or substitute for exact Effects. A transition contains a canonical atomic set of `set` or `retire` Effects. `set` stores one complete bounded post-state artifact once inline; `retire` preserves target identity through a tombstone. Expected prior state or absence is bound by exact identity rather than copied prose. Paths, headings, model-owned offsets, fuzzy replacement instructions, generated propagation lists, and repeated current bytes are not semantic transition authority.

At Decision Candidate checkpoint, Project Server binds the exact revision and Effects to the observed Knowledge State, accepted active Changes, compiler identity, deterministic application plan, projected Knowledge State, and projected Markdown or YAML identity. Only an authorized confirmed `approve` operation admits those unchanged Effects into accepted Knowledge reduction. Project Server commits Decision confirmation, Change Trace operation, resulting Knowledge identity, and WorkState commitment atomically under expected-head compare-and-swap. Rejected, deferred, withdrawn, failed, or merely passed Candidates remain history but never alter accepted Knowledge. Committed history is never reversed or erased; semantic reversal is another explicit Change. Global synchronized operation order and per-target prior-state checks permit byte-reproducible reconstruction and conflict detection without treating generated projections as independent truth.

Canonical history also binds immutable Change-scoped Planning deltas through typed `planning.delta_accepted` operations, singly owned Work Units, exact Knowledge Effect, unchanged-Knowledge, and acceptance-requirement coverage, explicit amendment lineage, their Candidates and Gates, and Project Server-owned scheduling admission. A canonical Work Unit Claim binds the exact WorkState and Work Graph heads, Worker Offer, scheduling policy, source base, scope, obligations, budget, lease, and assigned Workbench. Its atomic Assignment binds the same Claim, Worker Offer, isolated Workbench, and assignment digest. An Implementation attempt then records one exact Work Unit Candidate, shared stage policy, Evidence, independently completed Results, Gate Report, and `gate_failed` or `integration_pending` route without treating Gate passage as integration. Typed `integration.candidate_admitted` operations persist exact Private Integration Receipt `1.0.0` artifacts and reduce Private Change Integration Lineage `1.0.0` under lineage-head and Change-tail compare-and-swap. Typed `implementation.aggregate_frozen` records Implementation Aggregate `1.0.0` only after every required unit, dependency, accepted Effect, unchanged-Knowledge target, and acceptance requirement is covered. Git stores exact private commits and trees; Trace records their semantic admission; derived WorkState records current lineage and aggregate. No separate object store or per-unit protected merge is canonical authority. Aggregate Review then records one exact Review Attempt `5.0.0`, its fresh `review:<change-id>:<lineage-digest>` producer continuity and Run receipt, Project Context Snapshot, Check Pack, Evidence, Results, typed failure ownership, Gate Report, and fixed Project Server route. A failed route invalidates delivery authority and reopens only affected Implementation, explicit Planning amendment, or Decision. Typed `delivery.applied` history binds one exact passed current Review, Delivery Authority `1.0.0`, protected target, expected target head, delivered commit, and delivered tree after target-head compare-and-swap. The trace therefore connects accepted Knowledge meaning to everything that later realizes it while remaining a transition dossier rather than a second current-state encyclopedia.

Mutable allocation does not alter immutable Change meaning. Reviewer, contributor, Stage Producer, Implementation Worker, and machine identities live in policy-bound requirements, Claims, Assignments, producer attempts, and operations rather than Change revisions. A Review Requirement binds one exact revision, review class, scope, minimum approvals, independence rule, and policy digest. A Review Claim records current responsibility without implying approval. A Review Submission immutably binds one authenticated `approve | request_revision | defer | reject` disposition, rationale, Evidence references, Claim, delegation where applicable, and Project Server-owned time.

Human Review Submissions are optional inputs to the Review Stage Loop unless the user's Review Checks require them. Actor Profile, expertise, job title, CODEOWNERS, repository access, Agent or model identity, and Client kind cannot grant review or delivery authority. Project Server admits any Review Submission only when one exact Authority Grant and current policy authorize the actor for that requirement and revision. Archive remains a storage or lifecycle consequence after explicit semantic disposition; it never hides or substitutes for rejection, deferral, revision request, or approval.

Pull requests are delivery and recurring intake membranes, not proof of acceptance. Project Server normally creates or updates one integrated PR per Change only after every required Work Unit has a current passing Implementation Gate, all required outputs integrate, dependency closure holds, and one exact aggregate lineage head is frozen. It retrieves authenticated reviews and provider Checks, correlates them to that head, and starts Review. Automated Code and independently isolated Model Checks may provide the complete basis when policy permits. A passed Review Gate permits guarded merge only under current authority, provenance, freshness, branch policy, and expected-head compare-and-swap. Failed Review feedback normally reopens affected Work Unit Implementation; decomposition and meaning defects require explicit Planning or Decision operations. Out-of-scope findings enter Change Intake. Provider metadata alone grants no provenance, approval, Result, or merge authority.

Terminal history may move from hot coordination into immutable archive segments only after exact digest acceptance. Hydration is read-only. Reopening creates a new accountable hot segment rather than rewriting archived history. Canonical Change logs remain one file per Change under `.codewiki/traces/TRACE-CHG-<id>.jsonl`; no separate `.codewiki/changes.log` exists. Git remains the artifact-history owner. Execution Ledgers, raw DSH sessions, delegated child traces, exact prompts, query calls, Compaction Checkpoints, provider memory, and code-runtime scratch remain receipt-bound execution evidence outside Change Trace unless a semantic operation references their immutable receipt. Change Trace records authority-relevant meaning needed for accountability closure rather than every incidental Agent or repository interaction.
