# Implementation

Implementation satisfies one accepted Work Unit at a time in one Project Server-owned isolated Workbench. Work Unit Candidate `2.0.0` binds the exact Assignment and Workbench, owning Change revision, accepted Work Graph delta and Work Unit digest, covered stable Knowledge Effect, unchanged-Knowledge, and acceptance requirement IDs, source base, resulting tree, changed paths, Evidence identities, and Run receipts. Before each initial or escalated model route begins, Project Server creates Work Unit Model Assignment `2.0.0` over the scheduled Assignment, Work Unit, user-authorized Worker route pool, exact selected provider/account/credential/model route and policy snapshot, prior typed attempts, remaining budgets, and rationale. Planning declares requirements and risk but cannot select providers or models. A route change creates a new Run and fresh DSH Agent Session; bounded Runs on the unchanged route may continue only through exact Session-head custody.

Backend v1 permits one `implementation:<work-unit-id>` DSH Session to span up to eight bounded Runs across feedback, but exactly one final completed Run may produce each Candidate. Semantic Kernel target retains its Work Continuity key while closing each physical Session at terminal Run Receipt. Feedback revision or route escalation starts a fresh Session with exact Assignment, Workbench, accepted Completion Requirements, prior Candidate, failed Results and Gate Report, typed failure ownership, current source head, and predecessor Receipt. Only recovery of the same unreceipted in-flight Run may resume its physical Session.

Project changes satisfy accepted desired meaning; they cannot redefine it. Admitted CodeWiki Plugins may prepare external workspace, observe verification, or prepare integration through capability-scoped Requests/Receipts, but cannot write canonical Git/Wiki, issue Results, or complete Change. Independent ready Work Units may execute and be judged concurrently. Each coherent completed unit emits its own immutable Candidate and immediately enters its own Implementation Gate; Checks do not wait for all Workers. No Change-level model coordinator or Harness Agent owns scheduling, feedback forwarding, Worker retry, or canonical aggregate state; Project Server and WorkState provide that coordination.

Implementation Stage Policy `1.0.0` content-addresses one resolved stage-wide Implementation Check Pack snapshot and applies it to every Work Unit Candidate. Planning, workers, and routes cannot choose or author a Work Unit-specific Pack. Each Gate freezes the exact current resolved `.codewiki/check-packs/implementation/**` snapshot; a policy edit creates a new stage-wide snapshot and invalidates affected remaining Results rather than creating per-unit variants. Evaluation inputs vary only by exact Candidate, owning Change acceptance slice, Work Unit Completion Requirements, pinned base and dependencies, changed paths, stable Knowledge-to-source/test mappings, Evidence, and receipts. Deterministic Pack applicability rules may return `not_applicable`; they do not create another Pack. Optional Implementation Pack Skills guide production but never judge output or grant authority.

A failed Implementation Gate returns atomic feedback to the same Work Unit loop. A passed Gate qualifies only that exact Work Unit Candidate. Private Integration Receipt `1.0.0` binds Candidate/Gate and exact owning Change revision in Backend v1 or accepted proposal commit OID in target, Work Graph and delta, Work Unit acceptance slice and dependencies, Assignment, Workbench, custody receipts, observed Candidate tree and changed paths, prior lineage head, private Git base, result commit and tree or conflict, and Project Server time. Expected-head compare-and-swap reduces receipts into Private Change Integration Lineage `1.0.0`; Git retains exact commits and trees while Change Trace stores canonical admissions and WorkState derives the lineage. No third artifact store or protected-branch mutation occurs. `gate_failed`, `gate_passed`, `integration_pending`, `integrated`, `stale`, and `conflicted` remain distinct. Stale base, graph or dependency drift, changed bytes, lost custody, or conflict blocks admission or records a non-integrated conflict receipt; changed meaning returns to Decision as a new Change with its own proposal version.

Change remains in Implementation until every required Work Unit has a current passing Gate, every required output is integrated exactly once, dependency closure holds, and current Effect/unchanged-Knowledge or target Completion Requirement coverage is complete. Only then may Project Server freeze Implementation Aggregate `1.0.0`, binding exact lineage, Git head and tree, Work Graph and deltas, receipts, Candidates, Gate Reports, Work Units, and coverage. Only that deterministic completion condition advances the Change to Review. Unit Gates prove local outcomes; they do not certify cross-unit behavior, Change completion, or protected Delivery. Project Server owns Claims, dispatch, integration, persistence, completion reduction, recovery, transitions, and effects. Checks owns shared execution and Gate mechanics.
