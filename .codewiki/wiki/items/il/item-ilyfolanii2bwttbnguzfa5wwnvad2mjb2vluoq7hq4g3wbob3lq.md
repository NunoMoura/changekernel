# Work Unit Execution

Project Server grants one exact Work Unit Claim, selects eligible Worker from Offers/policy, creates and verifies one isolated Workbench (optionally through admitted `workspace.prepare` Plugin Request/Receipt), mounts one authorized Run Context Bundle, snapshots optional Implementation Pack Skills, and persists one scheduled Assignment. It then resolves only the user-authorized Worker route pool and creates Work Unit Model Assignment `2.0.0`, binding the scheduled Assignment, Work Unit, selected AI Provider, account, credential reference and model, exact options and policy snapshot, attempt, remaining budgets, and rationale. The Run Request binds both Assignment identities. Planning, Harness Agent, Worker, DSH, AI Gateway, and AI Provider cannot select or widen that route. Backend v1 `implementation:<work-unit-id>` Session may span eight bounded Runs while lineage, Build, route, and custody remain compatible. Target Work Continuity starts fresh physical Session after each terminal Run; only same-unreceipted-Run recovery resumes exact log. Each Work Unit Candidate `2.0.0` has exactly one final producing Run and binds all prior receipt identities without copying their bytes. The Worker mutates only its Workbench and cannot grant Claims, schedule canonical descendants, share mutable Workbenches, write canonical state, create authoritative Results, or perform effects.

Every Work Unit Candidate is judged by the same resolved stage-wide Implementation Check Pack policy. Project Server resolves one content-addressed Implementation Stage Policy `1.0.0`, then freezes one Work Unit-specific Gate Evaluation Package `2.0.0` containing the exact Candidate subject and resolved Check Pack snapshot and binding the Work Unit, Assignment, result tree, accepted Knowledge/Wiki targets, current acceptance or target Completion Requirements, project base, WorkState, Evidence, configuration, routes, declared selections, and execution identities. The package replaces the former Implementation-only package shape; Planning and workers cannot select a bespoke Pack. Independent unit Gates and their isolated Model Checks may run concurrently.

A failed Gate returns the exact Project Server-recorded Results and Gate Report directly to the same Work Unit continuity. Harness Agent may observe a compact current failure projection and exact report reference for user explanation, but it never authors, rewrites, or forwards feedback. A passing Gate qualifies only that exact Candidate. Project Server verifies current Change, Work Graph, dependency, Assignment, Workbench, custody, Candidate tree, changed paths, and Gate identities before creating current Private Integration Receipt `1.0.0` or admitting target `integration.prepare` Plugin Receipt. Expected-head CAS appends admission to Change Trace and reduces Private Change Integration Lineage `1.0.0`; Git stores exact worktree commits/trees and Project Server alone admits canonical integration. `gate_failed`, `gate_passed`, `integration_pending`, `integrated`, `stale`, and `conflicted` remain distinct. Claim loss, malformed output, base or dependency drift, changed custody or bytes, and conflict cannot claim integrated output or alter protected state.

The Change does not enter Review after one unit passes. Project Server advances only after every required Work Unit has a current passing Gate and exact integration receipt, dependency closure and current Effect/unchanged-Knowledge or target Completion Requirement coverage holds, and Implementation Aggregate `1.0.0` freezes the exact private Git and Change Trace lineage for Review.
