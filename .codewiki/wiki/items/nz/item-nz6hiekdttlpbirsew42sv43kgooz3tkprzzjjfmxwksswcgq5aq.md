# Project Server

Project Server is sole authoritative semantic control plane and long-lived owner for one governed project. Transport, identity-proof validation, Actor mapping, project AuthZ, canonical state, Change acceptance/completion, Stage Loops, Checks, Workbenches, guarded effects, and recovery share one owner. Each Project Server owns one subordinate Runtime for bounded execution. Runtime cannot authorize project operations or mutate canonical state.

A CodeWiki process may host several Project Servers behind one shared listener. The listener performs only connection acceptance and project lookup; it is not a semantic Gateway and owns no identity, policy, project state, or lifecycle. Client disconnection never stops accepted work.

## Request boundary

Every request follows one fixed order:

```text
Client transport
  -> Project Server identity-proof validation and Actor mapping
  -> Project Server project AuthZ
  -> command or query
  -> optional Run Request to Runtime
  -> Run Receipt
  -> Candidate admission and deterministic materialization
  -> Checks, Gate, confirmation, and Change operation
```

Identity proof establishes Actor connecting now. Pairing enrolls one Client installation; Client Session is one temporary authenticated connection. Project AuthZ independently decides whether Actor may perform exact operation. Pairing, Client kind, repository access, title, model identity, App UI, and transport never imply authority.

Backend v1 AuthN is narrow internal code. Semantic target lets CodeWiki App or external IdP own login UX, SSO, OIDC, MFA, and token acquisition, but Project Server accepts only configured signed, mutually authenticated, or scoped local proof. It validates issuer, subject, audience, expiry, signature/channel binding, replay/delegation state, then maps stable Actor. Unsigned actor headers and hidden-button policy grant nothing. External policy evaluator may advise; Project Server remains enforcement point. Credentials never enter project files, Run Requests, model context, Pairing, or Runtime.

Client Sessions use digest-only credential bindings, bounded lifetimes, rotation, revocation, generation compare-and-swap, and endpoint policy that never receives raw credentials. AuthN, Pairing, Client Sessions, repository-access observation, and project AuthZ remain distinct internal responsibilities. Browser App requests use secure same-origin, `HttpOnly`, and `SameSite=Strict` session handling; installed CLI, Pi, and MCP Clients require explicit enrollment according to policy.

## Project authority

Project Server owns Actor/delegation binding, idempotency, admission, time, digests, freshness, canonical/managed Git-ref CAS, Wiki Item/diff validation, Candidate attempts, active Changes, Completion Requirement reduction, Work Graph, scheduling, Claims, Assignments, integration, Plugin admission/Requests/Receipt verification, persistence, recovery, transitions, and effects. It authorizes the accountable Actor, not the Client, Runtime, or executor.

Git owns Backend v1 artifact history and target Project/Wiki/Trace versioning. Project Server uses sanitized Git plumbing, rejects incomplete/overridden history, validates objects, and alone writes canonical or managed Change refs. Canonical first-parent history is accepted state; terminal second-parent ancestry retains proposals. Reflogs, dangling objects, notes, replace refs, commit metadata, provider status, and Plugin Receipts are not lifecycle authority. Remote mechanics use admitted Plugins. External drift pauses guarded effects; Project Server never silently adopts or certifies it.

Project Server invokes exactly four Stage Loops under `src/loops/**`: Decision, Planning, Implementation, and Review. Checks separately owns Check Packs, Results, coordination, and Gate Reports. Stage Loops own subjects, Candidates, attempts, and feedback meaning. Backend v1 Project Server owns Project Context Snapshot `1.0.0`. Target replays canonical owners, rebuilds WorkState, and materializes one authorized immutable Run Context Bundle per Run; changed context requires a fresh Run/Session. After Candidate checkpoint it freezes Gate Evaluation Package `2.0.0`, resolving every declared input once and binding source heads, stage lineage, Check files, execution identities, and complete coverage before Checks run.

Project Server applies one fixed authority model:

```text
Decision pass + confirmation + expected-old Git ref CAS
  -> two-parent disposition: canonical first parent + managed proposal tip
  -> accept derived Wiki diff and freeze requirements
  -> completionRequirements:[] ? completed : Planning
Planning delta + Work Graph CAS -> Implementation
Work Unit pass -> integration pending; stale/conflict -> same Work Unit
All required Work integrated -> Review
Review pass -> required Delivery, if declared -> completion evaluation -> completed
Review unit defect -> affected Work Unit; decomposition defect -> Planning; meaning defect -> Decision
Any Gate stopped -> preserve state and stop attempt
```

Backend v1 applies equivalent Knowledge Effect and acceptance-requirement operations under current protocols.

Gate pass means exact Candidate meets current Checks; it is not acceptance, integration, Delivery, or completion. Backend v1 expands handles and compiles Knowledge Effects. Target uses proposal commit OID as version and verifies canonical parent, managed-ref ancestry/tip, Trace prefix, derived Item diff, Item/reference/provenance/retirement closure, authority intent, and requirements. Candidate/Gate bind canonical/proposal commits and trees. Invalid admission stops before Checks.

Authorized Actor confirms passed Decision Candidate/Gate against current WorkState, canonical commit, proposal ref tip, derived Wiki tree, and active-Change heads. Backend v1 `approve` commits Change plus compiled Knowledge transition. Target confirmation creates one two-parent disposition commit containing terminal Trace; acceptance uses proposed Wiki while other dispositions retain first-parent Wiki. It advances canonical ref by expected-old-OID CAS, retires managed proposal ref, and freezes Completion Requirements when accepted. Planning cannot revise them. Work Unit pass advances only that unit; all required units integrate before Review. Project Server owns typed failure routing and alone derives `change.completed` from exact requirements, reviewed aggregate, Evidence/Results, integration lineage, qualifying Plugin Receipts, and required Delivery Receipts. Checks, Runtime, models, Apps, and Plugins cannot perform lifecycle transitions by assertion.

## Runtime ownership

Project Server authorizes Requests and validates Receipts. Backend v1 Session Continuity spans Runs. Target Work Continuity gives each Run one Session; terminal Receipt closes it, and successors rehydrate canonical state plus predecessor Receipt. Same-Session recovery preserves the unreceipted Run semantic digest in a new repaired-head dispatch. Changed bindings stop; ambiguous closure enters non-waivable `recovery_stopped`. Runtime owns mechanics only.

Only Implementation uses Workbenches. For each ready unit, Project Server matches Offers/policy, then CAS-binds Claim, Assignment, project base, lease, and isolated Workbench. Target may issue `workspace.prepare`, `verification.observe`, or `integration.prepare` Plugin Requests; complete verified Receipts provide proposed artifacts/mechanics, never canonical-ref or completion authority. Runtime and generic mutation expose no Claim, queue, placement, or integration authority. Project Server admits exact fresh passing Candidates through `integration.candidate_admitted`, lineage-head CAS, and dependency, custody, and byte checks. Git stores exact worktree commits/trees and canonical integration; Change Trace stores admission/Plugin Receipts, and WorkState derives Private Change Integration Lineage `1.0.0`. `implementation.aggregate_frozen` records Aggregate `1.0.0` only after all-unit and acceptance coverage; no per-unit protected merge occurs.

## Custody and recovery

Controlled provenance requires exact persisted custody appropriate to the stage. Backend-owned custody adds a complete Run Receipt and CodeWiki-controlled Execution Ledger. Backend-delegated custody binds exact dispatch, delegate identity, configuration policy, process lifecycle, Workbench when applicable, final output, admitted artifacts, and explicit unknown child internals. External-client provenance binds only authenticated CodeWiki operations and any admitted Workbench custody. Candidate-supplied receipts or Gate claims are untrusted.

On restart, Project Server reloads canonical and managed Git refs/commits, fixed-path Wiki trees and complete `.codewiki/changes/**` traces, proposal and requirement facts, Work Graph deltas, Plugin Receipts, configuration, Skills/Checks, jobs, Claims, Assignments, integration lineages, Workbenches, Run Receipts/Ledgers, Gates, completion, and guarded effects. Backend v1 verifies Knowledge seed plus confirmed Effects. Target verifies complete Git ancestry/object closure, first/second-parent disposition structure, every Trace predecessor-byte prefix, proposal/managed-ref identities, Item/reference/retirement closure, and expected ref history, then rebuilds WorkState/Alignment. Recovery never fabricates Git acceptance, Knowledge transition, Result, integration, completion, or lifecycle authority.

The supported operational package surface is `src/project-server/index.ts`, published as `@nunomoura/codewiki/project-server`. Its public API exposes bounded commands, queries, operations, and events. Internal coordination remains under `src/project-server/coordinator/**`; this implementation detail is not a second product owner. Project Server imports no DSH, Cordis, or delegated-harness implementation; those remain behind Runtime contracts.
