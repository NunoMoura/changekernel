# DSH Run Execution

DSH is the operational plane for every CodeWiki-controlled Agent. Project Server authorizes one exact Run through the host-neutral Agent Runtime port. The DSH adapter maps that authorization to qualified DSH and Execution Host mechanics, then maps bounded output and custody closure back to an untrusted typed result/receipt for Project Server validation. DSH owns Agent execution, internal Sessions, model/tool continuation, AI/model provider mechanics, and compaction. CodeWiki owns Change/Wiki meaning, stage subject, Actor authority, exact context and capability ceiling, Gate coordination, Git admission, and receipt validation. Execution Host contains the process and physically enforces resource, cancellation, and isolation guarantees.

```text
Project Server
  -> Agent Runtime port
  -> DSH adapter
  -> Execution Host
  -> DSH Agent + authorized tools + AI/model provider
  -> optional scoped Preview handle -> Preview port/adapter
  -> DSH adapter result/receipt mapping
  -> Project Server validation
  -> Project Store / Gate / next action
```

CodeWiki does not create a second Agent runtime or assign semantic meaning to opaque DSH Session bytes. “Physical DSH Session” is not a Kernel lifecycle concept. Every immutable Run authorization binds one Run and idempotency identity. Transport retry or reconciliation of unchanged authorization reuses that identity and cannot launch duplicate semantic execution; DSH may recover an internal Session only inside the same authorized Run and qualified closure. Changed semantic input or a new semantic attempt requires a new Run. After failure, timeout, or cancellation, Project Server may authorize that successor only when the predecessor has a validated terminal receipt or independently proven process/effect quiescence and custody closure.

Every Run binds exact repository/project commit, managed Change tip where relevant, stage and subject, Actor/authority, role route, model/provider references, tool/capability closure, budgets, deadline, writable scope, mandatory Wiki context, feedback, and predecessor receipt refs. Project Server may materialize sealed read-only input/cache for execution efficiency, but it is derived Run input rather than cross-Run authority or a peer Context Bundle lifecycle. Git, Delivery, remote synchronization, publication, and other protected provider effects are not DSH provider mechanics; they use separately admitted Plugins authorized by Project Server.

Product-fixed role instructions are immutable build-bound policy values validated by Kernel mechanisms and supplied by Project Server; they are not executable policy hidden inside the pure Kernel. They require Agents to treat supplied Wiki as accepted intent, use stable Item IDs, resolve ambiguous terms through bounded tools, surface unknowns, and never silently reinterpret committed meaning. Project Server supplies deterministic target Items/Definitions from Change or Work Unit refs and permits bounded exact Wiki, link, Dictionary, history, diff, Alignment, Evidence, and Project queries. DSH Run receipts bind exact visible inputs, bounded query refs, outputs, and Gate context. That ordinary receipt is sufficient usage provenance; no standalone Wiki Usage Receipt is another authority. Stage Checks judge actual output; a tool call alone does not prove understanding.

Role capabilities differ. Decision may propose Wiki bytes but cannot write refs. Planning reads Committed Change and proposes Work Units. Worker receives one isolated writable Git worktree for project-artifact scope while Wiki/Trace remain read-only. When exact Work Unit and Run authorization grant `preview.work`, Worker receives only a scoped, revocable Preview handle; observations are producer feedback and cannot satisfy a Gate. Review reads the exact reconciled prospective Completion tree. Project-authored Model Checks receive only Gate-declared bounded inputs, no tools, and no producer memory; a Product-fixed semantic Model Check may receive explicitly declared bounded read-only Wiki/View tools. A fresh Model Check may consume already-captured immutable `preview.verify` Evidence but cannot launch producer Preview. Deterministic Code Check Runs use separate admitted sandboxes rather than DSH Agent execution.

Project Server requests cancellation through the Agent Runtime port. DSH and Execution Host perform cancellation and process-tree cleanup; Project Server validates the terminal receipt. Timeout, lease expiry, transport loss, cancellation request, or process exit alone never yields a Result, integration, or lifecycle transition. Missing or contradictory closure stops and blocks a successor semantic Run until quiescence is proven.

Execution evidence, raw DSH data, provider records, credentials, logs, caches, sockets, and temporary files remain in owner-private external state. They never enter project Git unless a bounded semantic Trace operation cites an immutable receipt. Each Agent-capable Product release binds one exact supported Agent Runtime contract, DSH adapter, DSH package closure, Execution Host profile, and qualification record. Unsupported or obsolete pre-stable execution records remain in release evidence rather than active Product readers. Public APIs expose only CodeWiki Run authorization and validated receipt semantics; they never claim CodeWiki owns the Agent runtime that DSH owns.
