# DSH Run Execution

DSH is the operational plane for every CodeWiki-controlled Agent. Project Server authorizes one exact DSH Run; DSH owns Agent execution, internal Sessions, model/tool continuation, provider mechanics, and compaction. CodeWiki owns Change/Wiki meaning, stage subject, Actor authority, exact context and capability ceiling, Gate coordination, Git admission, and receipt validation. Execution Host contains the process and enforces resource and isolation guarantees.

```text
Project Server
  -> DSH Run authorization
  -> Execution Host
  -> DSH Agent + tools + provider
  -> DSH Run result/receipt
  -> Project Server validation
  -> Change Trace / Gate / next action
```

CodeWiki does not create a second Agent runtime or assign semantic meaning to opaque DSH Session bytes. “Physical DSH Session” is not a Kernel lifecycle concept. DSH may use or recover internal Sessions as qualified mechanics; Project Server sees one bounded Run identity, exact authorization, output, receipt, and operational outcome. A retry or changed semantic input creates another DSH Run.

Every Run binds exact repository/project commit, managed Change tip where relevant, stage and subject, Actor/authority, role route, model/provider references, tool/capability closure, budgets, deadline, writable scope, mandatory Wiki context, feedback, and predecessor receipt refs. Project Server may materialize sealed read-only input/cache for execution efficiency, but it is derived Run input rather than cross-Run authority or a peer Context Bundle lifecycle.

Kernel-owned role instructions require Agents to treat supplied Wiki as accepted intent, use stable Item IDs, resolve ambiguous terms through bounded tools, surface unknowns, and never silently reinterpret committed meaning. Project Server supplies deterministic target Items/Definitions from Change or Work Unit refs and permits bounded exact Wiki, link, Dictionary, history, diff, Alignment, Evidence, and Project queries. DSH Run receipts bind exact visible inputs, bounded query refs, outputs, and Gate context. That ordinary receipt is sufficient usage provenance; no standalone Wiki Usage Receipt is another authority. Stage Checks judge actual output; a tool call alone does not prove understanding.

Role capabilities differ. Decision may propose Wiki bytes but cannot write refs. Planning reads Committed Change and proposes Work Units. Worker receives one isolated writable Git worktree for project-artifact scope while Wiki/Trace remain read-only. Review reads exact integrated tree. Project-authored Model Checks receive only Gate-declared bounded inputs, no tools, and no producer memory; a fixed Kernel semantic Model Check may receive explicitly declared bounded read-only Wiki/View tools. Deterministic Code Check Runs use separate admitted sandboxes rather than DSH Agent execution.

Execution evidence, raw DSH data, provider records, credentials, logs, caches, sockets, and temporary files remain in owner-private external state. They never enter project Git unless a bounded semantic Trace operation cites an immutable receipt. Missing or contradictory closure stops; Project Server never fabricates a Result, integration, or lifecycle transition from process exit.

Backend-v1 Runtime, Runtime Build, Bridge, Run Request/Receipt, Session continuity, compaction, provider broker, and sandbox protocols remain qualified executable/history evidence. Target architecture may retain internal adapters and host qualification, but wording and public API must not claim CodeWiki owns the Agent runtime that DSH owns.
