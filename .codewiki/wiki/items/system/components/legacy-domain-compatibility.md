# Legacy Domain Compatibility

Backend v1 used one executable Domain Plugin to define concept schemas, relationships, projections, default Check Pack resources, and software-development behavior. The Kernel has no Domain identity in Project configuration, Wiki Item validation, Kernel Build, Change/Gate contracts, or normal Run records. Domain is not a semantic extension point.

Kernel owns stable Wiki Item identity, open namespaced `itemType` and relationship values, one Change lifecycle, fixed Change type taxonomy, four stages, Gate reduction, authorization, Git CAS, Review, and protected effects. Project Wiki Items and Check Packs express domain-specific meaning/policy as data. They cannot add a stage, status, authority source, semantic store, compiler, Agent runtime, or lifecycle transition.

Release-managed Check Pack templates originate from packaged resources, but installation is passive one-time copy/adoption. The project owns resulting bytes. No executable Domain code runs during bootstrap, startup, Wiki query, proposal admission, Gate construction, or migration.

One isolated compatibility component may read retained Backend-v1 Domain-bound checkpoints, Pack records, fixtures, and receipts for diagnosis or explicit migration. It binds exact historical Domain identity and fails closed on unknown/drifted inputs. Historical package integrity is never recomputed from the evolving target package manifest. The component cannot create Wiki truth, synthesize missing identity, participate in current Gates, or dual-write old and new owners.

New specialization uses ordinary Wiki Item types/relationships, project Check Packs, bounded CodeWiki Plugins for external mechanics, and DSH role routes for Agent execution. A future executable semantic extension mechanism would require a new governed architecture and qualification rather than reviving Domain Plugin authority implicitly.
