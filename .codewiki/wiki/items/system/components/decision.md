# Decision

Decision is the first phase of one Change lifecycle. It aligns and validates intent before Planning or implementation consumes material resources. The Decision Agent is the only user-facing CodeWiki Agent role. It helps the user explore alternatives, query exact Wiki meaning, resolve terminology, split independently decidable outcomes, and prepare a Proposed Change. It is not the authenticated Actor, a Check, the Change committer, or Project Server authority.

Conversation and local drafts are mutable working material. They carry no Wiki, Change Trace, Git-ref, Result, or lifecycle authority. An authenticated submission creates or revises one Change on its managed ref. Each revision is a full Git snapshot of the governed Project whose Decision-phase delta is limited to that Change Trace and proposed Wiki Item/link changes. Its commit OID is the exact Proposed Change version.

A proposal binds the expected project head, stable Change identity or request-local key, intent and rationale, explicit relationships to other Changes, accountable submitter, and producer DSH Run where applicable. It declares exactly one `changeType`—`capability`, `correction`, `maintenance`, `policy`, or `investigation`—and exactly one `realization`—`wiki-only` or `project`. The Wiki post-state plus optional stable references to existing Wiki meaning is the semantic target; no separate requirement object restates it. A `project` Change may have no Wiki file diff when existing accepted Items already express the complete target; its Trace binds those Item/facet references and rationale.

Project Server validates identity, authority, expected-tip and expected-head compare-and-swap, complete Git objects, append-only Trace prefix, changed-path bounds, Wiki Item identity and relationship closure, and resulting Project/Wiki tree before creating a Gate. The Gate binds the exact Proposed Change snapshot, exact Decision Check Pack policy, frozen type-conditioned active Checks, declared inputs, and Gate digest. Proposal bytes, Agent role, route, and model cannot select or suppress Checks.

Change type describes purpose; realization describes work remaining after acceptance, not importance or file location. A terminology clarification may be Wiki-only if its complete outcome exists in the accepted snapshot. A Wiki proposal requiring a new artifact capability remains project realization. Small or Wiki-only policy changes can require stringent Checks; no classification grants arbitrary stage skipping.

Decision executes only explicitly adopted project Checks; no Product-authored alignment rubric is mandatory. A completely resolved empty policy produces an explicit warning, not a semantic verdict. Required Checks use exact declared inputs and independent execution. Missing material or unavailable execution stops; a failed judgment is addressed through a revised proposal and fresh affected Check Runs, not by suppressing judging policy.

A passed Gate makes only that exact Proposed Change eligible for an authenticated command. `commitChange` revalidates the Actor, Gate, active Checks and Results, Change tip, expected project head, Wiki delta, Change type, realization route, and active-Change dependencies. Project Server then creates the two-parent Change Commit and advances the project ref by expected-old-OID compare-and-swap. A true Wiki-only Change records both `change.committed` and `change.completed` because the full committed Project snapshot already realizes its target. A project-realization Change records `change.committed` and proceeds to Planning.

Before commitment, an authorized Actor may reject or defer a Proposed Change, and its submitter may withdraw it according to policy. Those outcomes append Trace on the managed Change ref without advancing canonical project history; deferral remains resumable. After commitment, the Change cannot be rejected or withdrawn. Wrong or changed intent requires a Superseding Change.

Trace and Git ancestry preserve every contributor. The Actor who commits the Change is accountable for the complete accepted intent; earlier proposal contributors, producing DSH Runs, Check Runs, Results, and the mechanical Project Server committer remain separately attributable. Attribution grants no lock, veto, or future authority.
