# Wiki

Wiki is the Git-versioned body of accepted descriptive, historical, and normative Project meaning. It records what collaborators have committed the Project to mean and do. It may intentionally lead current physical realization between Change Commit and Change Completion Commit; Alignment reports that owned gap. Source and tests record tracked Project bytes, Evidence records observations, Results record judgments, and Change Trace records why meaning and realization changed.

Every governed Project uses one local Git repository and configured project ref. Wiki Items are ordinary UTF-8 Markdown or YAML files directly within `.codewiki/wiki/**`, one Item per file. Category directories organize Items without an additional `items/` container. Every file in the declared Item tree follows the supported Item contract; indexes, caches, runtime state, and peer metadata stores do not live in that tree. Wiki Item is the sole first-class Wiki entity. Stable Item ID—not path, title, alias, body, Git OID, installation, or model output—establishes identity. Readable portable paths aid navigation; moves preserve Item ID. Git and Trace history reserve retired IDs.

Normal authored paths use meaningful lowercase category directories and kebab-case filenames, such as `.codewiki/wiki/system/components/checks.md`. A title change does not force a path change; an explicit move is an ordinary reviewed Git rename. Hash-derived filenames remain valid historical/import artifacts and content hashes/Git OIDs remain integrity identifiers, but normal authoring and Client links do not require opaque hash paths.

Canonical Item paths are NFC UTF-8 below `.codewiki/wiki/`, use lowercase ASCII category and filename segments, and end in `.md`, `.yaml`, or `.yml`; only non-executable regular Git blobs are admitted. Files are BOM-free NFC UTF-8 with LF line endings and a final line boundary. Markdown carries the envelope as one exact canonical-JSON front-matter line. YAML uses the dependency-free canonical JSON-compatible YAML 1.2 profile with `body` in the same object. One file is at most 5 MiB, one body is at most 4 MiB, one exact tree contains at most 4,096 Items and 32 MiB, and one Item contains at most 4,096 canonical inline Wiki links. These are fail-closed source bounds, not pagination defaults.

One common Item envelope carries title, aliases, attributes, explicit directed relationships, provenance, and body. Definition Items and Claim Items are typed Wiki Items, not peer stores or lifecycle objects. Binary material remains an ordinary Git artifact or policy-bound external material referenced by an Item. An empty Item tree is a valid empty Wiki.

## Durable project continuity

Wiki is the semantic half of version control: stable, human-readable, machine-addressable accepted meaning. It is not a session-summary store. Safe continuation reconstructs intent from Wiki, exact artifacts from Git, decisions and Work facts from Change Trace, and verification from Evidence and Results. Pending effects and live process state require private operational reconciliation, not inferred success or blind replay.

A fresh authorized Agent may need no prior conversation after all necessary task facts are captured. Undecided requests, hypotheses, and alternatives belong in explicit drafts or Change feedback, never automatic accepted-Wiki updates. Arbitrary-midpoint continuity and a fixed number of recent messages are not guarantees. Harness compaction remains useful for temporary execution context without owning durable project meaning.

## Definition Items and Dictionary View

A Definition Item uses `itemType: codewiki.wiki:definition` to govern one reusable meaning or sense. Its title and aliases are lexical labels; body and explicit relationships define meaning. Create one only when terminology is reused, ambiguous, contractual, or important to Agents and Checks. Do not create a Definition for every noun.

Dictionary View is a derived, read-only mapping from terms and aliases to Definition Item IDs over one exact project commit or Proposed Change tip. It may return several senses and must report ambiguity. There is no persisted Term entity, monolithic Dictionary file, separate Wiki Dictionary authority, or identity derived from text.

## Claim Items

A Claim Item uses `itemType: codewiki.wiki:claim` for one independently governed assertion whose subject, predicate, object/value, provenance, valid time, dispute status, or replacement may change independently. Evidence may support or contradict a Claim but never automatically makes it true. Operational events such as `change.completed` belong in Change Trace, not Claim Items. Do not turn ordinary prose sentences into Claims unless independent identity, provenance, querying, or temporal governance matters.

## Links and Views

Canonical Wiki links target stable Item IDs. Inline Markdown uses URL `codewiki://item/<percent-encoded-item-id>` with any display label; ordinary relative links remain navigation. Authored relationships carry typed links. Backlinks, inferred paths, history, attribution, semantic diff, Dictionary, graph, lexical, and vector facilities are Views.

Project Server owns semantic query contracts and authorized execution; pure Kernel mechanisms validate and reduce explicit values, while query services and ports obtain data. Harnesses decide when to query and how to pack returned context, not what canonical queries mean. Required target context follows explicit references and role policy; approximate ranking or truncation cannot silently omit it. Bounded task-context Views are reproducible derived input, not another semantic memory store.

Every View selects one exact project commit or managed Change tip and reports derivation identity, authorization/redaction, coverage, ordering, truncation, freshness, unknowns, citations, and exact versus approximate channels. Private indexes may accelerate queries but carry no identity or authority. Approximate similarity retrieves candidates only; it cannot create truth, links, conflicts, Change type, or Decision. `codewiki.legacy:*` attributes are available only through exact provenance inspection and are excluded from normal term resolution, search ranking, semantic diff, ownership, applicability, authorization, Agent context, and generated Views.

## Agent use

Every CodeWiki-controlled DSH Run binds exact relevant Wiki bytes or handles and role-specific read-only Wiki tools. A small Product-fixed build-bound role instruction, validated as explicit Kernel input and supplied by Project Server, requires stable Item identity, term resolution, explicit unknowns, and no silent contradiction. Decision may propose Wiki changes. Planning maps Work Units to Committed Change targets. Workers read but cannot edit accepted Wiki. Review compares the exact reconciled prospective Completion tree with committed meaning. DSH Run receipts record exact inputs and queries; type-conditioned stage Checks verify outputs rather than trusting a model assertion that it used Wiki.

## Change and accountability

Learning and refinement have no privileged Wiki writer. New governed improvements enter Change Intake; existing Work feedback stays with its owning Change. Proposal capability grants no acceptance authority. Rebuilding a private index or collecting an observation is not itself a new semantic Change; promoting a conclusion into accepted meaning or policy is governed.

A Proposed Change is a full Project snapshot on one managed Change ref. Its Decision-phase delta may add, edit, move, or retire Items and links. Project Server derives that Wiki delta directly from Git trees and validates complete Item/relationship closure. Decision Checks judge the exact proposed tip and a proposed-tip Dictionary View that includes new Definitions and their usages atomically.

An authenticated `commitChange` command creates the Change Commit. Accepted Wiki bytes become canonical Project history and are attributable to the accountable Change committer while retaining every proposal contributor, producing DSH Run, Check Run, and Project Server committer. A true Wiki-only snapshot completes in that commit. A project-realization Change continues while Wiki expresses accepted future intent. Correction or supersession is another Change, never silent overwrite.

Batch admission may create several independent Change refs atomically, but each Change retains its own type, Gate, commit/reject/defer/withdraw outcome, attribution, and completion. Pending alternatives are conflict evidence rather than veto authority.

## Adoption and version boundaries

Normal Wiki authoring uses readable `product/**` and `system/**` paths while stable Item IDs and Git rename lineage preserve identity. Normal operation reads only the current `.codewiki/wiki/**` and `.codewiki/changes/**` roots. A release may advertise an exact one-shot conversion from a specifically supported predecessor, including a differently nested Wiki layout. Conversion preserves stable Item identity, content and relationship semantics, history, and provenance under an exact reviewed path mapping. It validates collisions, active navigation rewrites, complete object closure, and expected refs before mutation. Conversion completes under backup-first recovery before startup and never creates dual authority or silently interprets an unsupported layout through recursive scanning. Unsupported pre-stable roots, compilers, and converters remain in Git and release history rather than active Product readers.
