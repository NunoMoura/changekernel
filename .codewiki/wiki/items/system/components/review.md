# Review

Review is the final stage for a Committed Change that required project realization. True Wiki-only Changes complete in their Change Commit and do not enter Review. Review judges whether one exact integrated full Project snapshot realizes the committed Wiki target without introducing uncommitted meaning.

Review starts only after every current Work Unit has a passing Implementation Gate, integrates onto the managed Change ref, and satisfies dependency closure. The Review subject is the exact Change tip/tree plus its Change Commit, committed Wiki delta or existing-Wiki targets, planning facts, contributing Work Unit commits, Check Results, Evidence, and current canonical Project head. A provider pull request may mirror this lineage but is neither required transport nor authority.

A Review Agent runs through a fresh bounded DSH Run with exact relevant Wiki inputs and read-only tools. Project Server resolves exact Review Check Packs and freezes active Checks from Change type and subject. Checks normally cover complete target realization, cross-unit behavior, full build, integration, provenance, scope, and applicable security/compatibility policy. Human review may enter as authenticated Evidence when active Checks require it.

Review does not reconsider or silently edit Committed Change intent. A Work Unit defect returns to exact affected implementation. A decomposition defect returns to Planning amendment. A meaning or type defect requires a Superseding Change through Decision. Out-of-scope findings enter Change Intake. Every route preserves exact Results and responsibility; no Check or model chooses lifecycle authority.

A failed Gate leaves the Change committed and incomplete. A stopped Gate preserves state and exposes recovery. A passed Gate qualifies only the exact reviewed Change tip. Project Server revalidates the Gate, Change Commit, Work Units, current Change tip, exact reviewed tree, current canonical head, authority, and relevant active-Change conflicts before creating the Change Completion Commit by expected-head CAS.

The Completion Commit joins current canonical Project history to the exact reviewed Change tip, applies the reviewed artifact delta, and appends `change.completed`. Git first-parent history remains canonical Project state; second-parent ancestry preserves complete Change collaboration. Delivery, publication, remote push, and external outcomes are later separately authorized effects and observations, not implicit Review or local completion.
