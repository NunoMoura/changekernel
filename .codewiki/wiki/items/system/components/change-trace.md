# Change Trace

Change is the stable, independently decidable intention that CodeWiki carries from proposal to commitment and, when project realization is required, verified completion. One append-only Change Trace and one managed Git ref are its sole semantic lifecycle representation:

```text
.codewiki/changes/TRACE-CHG-<id>.jsonl
refs/codewiki/changes/<id>
```

Every commit on the managed ref identifies a full governed Project snapshot. Change scopes the semantic delta, authority, and lineage; it does not define a partial repository or duplicate snapshot format. Git trees and blobs store exact Wiki, source, test, and project bytes. Trace records why a snapshot exists, who acted, which exact OIDs were involved, and which lifecycle fact became durable.

The Trace begins with one immutable header and then canonical typed operations in file order. Successor Trace blobs preserve the predecessor as an exact byte prefix. Operations may record proposal/revision, Decision Gate, commitment, rejection, deferral/resumption, withdrawal, Planning, Work Unit and integration facts, Review, completion, and protected effects. Current Change state is deterministically reduced rather than stored as a mutable peer record.

A proposed revision records bounded intent/rationale, Change type classification, realization route, relationships, accountable Actor/authority, producer DSH Run references, exact project base, and optional references to existing accepted Wiki meaning. Proposed Wiki bytes live once in the Git tree. Project Server derives changed Item IDs, facets, paths, and links by comparing exact trees; Trace does not repeat complete Wiki or source bodies, mutable path claims, fuzzy patches, or generated propagation lists.

The Change Commit joins the current project head to the exact managed Change tip: first parent is the current canonical pre-head; second parent is the exact Proposed Change tip. It applies accepted Wiki intent and appends `change.committed` with both parent OIDs, accepted Item/facet targets, frozen classification, Decision Gate, accountable Actor, and the fixed `containing_commit` result marker. Native Git context makes the containing Change Commit the resulting canonical head; the operation never embeds that commit's OID. When the committed full Project snapshot already realizes a true Wiki-only target, the same commit also appends `change.completed` under the same containing-commit rule. Otherwise Planning and implementation continue on the same Change ref while canonical Wiki records the accepted future and Alignment reports the owned realization gap.

Planning facts define Change-owned Work Units and dependencies in Trace. Passing Work Unit result commits integrate onto the Change ref through expected-tip compare-and-swap. Git ancestry is the integration lineage; Trace records exact Work Unit, Check Run/Result/Gate bindings, expected parent and admitted Work result OIDs, custody, conflicts, admission, and the containing-commit marker. The containing integration commit is the resulting managed Change tip. A derived Work View and WorkState expose current graph/readiness without becoming another canonical graph or private integration store.

Review judges one explicitly reconciled Change tip whose project-artifact bytes already include the current canonical Project state. A current passed Review Gate permits Project Server to create the Change Completion Commit: first parent is the unchanged reviewed canonical pre-head; second parent is the exact reviewed Change tip. `change.completed` binds both parent OIDs, all stage Gates, accepted Work integrations, accountable Actor, and the containing-commit marker. The Completion Commit preserves every reviewed project-artifact entry and OID. Its only permitted full-tree difference from the reviewed tip is the mechanically constructed bounded append to that Change's Trace; Kernel validation binds the exact prior Trace, Review Gate, operation bytes, and resulting Trace blob before CAS. Failed or stopped Review preserves accepted intent and routes exact feedback; it does not reject a Committed Change. Changed intent requires a new Superseding Change.

Rejected, deferred, and withdrawn proposals remain reachable through managed Change refs and do not advance canonical Project history. Corrections never rewrite accepted history. Semantic compensation or supersession is another Change; operational Git recovery may restore exact refs only within qualified rollback boundaries.

Trace contains semantic milestones and immutable references, not prompts, reasoning, raw model/tool output, credentials, DSH Session bytes, temporary worktrees, caches, or incidental discussion. Those remain private execution evidence. Views, summaries, indexes, and attribution projections cite exact source commit/path/blob/range and never replace full Trace history.

Digests bind already-complete operation bytes, commits, receipts, or segments. No operation embeds or computes its own digest. No operation stored in a commit embeds that containing commit's OID; it binds exact input OIDs plus the fixed `containing_commit` marker, and native Git context supplies the result OID. An enclosing or successor fact may cite an already-complete operation or commit. Trace identity never depends on cryptographic self-reference or a hash fixed point.

Normal operation accepts only the current Git-snapshot, managed-Change-ref, and append-only Trace protocol closure. Obsolete pre-stable records remain recoverable from Git history, release artifacts, and qualification evidence rather than active Product readers. Unknown or unsupported Trace bytes stop without inference, repair, or dual authority.
