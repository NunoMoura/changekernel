## SC-1 desk probes and reasoning

**Method and limits.** These are synthetic examples with stipulated facts, reviewed by the parent assistant against Wiki. They are neither observations of this package nor executed tests, independent reviews or fresh-Agent continuation trials. Each outcome is conditional on its stated premises; real findings would need attributable interpretations and relevant observations. No Python phrase check is used as evidence of meaning.

### 1. Software: a bad join despite isolated success

- **Given:** adopted knowledge says “Authentication secrets must never enter logs, including diagnostics.” UI work adds `credentialBundle` to login requests; backend work forwards it; observability work logs complete failed-login request bodies. Suppose each worker reports passing isolated tests that never exercise the combined path.
- **Reasoning:** the combined path places credentials in a logged body, contradicting the shared obligation even if files merge cleanly. The counterexample is the data flow, not a missing keyword or a test count. Review cannot accept that join unchanged. Implementation can redact the field; Planning must coordinate the shared boundary and a joined-path check. The candidate cannot authorize its own waiver.
- **Minimal need:** preserve the shared obligation, the relevant producer/consumer relationship and the actual joined subject. A complete automatically inferred dependency graph is not established by this example.

### 2. Non-software: onboarding knowledge is not an outcome

- **Given:** a Change aims to halve onboarding time. Three interviews identify confusing instructions; a proposed guide addresses that confusion. There is no rollout observation or duration measurement. An optional connector may supply interviews, but the same inquiry can use authorized local material.
- **Reasoning:** the interviews can support a scoped claim about those participants and a credible trial, not a population-wide causal result. Review may adopt the guide as the intended procedure, leaving rollout and measured improvement unrealized. A commit alone does not adopt it. Planning needs a trial, responsibility, measurement conditions and privacy limits; Implementation records what happened; Review assesses the original outcome claim.
- **Counterexample:** changing the goal to “publish a guide” after producing one must revisit Decision as an explicit intent revision. It cannot turn the original goal into a realized outcome retrospectively.

### 3–5. Historical reasons: retain, reassess, reconsider

Use the same retained decision throughout: a team chose a managed service because a local alternative lacked a required export feature **and**, independently, the team lacked support capacity. Either reason was sufficient to reject the local option in that recorded context.

| Variant and given current observations | Reasoned outcome |
| --- | --- |
| Both conditions still hold. | The old grounds remain relevant; reuse them rather than inventing a new rationale. This does not prove that no other consequential condition has changed. Infrequent retrieval does not retire the decision. |
| The team gains support capacity; the export feature is still absent. | One ground is defeated; the other independently remains. Reassess affected claims without automatically reversing the conclusion or pretending the original judgment used today's evidence. |
| The local alternative also gains the required feature. | The recorded rejection grounds no longer rule it out. Reopen comparison of costs, migration risks and current goals; this makes the alternative a live option, not automatically the best option or an adopted decision. |

Native Git history must expose the exact old conclusion, grounds, conditions and later disposition. A newly accepted Change can revise the current conclusion while keeping the prior judgment historically attributable. Rerunning a model is not recovery of that original judgment.

### 6. Retirement is an intentional effect, not file housekeeping

- **Given:** an adopted obligation is moved unchanged into `archive/` within the tracked tree, then omitted from an Agent's prompt. No retirement has been accepted.
- **Reasoning:** neither operation retires it. If an authorized Change instead retires that obligation, its exact prior passage and retirement reasons remain discoverable in Git. That retirement need not retire unrelated assertions in the same file. Merely observing that text disappeared cannot fabricate the missing acceptance record.

### 7. Retrieval can inform or challenge without adopting

- **Given:** a query returns a retired rule and three summaries derived from the same source; generated synthesis recommends following the old rule. Its previous acceptance and retirement reasons are available.
- **Reasoning:** historical acceptance is not current endorsement; three derivative summaries are not three independent grounds. Retrieve the retirement context before reconsideration. A new observation may undermine a current assumption or block proposed work, but the generated answer cannot silently replace accepted knowledge. An explicit Change is still needed for re-adoption.

### 8. No connectors, unavailable history, restricted context

- **Given:** there are no external data connectors. Relevant material is in retained local Git history. In variants, the referenced object is unavailable, or the current actor lacks access to a source used by an earlier judgment.
- **Reasoning:** the native-history case must work without a connector. The other variants require an honest access/availability limit, not invented reconstruction or disclosure under obsolete permissions. An authorized reviewer may supply suitably scoped assurance; otherwise required unresolved assurance blocks acceptance. A context rank or an inaccessible source is not evidence that an obligation is irrelevant. Do not leak private contents or existence details while explaining the limit.

### 9. Existing repositories and mixed passage roles

- **Given:** a tracked `README.md` states an operating commitment, quotes a vendor's incompatible claim, and includes a proposed exception. Notes record an abandoned alternative. There are no CodeWiki envelopes, document IDs or historical CodeWiki adoption records.
- **Reasoning:** all are discoverable material; they do not acquire equal governing force. Interpreting the commitment, quotation, proposal and historical account is a contextual judgment, not an extension/path test. An authorized initial Change can accept an explicit current interpretation and declared assurance now. It cannot invent past acceptance, treat every sentence as policy, or let the proposed exception authorize its own adoption. Ambiguous consequential roles remain unresolved.

### 10. Exact subjects, intent amendments and interrupted review

- **Given:** work and an assessment refer to intent revision 1 and candidate A. Intent is materially amended to revision 2; the work is also rebased or joined with another candidate. A reviewer loses its response after an attempted acceptance write.
- **Reasoning:** preserve the old assessment as history, not approval of the new intent/subject. Assess the actual candidate and affected authority again; valid old observations may be reused only with an explicit account of applicability. Reconcile the possibly completed write before retrying an effect. A record cannot solve this by asserting its own enclosing commit hash, and a cache cannot reconstruct a lost original judgment.
- **Unclosed protocol issue:** assessment artifacts, acceptance records and resulting Git commits need an explicit subject-closure and write-ordering design before SC-4. This round identifies that requirement; it does not claim to have implemented or qualified it.

### Comparison: good prose/Git versus minimal structure

Use the **same facts and reasons** on both sides. Well-written Markdown can already explain every case above; Git can already preserve its exact versions. This desk exercise supplies no measured quality or effort advantage over that baseline.

A small machine-readable association is justified where it enables a concrete safeguard: binding an assessment to an exact intent/candidate, locating a passage, linking a retirement to its grounds, tracking a shared obligation across work, or exposing a missing required result. The reasons remain readable prose. Source identity, role, disposition and support must not collapse into one `accepted` or `confidence` flag. These are Change-associated records and derived views, not additional authoring primitives.

Incorrectly extracted relationships can still produce incorrect findings. Deterministic checks can reject malformed/stale bindings or enforce declared transition rules; they do not establish that the interpretation is faithful, complete or true. Independent semantic cases, fresh-context trials and measured effort remain future evidence. Do not expand this into compulsory metadata for every paragraph, a universal score, a Check Pack, an archive database or a mandatory vector index.

Each descriptor names `path`, `mode` and `oid`; eligible Markdown additionally requires `bytes`. Non-Markdown descriptors do not need content loading. Git OID syntax and one object format per snapshot are checked, not object type, custody, tracking, authorization or hash-to-byte authenticity.
- Material records contain frozen identity metadata, exact decoded `text` and `byteLength`, not a caller-owned byte view. Strict UTF-8 decoding preserves BOM, CRLF, non-NFC text and all other valid UTF-8 data; re-encoding must recover the exact admitted bytes. Inputs and results cannot alter one another through a shared returned buffer. Shared backing buffers, detached views and out-of-bounds views are rejected. A native counterexample showed that a detached view could otherwise decode as an empty document; the guard and regression test now distinguish it from legitimate empty content.
- Descriptors are passive caller-supplied data, not a JavaScript sandbox. Required fields and optional bytes must be own data properties; accessors are rejected without invocation. Extra caller metadata is not interpreted or copied into results. Paths use `/` separators; reject backslashes, drive prefixes, absolute paths, empty/dot/traversal segments, NUL and unpaired surrogates without rewriting them. Case and Unicode spelling otherwise remain exact. A segment trie rejects file/descendant collisions in either order, including collisions involving excluded symlinks or gitlinks, without quadratic prefix-string construction.
- Preflight entry/path/document/byte budgets before decoding any content. Each result list preserves its relative descriptor order; non-Markdown exclusions are reported separately. Failure returns one typed issue, never a partial success. Eligible files claiming the same OID must contain identical text/bytes; this consistency check still does not authenticate that OID.
