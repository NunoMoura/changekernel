# Consumed Deterministic Assessment Profile

**Historical v3 contract; executable semantic host retired.** Start with the [current referenced-intent prototype](referenced-intent-prototype.md) and [SDK/Pi boundary](sdk.md). This page preserves its consumed schemas, authority, custody, retry and accounting meanings and existing anchors. This is the selected bounded successor contract for one deterministic assessment consumer on a trusted Linux host. It specializes [typed Checks](checks.md#typed-check-requests), [Trace custody](state.md#file-first-change-trace-custody), [history/context access](state.md#structured-history-access-and-context-projections) and [typed operations](../../product/changekernel.md#typed-requests-operations-and-records). The [consumed opening profile](state.md#consumed-opening-profile) and [consumed intent-revision profile](intent-trace.md) remain unchanged. The authenticated owner must still opt into the fixed policy for each new fixture custody. Source-development selection of this contract does not activate policy or a controller in this checkout. General user-defined Check requirements, adoption and evaluation runtimes remain separate capabilities; custom policy belongs in adopted Checks, not a separate user Kernel governor. ## One question, not a semantic intent judge

Selected fixed definition `notice-what@1`: **Does the exact adopted What fit an 80-byte raw UTF-8 notice payload without truncation?** Passing condition: `what.as_bytes().len() <= 80`. The input is the complete exact What from one accepted intent record. No normalization, trimming, escaping, summary, Why, JSON framing or terminator contributes to this raw-payload count. Ingress still requires nonblank What of at most 65,536 bytes. Therefore both pass and nonpass are valid admitted inputs; the criterion is not an admission tautology.

Use: a deterministic client deciding whether it can present that exact What in its fixture's small raw-text notice channel. The channel capacity is a selected opt-in fixture policy, not a claimed native application observation. No notice is sent. A negative answer suggests shortening What through an explicit owner-directed revision, or choosing another channel later; it never rewrites text automatically. This is more narrowly useful than an alleged assessment of intent completeness: it supplies exact lossless-presentation eligibility, not whether the goal is good, aligned, feasible or fulfilled. Why may remain null, empty or arbitrarily supplied within the existing bound; no general or fixture Why requirement is added.

Definition identity `notice-what@1`, policy identity `fixture-notice@1`, evaluator identity `utf8-length@1` designate the immutable specifications in this contract, including the threshold 80, raw-text interpretation, result construction and limits. `utf8-length@1` is a trusted built-in Rust calculation, not a callback, subprocess, registry, downloadable artifact or caller-selected evaluator. Replacement semantics require new identities/profile assignment, not reuse of these names. Exact source/artifact revision must accompany future implementation evidence; a version label alone does not authenticate deployed bytes.

The authenticated fixture owner `owner-1` must explicitly select this policy in the trusted host's independent first-use grant. The new anchor durably retains this adoption, and reconnect requires the same independently supplied selection. The assessment request runs an already selected Check; it neither adopts the definition nor changes policy. This grant is a fixture adoption boundary, not a general policy-adoption API. This contract selects the optional notice-fit question for a bounded source fixture; each newly provisioned custody still requires the authenticated owner's independent explicit selection. It does not impose a policy on this source repository, decide the worth of a genuine user goal, or create a universal intent-length requirement.

## Closed consumed shapes

All request fields are required; only request Why and read `at` are nullable. Record/control nullability remains exactly as separately declared, including origin `prev:null`, checkpoint `sha256:null` at zero, nullable `pending`, and embedded request Why/at. Existing byte/text/identifier/reference bounds and canonical encoding apply, including terminal LF, lowercase control escapes and exact typed comparison. References retain the origin/op grammar and sequences 1–128; their type is checked through accepted history, not spelling. The only new bound is the fixture's assessment criterion, not a request-admission text bound.

Public dispatchers: `open_change`, `revise_intent`, `inspect_intent`, `assess_intent`, `inspect_assessment`. Opening consumes the unchanged v1 seven-field request and emits the unchanged v1 origin/result. New revision/read requests use v3, so the old v2 contract is not silently changed:


`expected_intent` binds the exact adopted subject. New assessments require it to equal current intent at acceptance; assessment of a superseded intent is not a new supported run. Read `at:null` selects current intent for intent reads; for assessment reads it selects the latest accepted assessment of current intent. Nonnull assessment `at` selects an exact accepted assessment operation, including a stale one. No current assessment yields unavailable, not a false answer or an automatic run. Reference to an existing record of the wrong kind is unavailable. Opening/revision keys and assessment keys share one namespace across every operation and actor.

Revision result/record use the profile-2 member order and fields, with `v:3` in request, result and record. Revision `prev` is the last operation; `previous_intent` and input `expected_intent` are the last adopted intent, which can be earlier. Result/intent identity is the new operation reference. New assessment uses this exact ordered result schema:

```json
{"v":3,"kind":"intent_assessed","workspace_id":"workspace-1","change":"change-1","key":"assess-1","actor":"owner-1","result":"change-1:op:2","seq":2,"intent":"change-1:origin","policy":"fixture-notice@1","check":"notice-what@1","evaluator":"utf8-length@1","passed":false,"feedback":"shorten_or_use_other_channel","evidence":{"intent":"change-1:origin","field":"what","utf8_bytes":81,"limit":80}}
```

`passed` is a JSON Boolean, count/limit unsigned integers, feedback exactly `fits` for true and `shorten_or_use_other_channel` for false. All result/evidence members are required, nonnullable. `result` is the assessment operation identity, not a new intent. The record envelope is exactly `v,custody,workspace_id,binding,change,seq,prev,kind,input,result` in that order, with `v:3`, `kind:intent_assessed`, `prev` the immediately previous operation, input the complete assessment request, result as above. No timestamp, confidence, native receipt, effect grant or caller-supplied evidence is invented. The accepted earlier intent record supplies exact retained text/provenance; evidence count describes that field, not all Change context. The record and anchor retain definition/evaluator/adoption provenance. Referenced intent must remain retained and currently disclosable under the all-or-nothing owner guard.

The completed evaluator is total for valid supported inputs: a bounded UTF-8 byte length and integer comparison cannot yield semantic ambiguity, timeout, cancellation, malformed evaluator output or missing external evidence. No injectable evaluator experiment is added to pretend those capabilities exist. Missing/damaged intent, wrong/missing adoption, unavailable authority or failed storage are operational unavailability, never Boolean results. Unsupported Check selection is unsupported on a genuinely new otherwise authorized request. A process cut may recompute this pure deterministic result for its exact reserved input; it cannot resample a judgment. Accepted retry never reevaluates to replace its retained result. During prefix integrity validation, checking retained count/Boolean against exact historical inputs is validation, not a new accepted run.

### Duplicate-aware closed union and error order

Use one bounded typed MapAccess union with slots for `v,op,workspace_id,change,key,expected_intent,what,why,at,check`. Required-null presence is separate from value. Opening and the private legacy v1 inspection retain their exact recognized shapes. Privately recognize the exact old v2 revision/intent-read shapes only to reject them as unsupported on this host. New v3 shapes are exactly those above. `check` is nonempty ASCII `[A-Za-z0-9_@-]{1,64}`; unknown well-formed identities can be rejected without guessing a definition. Missing fields, wrong types, unknown/duplicate fields, forbidden extras, arrays, arbitrary nesting, invalid bounds/reference grammar, trailing input and unknown op/version pair all produce invalid_input. Decide pair/field mask at map end; never return early on an op/version field. The union has no actor, policy, evaluator, passed, feedback, evidence or result input slots.

Ordered boundaries:

1. Bound/decode/end-check all bytes; any shape/unknown-pair failure is invalid_input independent of member order. A fully valid recognized variant on the wrong dispatcher, or private legacy inspection/v2 variant anywhere on the new host, is unsupported before authorization/private lookup.
2. Matching dispatcher: policy unavailable → unavailable; deny/wrong principal/wrong Workspace/Change → denied. Check a grammar-valid embedded reference's Change association next; foreign Change → denied before private lookup. Malformed reference already failed step 1.
3. Validate profile grant/anchor/physical custody, inventory/incident, entire installed prefix and pending feasibility, then proven temporary cleanup/revalidation. Any damage, wrong profile, impossible pending or uncertainty → unavailable, preserved evidence, no private response. Connection is independently guarded and may fail before client dispatch.
4. Accepted key lookup precedes all new-subject/check/capacity tests. Same exact typed original input returns its retained result after delivery barriers/current disclosure, even after later revisions/assessments, at capacity, or with feasible pending/bounded unexplained suffix. Changed kind, Check, expected intent or any original field → conflict. No result is reassigned to the current caller.
5. Pending key: same key changed typed input/kind → conflict; exact pending input alone can complete. Any other new key while pending → unavailable. Old reads/retries may disclose accepted history only if the installed pending is feasible.
6. New request: unused non-original opening key → unsupported. Revision/assessment with no origin → unavailable; expected intent different from current, including an assessment operation reference → conflict. A new unknown Check then → unsupported. A read of absent/wrong-kind `at`, or no current assessment → unavailable. A bounded suffix without pending blocks new mutation as unavailable.
7. Count/byte capacity crossing → unsupported before reservation; equality allowed. No new identity bypasses earlier damage or pending refusal.
8. Final guard/delivery cut failure → denied/unavailable error only; discard private response. A committed result stays committed, recoverable by later authorized exact retry. Errors use the unchanged v1 error envelope; they are not lifecycle records or proof of nonacceptance.

## Streaming validity, applicability and purpose-specific reads

During a sequential pass, maintain `tip`, `current_intent`, current What byte count and at most 128 bounded global keys. Origin sets current intent/count. Revision must name that current intent and changes both; its `prev` names the immediately prior operation. Assessment must name current intent at its historical record position, leaves current intent unchanged, and reconstructs policy/evaluator/count/limit/Boolean/feedback from the fixed definition and running count. This resolves validation against an earlier record with no hidden prefix rescans and no retention of every intent's prose. Retain only selected/key-matched records needed for response. A complete current intent record need be retained only for an intent query; its bounded offset can alternatively select/decode one line from the already read immutable buffer, with that extra decode/re-emission counted explicitly. No raw record bytes become an executable evaluator.

For `inspect_intent.at:null`, track the most recent origin/revision, not last sequence. For nonnull, select only the named origin/revision. Assessment queries retain the latest matching assessment since the latest revision, clearing that selection on revision; explicit historical selection remains unchanged. All records, including ones not returned, must validate. Current intent is computed transiently, never inferred from checkpoint generation.

Intent inspection follows the profile-2 envelope/member order with `v:3`, `projection:ck-assessment-intent-view@1`, `purpose:intent`. `tip` is latest operation; `current_intent` is latest adopted intent; `selected_intent` and complete selected record identify the cursor. Coverage has first/last/hash/selected/returned/complete as before. A query does not mutate, finish pending, evaluate or append.

Assessment inspection is exactly:

```text
{"v":3,"kind":"assessment_inspection","workspace_id":"workspace-1","change":"change-1","projection":"ck-assessment-view@1","purpose":"notice_payload","origin":"change-1:origin","tip":<operation ref>,"current_intent":<intent ref>,"selected_assessment":<assessment ref>,"applicability":<"current" or "historical">,"record":<complete assessment record>,"coverage":{"first":1,"last":<count>,"sha256":<64 lowercase hex>,"selected":<assessment seq>,"returned":1,"complete":true},"progress":<readiness>}
```

Every direct envelope/coverage member is required nonnullable. `applicability:current` means result.intent equals current_intent and the fixed adopted policy/check/evaluator match; it is not permission, proof of alignment or notice delivery. Historical false/true results keep their original meaning; revision makes older results historical even if text happens to be identical. At-null chooses the latest applicable result, not an implicit pass aggregation or mandatory gate. Multiple runs on the same current intent remain separately attributable even with identical results. The exact selected prefix is identified by count/digest under pinned custody, not file end. Coverage means all accepted records validated and one returned; it is not native State coverage or inclusion of all inputs. Exact What can be retrieved via inspect_intent at result.intent. Progress is `blocked_pending` before `blocked_unaccepted_tail`, otherwise `ready`; this is custody readiness, not effect readiness. Generation zero is unavailable.

## Pending, temporaries, acceptance and counterexamples

Retain limits: request/record/result/control 1,048,576 bytes including emitted LF; query 2,097,152; accepted count 128; accepted bytes 16,777,216; total trace including suffix 17,825,792. Fixed-schema output is bounded without truncation. The metadata-only assessment is small, but opening/revision still exercise large text/byte capacity. Existing accepted bytes are never rewritten.

Installed pending feasibility is independently checked before any private result/read, temporary cleanup or append:

1. Fully valid mutation input, pinned actor/subjects, selected Check if assessment, key absent from every accepted operation. No read or old-v2 variant in pending.
2. Count <128. Opening requires zero/end zero/hash null/key open-1. Revision/assessment requires origin and expected_intent equal to the validated current intent, not necessarily logical(count). Definition/adoption/evaluator match independently pinned profile.
3. Reconstruct exact next record at count+1 from operation tip, current intent/count and retained input/actor. For assessment, construct its deterministic completed result; no result is accepted from pending input. Canonical L is positive and <=1,048,576; checked end+L <=16,777,216.
4. Physical suffix is empty or an exact byte prefix of this single canonical record, up to complete length. Never compare only a hash or parseability. Impossible count/byte/key/actor/subject/predecessor/definition or mismatching/extra suffix is damage even if suffix is empty or a complete-looking candidate.

Producer admission must use the same predicate; installed validity is not inferred from producer refusal. Example after the four records: count 4, tip op:4, current intent op:3; pending `{"input":{"v":3,"op":"assess_intent","workspace_id":"workspace-1","change":"change-1","key":"assess-3","expected_intent":"change-1:op:3","check":"notice-what@1"},"actor":"owner-1"}` is feasible if capacity permits. Its next record is seq 5/prev op:4/intent op:3. Changing expected_intent to op:4 makes installed pending impossible, not an authorized historical retry; all private reads/old retries refuse and preserve controls/tail/temp. Pending rev-2 can likewise name op:3 while prev is op:4. Current operation and intent roles cannot be collapsed.

Protocol: authorize → full validation/global key resolution → feasible new reservation (or exact pending retry) → durable checkpoint pending replacement → reconstruct/compare canonical next record → append only missing suffix bytes → synchronize trace → synchronize checkpoint temporary → rename → synchronize directory → fresh installed full-prefix validation → delivery barriers and fresh revalidation → final guard/delivery cut → retained response. A pure result computation before append is not a completed accepted operation. Fresh reopen never completes a run by itself. Only exact authorized pending retry completes deterministic bytes; it may recompute this fixed pure result. Lost response after acceptance is resolved by accepted key lookup.

Checkpoint temporaries permit unlink plus parent synchronization, never promotion, only after installed full-prefix/pending validation:

- Canonical equality with independently valid installed control.
- Feasible reservation successor with unchanged count/end/hash, installed pending null, physical trace exactly accepted end.
- Exact accepted successor of feasible installed pending with the complete deterministic suffix, count+1/end+L/full-prefix hash/pending null checked. Prove from already validated prefix and exact extension using current-pass hash state; no second full walk hidden in this proof.

Revalidate after cleanup. Invalid installed pending defeats every relationship including equality; partial, unrelated, backward, noncanonical or capacity-crossing temporary refuses and remains. Preparing/installed anchor temporary proof remains restricted to complete deterministic zero-history initial inventory, including new grant fields; history/pending forbids its cleanup. Any incident temporary, including clear, blocks and is never housekeeping.

## Complete-call work and buffer contract

These are implementation budgets to verify, not measurements. Connect is separate from API calls. A call resets and snapshots attempts/completions including failures, incident-retention work, error emissions and discarded private replies as the accepted `IntentWork` seam does. No cached validation substitutes for fresh custody validation.

Let C=1,048,576, Q=2,097,152, T=17,825,792, A=16,777,216. P is the number of full-prefix validation passes **entered**, including a pass that refuses before reaching records. For each pass j, n_j is its checkpoint count after header/capacity checks permit record iteration (zero if those checks were not reached/satisfied); 0<=n_j<=128. N=max(n_j) over the entire call, or zero if there are none. It is not merely the preflight count. A successfully completed mutation from N0 has later passes at N0+1, hence N=N0+1<=128; a nonmutating valid call has N=N0. A failed call uses only actually entered pass counts, even if the persistent checkpoint changed before the failure. Damage may stop a pass before n_j records; count only actually reached attempts. Declared count 129 does not permit 129 record decodes or comparisons. Ordinary query/accepted retry uses P=2; new mutation/exact pending completion P=3. One justified checkpoint cleanup adds one pass; maximum P=4. Connected reopen uses two passes, at most three with cleanup; fresh/resume separately includes bounded initial inventory/anchor work. Absent-temporary synchronization is not an extra prefix pass.

Let R<=P be any optional selected-line re-decode/re-emission/semantic check from the already read immutable buffer. It is separately counted, never a new prefix walk. It may be zero with retained selection, and verification-only passes need no selection. Define D=1+P*N+R+4*P+2 as a conservative number of bounded request/record/control decode attempts, and K=P*N+R+2*P+4 as a conservative number of semantic/next-record constructions. These are ceilings, not identities derived from completed codecs.

### Reads, hashing, codecs and evaluation

- Trace bytes read <=P*T; accepted-prefix hashing <=P*A; successor hashing at most 2*C (constructing successor and proving an abandoned accepted-successor temporary). No suffix is hashed as accepted except a proved successor extension or fresh selected-prefix pass.
- Record decoding/canonical re-emission <=P*N+R. Semantic reconstruction <=P*N+R plus conservatively 2*P+4 pending/temp/producer constructions. Count failed attempts and reached completions separately. Reconstruction/emission does **not** count a later equality operation.
- Per pass canonical control reads at most four C-bounded objects (anchor, incident, checkpoint, optional checkpoint temporary; an incident temporary causes immediate refusal instead of continuing). Add at most two control reads outside passes for installed reservation verification and incident retention. Control-read ceiling `(4*P+2)*C` includes failed reads' appended bytes. Constructed controls include reservation/acceptance and at most one blocked-incident attempt. Control re-emissions remain separate. Metadata, barriers and writes are not buffered-read/disk-traffic quantities.
- Ingress once <=C and one request decode attempt; success result/query emission once <=C/Q. Final denial can discard that private emission and emit one error; account both. Malformed/no-custody requests remain in scope. Inventory visits at most six known entries plus the first unknown/refused entry; stop immediately at an unknown name/type. No new unbounded scan.
- Evaluation uses already decoded What's byte length, not another prefix read. Validation reconstructs every historical assessment from its historical running subject/count. Count evaluator runs and retained semantic validations separately, including unsuccessful validation; neither is an accepted assessment by itself.

### Comparison observations: categories and actual boundaries

A comparison **attempt** is entry to an explicit logical equality/prefix predicate or selector boundary; **completion** is return of its Boolean/selected-arm/no-match result, including false/no-match. Publish true/false (or match/no-match) outcomes separately. Short-circuited branches create no attempt. An opaque derived struct equality counts one outer attempt, not imagined attempts for every member; its internal short circuit is unknown. Process death can leave an attempted boundary without an observable completion. Normal false results still complete. Decode/emit success, bytes read and successful reconstruction never imply an equality attempt or success.

Publish conservative **one-sided operand charges**, separately from attempts/completions and existing read/hash/codec counters. For byte equality use max(left length,right length); for typed equality use max(sum of each operand's string/byte payload lengths), with scalar/tag/Option work separately charged a fixed schema-word ceiling. Those sums use existing string `.len()`/fixed fields, not reserialization or scanning prose. A schema word is an eight-byte accounting unit for one scalar/tag/length observation, not a machine instruction, struct-layout or actual-memory-read claim. For valid bounded retained objects the decoded payload is <=C; mixed reconstructed objects conservatively <=2*C. Whole-object charge covers all potentially visited string members once even if equality returns at the first field. For a literal or fixed-bounded trusted-expected-string comparison, charge the expected range and scalar length comparison, not an unbounded guard principal or malformed retained path. The expected principal literal is seven bytes; a connected slot directory is <=4,096 bytes. This is a one-sided expected-operand accounting convention, not a measurement or assertion of Rust's emitted scan/optimization. For prefix proofs charge the compared prefix range only after the length guard, at most C; an overlong suffix returns false with scalar-length work and zero payload-prefix range. A charge is an upper range of operands available to a logical predicate, **not** measured `memcmp`, actually scanned bytes, CPU instructions/loads, cache/disk traffic, or proof that all charged bytes were touched. Do not label it “comparison bytes scanned.” No instrumented libc interception or inner Rust equality trace is required.

### Simultaneous allocation/lifetime contract

Retained preflight trace may coexist with a fresh validation or failed read buffer; count allocation capacities, not only successful-read lengths. This does **not** permit one such key/selection allowance per simultaneous pass.

Required small lifetime strategy for the new profile:

- A query preflight retains only its requested selected record; a mutation preflight retains only a matched-key record if needed, not a default tip selection. Drop unneeded selections. Verification-only post-checkpoint/delivery passes retain no selected/matched record; optional offset re-decode must consume/replace the existing selection slot, not keep another selection alive.
- Drop/deallocate preflight's key vector before any fresh pass. For a read/accepted retry this is after validated selection/key resolution; for a new mutation after reservation feasibility/installed reservation verification; for an exact pending completion after preflight feasibility/input matching. No later stage needs those old keys: fresh passes own their independent bounded key vector. `clear()` alone does not release its allocation and is insufficient. Failed branches do not enter another key-owning pass. Cleanup recursion already drops its prior validation value before re-reading.
- Release unused preflight `next` bytes and transient feasibility/temporary buffers before fresh validation. Hold at most the old trace, the producer's next record/bytes and the one reply/selection as actually needed. Hash/prefix metadata suffices for successor construction; do not preserve a second prose history or reconstructed-record collection. Local temporaries and failed read buffers still belong to peak observations.
