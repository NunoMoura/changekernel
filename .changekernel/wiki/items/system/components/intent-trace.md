# Consumed Intent-Revision Profile

**Historical v2 contract; executable semantic host retired.** Start with the [current referenced-intent prototype](referenced-intent-prototype.md) and [SDK/Pi boundary](sdk.md). This page preserves its consumed schemas, authority, custody, retry and accounting meanings and existing anchors. Implementation-era status, reuse instructions and old-API/test preservation statements below are historical, not an active assignment or perpetual support promise; see the [support disposition and exact source checkpoint](native-profiles.md#historical-compatibility-reference). No old-custody operation or current semantic change is authorized.

This is the selected bounded successor contract for repeated intent revisions and useful current/historical inspection on one trusted Linux host. It specializes [Trace custody](state.md#file-first-change-trace-custody), [history/context access](state.md#structured-history-access-and-context-projections) and [intent refinement](../../product/changekernel.md#intent-capture-and-refinement). Its producer, consumer and storage must be implemented and tested together. Selection of this contract is not source acceptance, release qualification, activation or controller handoff.

The [consumed opening profile](state.md#consumed-opening-profile), referenced here as R21/profile 1, remains unchanged. The fixture retains its independently authenticated owner, fixed Workspace/binding, cooperative exclusive writer, custody protections and declared failure limits. The [retained native profiles](native-profiles.md) remain separate compatibility contracts. This profile advances only part of [Phase 1](../../product/plan.md#phase-1--a-durable-inspectable-change-without-effects); it does not freeze general ledger, workflow, archive or transfer formats.

## Explicit, fresh-only intent profile 2

Use one fresh-provisioned `ck-intent@2` profile, using the same single Trace, permanent writer lock, anchor/checkpoint/incident roles and trusted-owner fixture. It accepts the unchanged version-1 opening request/origin/result as its origin, then version-2 complete intent replacements, plus a version-2 read of one selected intent. It supports up to 128 accepted records, subject also to a 16 MiB accepted-byte limit. This is a repeatable bounded history, not a hardcoded origin-plus-one-revision demonstration.

Select profile 2 explicitly in trusted host composition before provisioning. Use new anchor/checkpoint/incident format tags, not generation 2 in an opening-profile checkpoint. Leave `OpeningHost` and its profile-1 APIs/controls/limits unchanged. A separate `IntentHost` owns the profile-2 dispatchers; it is a library fixture consumer, not a launcher or controller. Share concrete storage primitives rather than clone a persistence engine. The new host's `open_change` deliberately consumes the old opening schema and exact result, while the host selection establishes the new custody interpretation independently of JSON.

**Adoption is only for newly authorized unused slots.** Profile-2 fresh provision refuses an existing anchor/directory/controls. Profile-2 reopen/resume refuses profile-1 custody. Existing R21 slots remain profile 1 and retain their original retry/inspection service. There is no automatic or manual in-place upgrade in this slice, no copying accepted R21 records into another continuing Change, no dual-writing, and no reinterpretation of legacy SQLite custody. Continuing an already provisioned R21 Change through revision is outside this profile: an explicit upgrade protocol needs a separate approved contract before implementation. A new fixture may independently use the fixed fixture identifiers in its isolated installation; that is not enrollment of a copy of old custody.

Old opening readers/writers refuse profile-2 anchors/controls even at generation 0 or 1. Existing code rejects unknown format tags and cannot consume a longer prefix. It must not be taught to ignore the new tags. Wrong/missing/damaged retained profile controls produce unavailable at connection, with no automatic profile fallback. Version-1 inspection is not served on profile 2: its exact legacy shape is recognized privately only so that all new-host dispatchers reject a shape-valid legacy inspection as unsupported. Malformed legacy inspections are invalid_input first. Do not add a public always-refusing inspect_change method. Unchanged R21 tests must still exercise profile 1.

Excluded: Stage, mandatory Decision/Planning, semantic evaluation of every revision, Check execution, models, source observation, native effects, policy adoption, multi-user transfer, ledger collection, archive, generic registry, index/snapshot and arbitrary append.

## Wire schemas and identities

### Closed requests

Profile-2 opening consumes exactly the existing seven-field version-1 request, with original key `open-1`. New requests, in canonical output field order:

```json
{"v":2,"op":"revise_intent","workspace_id":"workspace-1","change":"change-1","key":"rev-1","expected_intent":"change-1:origin","what":"Keep settings cleanup scoped to local defaults","why":null}
{"v":2,"op":"inspect_intent","workspace_id":"workspace-1","change":"change-1","at":null}
{"v":2,"op":"inspect_intent","workspace_id":"workspace-1","change":"change-1","at":"change-1:op:2"}
```

Every field shown is required. `why` and `at` are the only nullable request fields. Missing Why is invalid; null and empty Why differ. `expected_intent` cannot be null. The revision is a complete What/Why replacement, not a patch: null explicitly means no supplied Why at this revision and never inherits an old Why. Original and intervening values remain intact. Repeating identical text with a fresh key/current predecessor is allowed as a new attributable adoption; the backend performs no semantic deduplication or quality assessment.

Unknown/duplicate fields, including repeated nulls, arrays, arbitrary nested values, caller actor/approval/result and trailing non-whitespace input are invalid_input. Versions are exact unsigned integers; no float/string coercion. Unknown op, unsupported version or unsupported op/version pair are also invalid_input, regardless of field order or additional shape errors. At the ingress/dispatcher boundary, unsupported is reserved for a fully shape-valid recognized request on the wrong dispatcher. Version selection must not fall back to another parser. Use the single closed-union typed visitor described below; required-null presence is separate from its inner value. Requests are at most 1,048,576 bytes before decoding. What is nonblank exact UTF-8, 1–65,536 bytes; Why is null or exact UTF-8, 0–65,536 bytes. No trim, case-fold, Unicode normalization or newline conversion is applied to retained text. Existing opaque identifiers remain ASCII `[A-Za-z0-9_-]{1,64}`.

Logical reference grammar is distinct from opaque identifiers: `<change>:origin` selects sequence 1; `<change>:op:<N>` selects canonical decimal sequence N, 2–128, with no leading zero, sign or whitespace. Maximum logical reference length is 71 bytes. These references are scoped to the independently established Change/custody; they are not globally unique authority tokens. Sequence is logical accepted order, never a byte offset. Byte `end` stays private acceptance control. There is no stable offset API.

For this intent-only profile each accepted operation creates one complete intent: origin's operation/result/intent reference is the existing `change-1:origin`; revision N's operation/result/intent reference is `change-1:op:N`. The roles are distinct even though their values coincide here. No universal rule says future operations must create an intent or share its identity. No separate random identity allocation is needed for retry.

### Retained success and revision record

The opening result and origin bytes remain exactly R21's version-1 encoding, including required `prev:null`, result identity and LF. Profile-2 revision result:

```json
{"v":2,"kind":"intent_revised","workspace_id":"workspace-1","change":"change-1","key":"rev-1","actor":"owner-1","result":"change-1:op:2","seq":2,"intent":"change-1:op:2","previous_intent":"change-1:origin"}
```

The corresponding record is:

```json
{"v":2,"custody":"custody-1","workspace_id":"workspace-1","binding":"fixture@1","change":"change-1","seq":2,"prev":"change-1:origin","kind":"intent_revised","input":{"v":2,"op":"revise_intent","workspace_id":"workspace-1","change":"change-1","key":"rev-1","expected_intent":"change-1:origin","what":"Keep settings cleanup scoped to local defaults","why":null},"result":{"v":2,"kind":"intent_revised","workspace_id":"workspace-1","change":"change-1","key":"rev-1","actor":"owner-1","result":"change-1:op:2","seq":2,"intent":"change-1:op:2","previous_intent":"change-1:origin"}}
```

For N > 2, `prev` and `previous_intent` equal `<change>:op:<N-1>`. `prev` means the immediately preceding accepted operation; `expected_intent`/`previous_intent` mean the previous adopted intent. They agree in this closed profile, not by a universal workflow assumption. All direct revision-record envelope and direct result members are required and nonnullable. Embedded input retains its request schema: input.why is required but nullable; missing, null and empty string remain distinct. Accepted input is the complete typed request. Attribution comes from the independently authorized trusted host principal, passed privately into construction/reservation, not client JSON. Only `owner-1` is supported; retaining its value still records provenance rather than inheriting caller authorship on delivery.

Records/results are each at most 1,048,576 bytes. Use R21 deterministic member order, exact UTF-8, lowercase `\u00xx` controls, quote/backslash escaping, unescaped solidus, unsigned decimal integers and exactly one terminal LF. Retained objects must equal typed re-emission. SHA-256 covers the complete concatenated accepted prefix including every LF, not only the last record. During validation, reconstruct each result/reference from its accepted request, sequence, predecessor and retained trusted actor; matching a digest alone does not validate its semantics. No record supplied by a caller is a mutation interface.

Failures use the unchanged version-1 error envelope/codes and are not accepted lifecycle results. Stale predecessor or conflicting accepted/pending key is conflict. Exhausted capacity or an unused non-original opening key is unsupported only after valid authorized custody and key resolution. A syntactically valid same-Change `at` reference not in the accepted prefix is unavailable, never a fabricated record. A reference with another Change is denied after host/subject authorization but before private lookup; a malformed reference is invalid_input. Damaged retained controls/history, impossible installed pending and storage uncertainty are unavailable, not invalid caller input or proof of nonacceptance.

### Closed-union decoding and error precedence

IntentHost exposes only open_change, revise_intent and inspect_intent. All three use one bounded duplicate-aware typed decode over four explicitly recognized request shapes: `(1,open_change)` with exactly v/op/workspace_id/change/key/what/why; `(1,inspect_change)` with exactly v/op/workspace_id/change; `(2,revise_intent)` with exactly v/op/workspace_id/change/key/expected_intent/what/why; and `(2,inspect_intent)` with exactly v/op/workspace_id/change/at. The legacy inspection variant is private rejection vocabulary, not a new public method. Successful opening/origin/result bytes are unchanged. New-host decoding recognizes more shapes than OpeningHost, whose existing Request visitor, error behavior and tests remain unchanged.

Use one manually implemented MapAccess visitor with a fixed seen-bit set and typed presence slots for the union's nine possible fields. Strings, unsigned v and nullable-string why/at have fixed types independent of discriminants. Reject duplicate or unknown fields immediately as invalid_input; parse known fields into typed slots without returning early unsupported upon seeing v/op. At map end, require v/op, select only one recognized pair, then verify that pair's exact field-set/presence mask, field types, text/identifier bounds and reference grammar. An unrecognized pair is invalid_input, not a claim to validate an unknown schema. Finish the bounded UTF-8/JSON decode with Deserializer::end() before dispatch. No arbitrary map/Value, untagged retry parser, reparse fallback or order-dependent discriminant response. Domain association of a grammar-valid embedded reference is checked separately after authorization, not during grammar validation.

| Boundary, evaluated in this order | Result |
| --- | --- |
| Request byte bound, malformed JSON/UTF-8, trailing non-whitespace, duplicate/unknown/missing/wrong-type fields, invalid identifier/text/reference grammar | invalid_input on every dispatcher; no authorization/private lookup/mutation. |
| Unknown op, unsupported version or unsupported op/version pair, with or without additional shape defects, in any member order | invalid_input on every dispatcher; no schema fallback. |
| Fully shape-valid recognized request on a different dispatcher; fully shape-valid legacy v1 inspect_change on any new-host dispatcher | unsupported before private lookup. Malformed variants still fail decode as invalid_input. |
| Matching dispatcher; policy unavailable versus denied/wrong principal; request Workspace/Change mismatch; grammar-valid embedded reference names another Change | unavailable for unavailable policy; otherwise denied. Check host/subject first, then embedded-reference association, all before private lookup. |
| Connection to wrong/missing/damaged retained profile controls, or invalid installed custody/prefix/incident/pending during a call | unavailable, evidence preserved; no profile/parser fallback or private delivery. |
| Valid authorized custody; accepted key then pending key with changed kind/typed input | conflict before new predecessor/capacity admission. Exact accepted retry returns its original result even at capacity or after later revisions. |
| Valid new revision with stale predecessor; valid new request while another key is pending; missing origin or absent accepted at reference | conflict for stale predecessor; unavailable for the other cases. |
| Otherwise admissible new request exceeds count/accepted-byte capacity; unused non-original opening key | unsupported, without reservation or append. |
| Final disclosure unavailable/denied after accepted work or historical selection | unavailable/denied error only; commitment is not rolled back and cannot grant disclosure. |

Wrong entry-point recognition does not consult custody or disclose existence. Connection is an independent trusted-host operation, not client-request parsing. Private custody validation may run only after matching-dispatcher authorization/associations. Unknown operations never reach key resolution.

## Retry, predecessor and authority order

1. Bound/decode the complete closed union and reject malformed/unrecognized input as invalid_input; compare the recognized variant with the dispatcher. Establish current trusted-host policy/principal and Workspace/Change, then check any grammar-valid expected_intent/at reference's Change association before private lookup. Keep the policy valid throughout custody access and delivery as in R21.
2. Validate installed custody, incident control, the entire accepted prefix and the complete installed-pending feasibility predicate below before any private result/read, temporary cleanup or append. Build no persistent retry table; scan at most 128 records for the key, irrespective of operation kind. Existing origin and every revision participate in the one Change-wide namespace.
3. If the key already names an accepted operation, compare the entire typed original request: version, kind, subjects, key, expected predecessor where present, exact What and nullable Why. Changed kind or any changed input conflicts. An exact match returns the original stored result/actor/reference after fresh barriers, revalidation and current disclosure check. **Do this before comparing a new expected predecessor with the current intent.** Later revisions, capacity exhaustion, a pending newer request or an unaccepted suffix do not invalidate this historical retry if accepted grounds remain intact and no incident blocks delivery.
4. If not accepted, compare with installed pending custody. Same key plus changed input/kind conflicts. Only the exact pending request may finish it. A different new key while another request is pending is unavailable, not permission to replace/cancel its reservation. Inspection and old accepted retries may still disclose accepted grounds without completing pending work.
5. For a genuinely new revision require an accepted origin, no pending/suffix, expected_intent equal to the current accepted intent, unused key and remaining capacity. Stale predecessor conflicts; no origin is unavailable. Do not reserve on stale/capacity/denied input. Opening with an unused non-original key is unsupported; opening under an accepted revision key conflicts, and revising under `open-1` conflicts. Neither kind allocates a new namespace.
6. Reserve the exact input and independently established actor durably before append. Completion returns only after acceptance barriers, installed-control revalidation and current disclosure check. A denied final response does not undo acceptance; a later authorized exact retry delivers the original result.

No fresh key bypasses incidents, unresolved pending custody, accepted corruption or a suffix. Attribution is historical while disclosure authorization is current. The single-owner permission lease remains the sole selected policy: this slice does not add partial-record disclosure or a collaboration policy. It does not treat intent capture as permission for effects.

## Bounded current/historical intent read

`inspect_intent.at:null` selects the latest accepted intent. A nonnull reference selects that exact accepted intent, including origin or any intervening revision. Selection does not change the tip or execute/resume a request. The response has this exact ordered schema (angle-bracket material denotes a typed value, not literal JSON):

```text
{"v":2,"kind":"intent_inspection","workspace_id":"workspace-1","change":"change-1","projection":"ck-intent-view@1","purpose":"intent","origin":"change-1:origin","tip":<latest operation ref>,"current_intent":<latest intent ref>,"selected_intent":<selected intent ref>,"record":<complete selected origin or revision record>,"coverage":{"first":1,"last":<accepted count>,"sha256":<accepted-prefix digest>,"selected":<selected seq>,"returned":1,"complete":true},"progress":<readiness string>}
```

All direct inspection-envelope fields and direct coverage members are required, nonnullable and fixed-schema. Embedded record schemas retain their declared nullability: origin record.prev is required-null; origin/revision record.input.why is required nullable. Request at is required nullable but is not copied as an envelope member. Missing/null/empty distinctions survive projection and retry comparison. The versioned projector exposes exact assertions, attribution, request/result and predecessor, not a summary or assessment. Coverage says that records 1 through `last` were validated, while only one selected complete record was returned; it does not imply every historical intent was included in the response. The selected prefix is the current installed checkpoint at this serialized call, identified by Change/custody validation plus count and digest. There is no client-selected old checkpoint, follow stream, ledger range or native State coverage. `origin`, `tip` and cursor (`selected_intent`) are distinct even if some values coincide. A reader can retrieve all middle records by their bounded logical references; references remain usable after later revisions.

`progress` is exactly `ready`, `blocked_pending` or `blocked_unaccepted_tail`. Pending takes precedence when a valid installed pending request exists, including its exact partial suffix. Otherwise extra bytes imply blocked_unaccepted_tail. This describes storage readiness for these two mutation kinds, not effect admission or a workflow stage. At generation 0 inspection is unavailable; no empty/origin text is invented. A retained incident, damage anywhere in the accepted prefix, malformed pending/control or unexplained temporary blocks all private reads. A bounded unexplained suffix without pending does not enter the view and does not prevent delivery of an intact accepted prefix.

Query responses are bounded to 2,097,152 bytes, allowing one maximum-size record plus fixed metadata. Use a private query-only bounded emitter entry point with the same canonical formatter; keep the existing emit entry point and its 1,048,576-byte cap for R21 and for all requests/records/results/controls. Do not globally widen LIMIT or expose a caller-selected output limit. There is no truncation, redaction-as-completeness or omission of What/Why. Authorize before lookup and recheck immediately before delivery; denial/unavailability returns only the error envelope. Current and historical reads use identical disclosure gates and fresh custody barriers. The original text remains available by selecting origin, not by making every response duplicate it.

## Version-2 controls, bounds and acceptance

### Exact control interpretation

Use the existing inventory names, lock/descriptor protection and explicit fresh/resume/reopen modes. Anchor has exactly R21's ordered members and provisioning semantics, but `format:"ck-intent-anchor@2"`. The independent host grant pins this profile and all existing associations/physical identities; a path/tag alone cannot select/enroll custody. Internal anchor `stage` remains preparing/installed provisioning state, not public Stage. Incident has exactly R21's clear/blocked shapes and phase/issue enums, but `format:"ck-intent-incident@2"`. Blocked/malformed incident or any incident temporary remains monotonic refusal, including historical delivery. No repair/reset route is added.

Checkpoint retains the same ordered seven members but uses `format:"ck-intent-prefix@2"`:

```json
{"format":"ck-intent-prefix@2","custody":"custody-1","change":"change-1","generation":0,"end":0,"sha256":null,"pending":null}
```

`generation` now means accepted record count, 0–128, explicitly only under the new tag. No replacement/reservation counter is implied. At zero, end is zero and sha256 is required-null. Above zero, end is positive and sha256 is the lowercase 64-hex hash of bytes `[0,end)`; required `pending` is null or exactly `{"input":<complete opening or revision request>,"actor":"owner-1"}`. Nonnull pending must pass the complete consumer feasibility predicate below; positive count/current predecessor alone do not suffice. Result/seq/offset are not stored twice in pending: the selected prefix and deterministic constructor fix them. A pending reservation cannot advance accepted count/end/digest. An accepted replacement increments count by one, selects the old prefix plus exactly its reserved canonical record and clears pending. No accepted checkpoint may skip records or retain pending for an already accepted key.

All controls remain bounded to 1,048,576 bytes. Accepted bytes are at most 16,777,216; each accepted record is at most 1,048,576 bytes; count at most 128. Total trace including suffix is at most 17,825,792 bytes. A new reservation is refused as unsupported if its deterministic full record would cross either accepted bound. Existing accepted history with valid pending:null remains readable/retryable at capacity; there is no eviction or archive rollover. Oversized existing storage is unavailable and preserved.

### Complete installed-pending consumer predicate

First validate installed profile/associations, incident/inventory, accepted count/end/hash and every accepted record independently. Before any private read/retry response, checkpoint-temporary cleanup or append, validate each installed nonnull pending against that accepted prefix:

1. Pending has exactly required input and actor; actor is the independently pinned owner-1. Input is a fully shape-valid mutation request, with pinned Workspace/Change and valid key/text/null distinctions; inspection variants are forbidden. The pending key is absent from every accepted operation regardless of kind.
2. Opening pending requires count/end 0, sha256:null and key open-1. Revision pending requires count 1–127, with expected_intent equal to the accepted tip intent. Thus every pending requires count < 128; pending at count 128 is damage, even with an empty suffix.
3. Construct the deterministic next record using retained actor, input and validated predecessor at checked sequence count + 1. Canonical record length L must satisfy 0 < L <= 1,048,576 including LF; construction/reference/result validation must succeed. With checked unsigned arithmetic require end + L <= 16,777,216. Overflow or construction failure is damage, not permission to append partially.
4. Physical suffix [end,trace_length) must be empty or an exact byte-prefix of that one canonical record, including at most its complete bytes. Accepted bytes remain untouched. Extra, mismatched or oversized suffix is damage.

This same feasibility predicate governs producer reservation and prospective reservation controls, rather than relying on producer refusal as evidence of installed validity. Apply steps 1–3 to a proposed reservation temporary against the installed accepted prefix, with step 4 checked against actual suffix as required by its cleanup relationship. For an accepted-successor temporary, require a feasible installed pending and a complete exact suffix, then validate the candidate's count/end/hash/pending:null and full selected prefix normally. Equality with installed bytes is never an exemption from installed-control validation.

An impossible installed pending is unavailable damaged custody: preserve installed control, suffix and every temporary; no private historical delivery, append or checkpoint cleanup. The result is the same with empty, partial or complete deterministic suffix and with an identical or purported-successor temporary. This differs from valid full-capacity pending:null control, which permits reads/old retries and rejects a new reservation as unsupported. A feasible pending at count 127 reaching exactly 128, or end + L exactly equal to the byte ceiling, remains supported.

These are conservative fixture ceilings, not measured scalable-ledger targets: 128 bounds key/association comparisons and supports 127 small revisions; 16 MiB bounds cold validation/data retention; one extra record-sized allowance bounds an interrupted or unexplained suffix. Two independent limits avoid allowing 128 maximum-size records to require roughly 128 MiB. Text/record limits retain R21 compatibility. Raising any ceiling is an explicit profile change with measured evidence, not a silent configuration knob.

Each validation pass reads at most the bounded trace plus bounded controls, hashes selected bytes, walks at most 128 fixed-schema lines and verifies contiguous sequences, predecessors, association, actor, global key uniqueness, reconstructed results and canonical bytes. Hashing alone is insufficient. Use a bounded trace buffer and sequential decode; retain only needed selected/key-match records and bounded key metadata during a pass, not every decoded intent or a persistent index. Normal API calls should require no more than four full validation passes (preflight, post-checkpoint when mutating, fresh delivery revalidation, and at most one cleanup revalidation); connect is a separate bounded operation with at most three. This is a bounded work budget to verify against implementation, not demonstrated efficiency. Construction buffers are additionally bounded by request/record/response/control limits. No unbounded directory scan is permitted: fail upon the first unknown entry and stop after the fixed inventory maximum. Publish actual trace/control bytes read, accepted/suffix bytes hashed, canonical decodes/re-emissions, pass counts and peak simultaneous live buffers in witnesses, including preflight objects retained during delivery validation. Cleanup revalidation and accepted-successor temporary validation count toward the same pass/work budget; they are not free work. No latency claim is made.


A prospective successor may be proved from the already fully validated accepted prefix and the deterministic next record in the same immutable, already-read trace buffer. Cover all selected bytes: a retained current-pass SHA-256 state may be extended over the exact next bytes. This is not acceptance from only count/hash, an unchecked extension, promotion of a temporary or a persistent cache. It does not replace required fresh post-cleanup, post-checkpoint or delivery validation. Any additional full read/hash/decode/re-emission walk counts toward the work budget. Count-129 suffixes in negative witnesses are purported invalid data, not valid constructible profile records.

### Producer/consumer protocol for any prefix length

Under the same pinned cooperative lock and policy lease: validate/resolve accepted key → verify feasible pending or new predecessor/capacity using the bounded canonical next record → for a new request, replace and synchronize its feasible reservation checkpoint → reconstruct/verify the one canonical reserved record against that reservation → append only missing bytes → synchronize trace → write/synchronize checkpoint.tmp → rename over checkpoint → synchronize slot directory → validate installed accepted count/end/full-prefix hash and every selected record → fresh custody barriers/revalidation → recheck current disclosure → deliver retained result.

Original accepted bytes are never rewritten. Appending a revision requires physical trace length equal to selected end, except an exact installed pending suffix eligible for continuation. Reopen never promotes a parseable suffix or a checkpoint temporary. Fresh barriers include trace, checkpoint, incident, slot directory, anchor and anchor parent as in R21. Handle ownership, no fork/inherited custody fds, confirmed predecessor exit and permanent nonblocking cooperative flock remain required. Lock acquisition alone is not predecessor-exit proof.

| Installed evidence, with no retained incident | Required successor behavior |
| --- | --- |
| Count 0, pending null, empty trace | Accept the original opening normally; no inspection yet. |
| Count 0–127, pending satisfying every feasibility predicate, suffix empty or exact byte-prefix of its deterministic next record | Reads/old retries select only accepted records, if any. Only authorized exact pending retry appends missing bytes and runs full acceptance. A complete suffix is still unaccepted. No reopen auto-completion. |
| Pending impossible by count, projected accepted bytes, actor/kind/subjects/key/predecessor, canonical construction or suffix mismatch/extra/size | Unavailable; preserve controls/suffix/temporaries, refuse all private reads/retries, cleanup and append. Empty or complete matching suffix does not cure impossible capacity. |
| Count > 0, pending null, exact accepted end | Reads/exact retries deliver original records/results after barriers; no append on retry. New revision needs current predecessor. |
| Count > 0, pending null, bounded extra bytes | Validate accepted prefix independently. Read with blocked_unaccepted_tail; exact accepted retry delivers original result. Refuse new mutation; preserve suffix. |
| Count 0, pending null, nonempty trace | Unavailable, not a new origin inferred from bytes. |
| Missing/changed accepted bytes, wrong selected hash/count/end, duplicate keys, gaps or inconsistent result/predecessor | Unavailable for all private delivery/progress. Never rebuild acceptance control or regenerate lost accepted content. |

Pending append continuation compares only suffix `[end,trace_length)` with the canonical reserved record and preserves bytes `[0,end)` exactly. Deterministic append completion is permitted for process interruption, not after an observed short write/I/O/barrier/replacement incident: live latch and retained incident still block it.

### Temporary cleanup and uncertainty

Before a new replacement, validate the installed checkpoint, full accepted Trace and complete installed-pending feasibility first; then validate checkpoint.tmp canonically against that valid control and Trace. Invalid installed control forbids every cleanup relationship, including byte equality. Only these relationships permit unlink plus parent synchronization, never promotion:

- Temporary exactly equals an independently valid installed checkpoint, including pending feasibility if nonnull.
- Installed pending is null, physical trace equals accepted end, and temporary is a feasible reservation successor under the complete consumer predicate, with unchanged count/end/digest. At zero only the original opening may reserve; at middle only an unused-key/current-predecessor revision; at count 128 or insufficient byte room no reservation temporary is valid.
- Installed pending passes the complete feasibility predicate, suffix equals the complete deterministic reserved record, and temporary equals its exact accepted successor (checked count + 1, end + L within bounds, full-prefix hash, pending null). Validate that successor's full accepted grounds, not only its increment/hash. Count 127 → 128 and exact byte-ceiling equality are supported; capacity crossing never is.

A valid abandoned reservation temporary is discarded, not treated as a durable reservation; exact original request may reserve again. Partial/noncanonical/unrelated/backward temporaries block and remain. No arbitrary next-generation candidate is accepted merely because its hash matches. Revalidate installed control and prefix after cleanup; interruption before unlink repeats validation, after unlink synchronizes the directory before further mutation, and after the cleanup barrier resumes normal exact-input processing. An observed unlink/barrier failure follows incident retention. The accepted checkpoint never comes from a temporary or tail.

Anchor-temporary cleanup remains restricted to complete deterministic initial inventory with zero count/no pending/clear incident; it cannot clean a provisioning temporary after history exists. Incident temporaries are never housekeeping. Unknown entries, symlinks/nonregular controls, missing permanent files, wrong directory/lock identity or copied custody refuse rather than re-enroll.

Any genuine observed I/O error, short write, failed barrier or uncertain replacement latches unavailable before an acceptance-bearing response; attempt bounded blocked-incident retention through the same writer. Never overwrite blocked/malformed evidence with clear. Failed incident retention cannot clear the live latch. Restart refuses surviving blocked/malformed incident evidence. This extends R21's refusal semantics, not a new recovery authority.

Complete loss/consistent rollback of all evidence remains undetectable; an incident observation lost before retention cannot be recovered. Crash cutpoints do not prove power-loss/reboot durability, hostile rollback resistance, hostile same-privilege isolation or native effects. Incident repair, migration and transfer are outside this profile.
