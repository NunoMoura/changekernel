# Ledger Collection and Selection Profile

**Historical v4 contract; executable support withdrawal adopted, integration pending.** Start with the [current referenced-intent prototype](referenced-intent-prototype.md) and [SDK/Pi boundary](sdk.md). This page preserves its consumed schemas, authority, custody, retry and accounting meanings and existing anchors. Implementation-era status, reuse instructions and old-API/test preservation statements below are historical, not an active assignment or perpetual support promise; see the [support disposition and exact source checkpoint](native-profiles.md#historical-compatibility-reference). No old-custody operation or current semantic change is authorized.

## Status and requirement authority

**Selected consumed contract after independent correction review and manager adoption. Not implemented or source-accepted.** This page fixes the bounded producer/consumer protocol for a separately assigned source increment; adoption alone grants no implementation assignment, installation, qualification or controller authority. Existing opening, intent-revision and assessment profiles remain unchanged.

Requirements come from the [foundation-first collection increment](../../product/plan.md#foundations-before-agent-integration), [ledger ownership](../../product/changekernel.md#ledger-change-files-and-derived-context), [working-set and archive boundary](state.md#ledger-working-set-archive-and-restore), [retry and durability requirements](state.md#record-replay-and-durability-requirements) and [authorized structured reads](state.md#structured-history-access-and-context-projections). Necessary creation associations are custody controls, not rebuildable indexes. JSONL remains the sole Change lifecycle history.

## Outcome, fixture and exclusions

An authenticated fixture owner creates two independent intent-bearing Changes, lists an authorized page of size one, selects either stable identity and inspects its exact original intent from a fresh process after confirmed predecessor exit. Exact original creation retries return the original Change/result without another allocation or line, including after another Change exists or the response was lost. Listing, selection, inspection and ordinary reopen do not accept pending creation, append, assess or execute effects.

The proposition fails if retry creates another pursuit, a selector resolves another member, unauthorized metadata is returned, missing acceptance control is guessed from files, or unavailable validation becomes a complete/empty page. This finite fixture makes no scalable-ledger, constant-cost, cold/warm latency or release claim.

Select fresh-only `ck-ledger@4` in a model-free Rust library `LedgerHost`. This is an **opening-only collection successor**, not enrollment of an existing profile-1/2/3 slot and not a downgrade of those slots. A ledger member has precisely one original intent operation; revision/assessment on these new members is unsupported by this selected interface. The independently selected assessment policy is not required to create or list a Change. Extending these members with later operations needs a separately consumed successor contract.

Retain a trusted local Linux host, one independently authenticated `owner-1`, `workspace-1`, binding `fixture@1`, local filesystem/directory synchronization assumptions and cooperative exclusion. Paths and custody grants come from trusted composition, never client JSON. No untrusted code receives custody descriptors; no fork occurs while a host owns them. A successor requires confirmed predecessor exit and no inherited handles, not merely successful lock acquisition. Host compromise, hostile same-privilege writers, external namespace replacement, network filesystems and storage repair remain excluded.

No folder-wide sharing, native effects, completion/disposition mutation, archive/restore/deletion, general queries, relationships, agents, models, arbitrary append, general Checks, migration, receipt reinterpretation, speculative index/cache or controller operation is selected. Every jointly accepted fresh member belongs to the active working set; creation does not establish lifecycle completion. Physical placement has no permission or workflow meaning.

## Trusted identities and allocation

Trusted `LedgerGrant` supplies profile, ledger identifier, ledger custody identifier, owner, Workspace/binding, absolute ledger directory and external anchor path, plus an ordered array of exactly **16 unused pairs** `{change,custody}`. Pair fields use opaque ASCII `[A-Za-z0-9_-]{1,64}`. Change identifiers are distinct within this ledger; every member custody differs from ledger custody and every other member custody. The host independently provisions each ledger with a distinct ledger custody and its own unused member grants. Reusing printable Change/key values in an isolated ledger does not share authority. Supplied paths are canonical absolute UTF-8, at most 4,096 bytes each, without symlinks, control characters or dot/parent components. Anchor lies outside the ledger directory in its trusted parent.

The anchor pins the entire grant. Reopen requires the same independent grant, protected anchor and physical identities. A client ledger identifier is only a selector. A foreign/wrong ledger or Workspace is denied before private lookup. The initial fixture may name its first two pairs `change-a`/`custody-a` and `change-b`/`custody-b`; these are examples, not fixed global identities. Pair names need not encode allocation position. Private slot numbers never enter responses/cursors.

After authorized shared-control validation, resolve an installed accepted or pending creation key **before allocating a pair, provisioning a member, accessing a source or performing effects**. There are no sources/effects here. A genuinely new creation reserves the first unused grant position, `entries.len()+1`. This is host allocation from explicit finite unused grants, not random allocation or a caller-selected Change/path. A reservation never changes identity during recovery. No deletion, slot recycling or re-enrollment is supported.

Ledger/ledger-custody/creation-key request and grant identifiers use the same opaque ASCII 1–64-byte grammar as member pairs. Workspace, owner and binding remain the stated fixture literals, with binding `fixture@1` deliberately outside the opaque-identifier grammar.

A creation key names one original operation in `(profile, ledger custody)` across actors, not `(actor, operation)`. Complete typed input equality includes version, kind, ledger, Workspace, key, exact What and nullable Why. JSON whitespace/member order do not change typed identity. Null and empty Why differ. Hash equality alone never replaces typed equality. Historical delivery retains the original actor/result; an authorized later caller cannot acquire authorship. Only `owner-1` acts in this fixture. Future member operation keys must retain their own Change-wide namespace; this contract neither imports old `open-1` keys nor reinterprets them as ledger keys.

## Closed API and wire contract

Trusted composition provides `LedgerHost::connect(grant, mode, guard, optional_fixture_hook)` with `FreshProvision`, `ResumeProvision` and `Reopen`. Connection is independently authorized for the ledger and returns either an owning host or unavailable/denied; it is not request parsing or acceptance-bearing disclosure. Reopen acquires the permanent ledger lock, validates installed shared controls and performs only the shared structural classification of creation.tmp described in [deferred creation proof](#reconnect-and-deferred-creation-proof). A canonical structurally feasible ready/acceptance successor returns a **nondisclosing owning host with unresolved proof**, not a proved temporary or an accepted member. No member handles/controls/origins are accessed in connect; M=0. Ordinary member A damage therefore does not prevent connecting to select B when no unresolved shared remnant applies. Reopen initializes/repairs/cleans nothing; genuine observed shared I/O/barrier failure follows the bounded incident-retention exception below. Before returning a host, synchronize/revalidate the shared grounds, repeat current ledger-connect authorization and discard/release the host on denial/unavailability. Resume is for explicit ledger installation only, never completion of a member creation. Connection observations survive failure before a host exists.

Public bounded dispatchers are `create_change`, `list_changes`, `select_change` and `inspect_change`, each consuming the following new shapes. All shown fields are required; Why and cursor are the only nullable request fields. Limit is unsigned integer 1–4.

```json
{"v":4,"op":"create_change","ledger":"ledger-1","workspace_id":"workspace-1","key":"create-a","what":"Record settings cleanup","why":"Keep original reason"}
{"v":4,"op":"create_change","ledger":"ledger-1","workspace_id":"workspace-1","key":"create-b","what":"Record backup cleanup","why":null}
{"v":4,"op":"list_changes","ledger":"ledger-1","workspace_id":"workspace-1","limit":1,"cursor":null}
{"v":4,"op":"list_changes","ledger":"ledger-1","workspace_id":"workspace-1","limit":1,"cursor":{"v":4,"ledger":"ledger-1","workspace_id":"workspace-1","after":"change-a","limit":1}}
{"v":4,"op":"select_change","ledger":"ledger-1","workspace_id":"workspace-1","change":"change-b"}
{"v":4,"op":"inspect_change","ledger":"ledger-1","workspace_id":"workspace-1","change":"change-b"}
```

There is no client actor, approval, path, custody, slot, allocator, result, digest, policy, evaluator or passing-result field. Reject unknown/duplicate/missing fields, duplicate-null, wrong types, floats/coerced integers, forbidden extras, malformed UTF-8/JSON, arbitrary arrays/nesting, bad identifier/text bounds and trailing non-whitespace as invalid_input. What is exact nonblank UTF-8, 1–65,536 bytes, using the opening profile's nonblank predicate; Why is null or exact UTF-8, 0–65,536 bytes. Preserve all supplied bytes without normalization. Ingress is bounded to 1,048,576 bytes before decode.

Use one duplicate-aware manually typed request union with slots for `v,op,ledger,workspace_id,key,what,why,limit,cursor,change`. Nullable presence is separate from value. At map end select exactly a recognized v4/op pair and verify its exact field mask; do not return early upon an op/version field or reparse with a fallback visitor. Unknown op/version pairs, including old v1/2/3 requests, are invalid_input here. A fully valid recognized v4 request on the wrong dispatcher is unsupported before authorization. These new decoding choices do not change any old host's precedence.

Requests/results/records/controls use the opening profile's fixed struct-order canonical formatter: exact UTF-8, quote/backslash escaping, all control characters as lowercase six-byte `\u00xx`, solidus unescaped, unsigned decimal integers and one terminal LF. Retained data must equal typed re-emission. Arrays described below are the only new arrays: accepted entries and grant pairs, at most/exactly 16 respectively; reject the seventeenth element immediately. Client arrays are never accepted. SHA-256 is lowercase 64 hex over canonical LF-inclusive bytes, evidence under trusted custody rather than authentication by itself.

### Origin, retained result and inspection

A's retained result and sole lifecycle record are exactly these ordered shapes:

```json
{"v":4,"kind":"created","ledger":"ledger-1","workspace_id":"workspace-1","change":"change-a","key":"create-a","actor":"owner-1","result":"change-a:origin","seq":1}
{"v":4,"custody":"custody-a","ledger":"ledger-1","workspace_id":"workspace-1","binding":"fixture@1","change":"change-a","seq":1,"prev":null,"kind":"created","input":{"v":4,"op":"create_change","ledger":"ledger-1","workspace_id":"workspace-1","key":"create-a","what":"Record settings cleanup","why":"Keep original reason"},"result":{"v":4,"kind":"created","ledger":"ledger-1","workspace_id":"workspace-1","change":"change-a","key":"create-a","actor":"owner-1","result":"change-a:origin","seq":1}}
```

Every direct record/result field is required and nonnullable except record `prev`, required-null. Embedded Why retains its required nullable meaning. Result identity is allocated Change plus literal `:origin`, 8–71 bytes, not an opaque-identifier field or authority token. Reconstruct the complete record/result from reservation, installed associations and original actor; check every field and canonical byte, not merely a digest.

Selection is an explicit stable identity operation, not a hidden global selected slot. It returns `{"v":4,"kind":"selection","ledger":L,"workspace_id":W,"member":M}`, where M has exactly the list metadata schema below. It opens and validates that member afresh. The caller then names this same Change in `inspect_change`; the latter reopens/reauthorizes independently, even in a new process without prior listing/selection. Selection returns no continuing custody handle or execution permission.

Inspection returns this ordered template (metavariables are not literal JSON):

```text
{"v":4,"kind":"inspection","ledger":L,"workspace_id":W,"change":C,"projection":"ck-ledger-origin-view@1","purpose":"intent","origin":C+":origin","tip":C+":origin","current_intent":C+":origin","record":<complete origin>,"coverage":{"first":1,"last":1,"sha256":<origin digest>,"selected":1,"returned":1,"complete":true},"progress":<"ready" or "blocked_unaccepted_tail">}
```

All direct fields are required/nonnullable. Progress ready means intact accepted origin custody/disclosure only, not permission or native readiness to continue/execute a pursuit. Coverage means the entire one-record accepted prefix validated, one record returned; not native State coverage, continuation readiness or absence of other ledger members. A bounded suffix with otherwise valid acceptance may be disclosed as blocked_unaccepted_tail; it is never adopted, truncated or included. No jointly accepted creation is unavailable, not an invented empty intent. Query/selection never appends, finalizes pending association, assesses, moves a tip or executes work.

## Durable controls and physical layout

The external protected ledger anchor has exact ordered fields:

```text
format,ledger,custody,workspace_id,binding,owner,directory,directory_device,directory_inode,lock_device,lock_inode,members_device,members_inode,grants,stage
```

`format` is `ck-ledger-anchor@4`, grant associations match independently supplied values, physical fields are unsigned 64-bit device/inode identities, grants is the ordered 16-pair array above, and stage is preparing/installed. It identifies both the permanent ledger directory/lock and permanent `members` directory. Stage is internal installation state, never a workflow primitive. The anchor and its reserved sibling `anchor.tmp` are the only files of this installation in its independently configured trusted parent; other installations in that parent are not discovered/scanned.

Ledger root inventory is exactly `writer.lock`, `creation.json`, `incident.json`, `members`, plus at most `creation.tmp` and `incident.tmp`. Lock and members directory are never renamed/removed. `members` contains, for each accepted/pending private slot n, at most directory `m-n` and file `m-n.anchor.json`, plus at most one `anchor.tmp` for the currently pending member. No unused slot's files may appear. There are at most 33 names, plus the first refused unknown name. Physical flatness is logical Change identity, not a promise of only JSONL files in one directory.

Each member directory inventory is exactly `writer.lock`, `trace.jsonl`, `checkpoint.json`, `incident.json`, plus at most `checkpoint.tmp` and `incident.tmp`. Its anchor is a protected sibling, outside that member directory. Unknown names are refused immediately; no directory tree discovery occurs. Member paths derive solely from the private installed slot, never Change spelling or caller path concatenation.

The member anchor uses ordered opening anchor fields under `ck-ledger-member-anchor@4`, with `ledger` immediately after `custody`: `format,custody,ledger,workspace_id,binding,change,owner,key,directory,directory_device,directory_inode,lock_device,lock_inode,stage`. Associations come from the durable reservation and independently pinned grant; key is that original ledger creation key. Ledger acceptance additionally pins its physical tuple below. Preparing/installed rules have the explicit exception that **only an exact authorized create retry** can resume a pending member. Ordinary reopen/reads create no missing controls.

Member checkpoint uses `ck-ledger-member-prefix@4` with exact ordered fields `format,custody,change,generation,end,sha256,pending`. Generation is 0 or 1 only. Initial is 0/end 0/hash null/pending null; reservation has pending `{"input":<complete v4 creation>,"actor":"owner-1"}`; accepted is 1/end L/hash of origin/pending null. Pending must match the shared ready reservation exactly, including ledger, key, original actor and entire typed input. At zero, any physical trace is either empty with pending null or an exact byte-prefix of that pending deterministic origin. At one, validate the whole canonical origin independently. A missing control cannot be regenerated from a parseable origin.

Ledger/member incidents use `ck-ledger-incident@4` / `ck-ledger-member-incident@4`, with ordered clear fields `format,custody,state`; blocked adds `phase,issue`. State is clear/blocked. Phase is provision/reserve/append/checkpoint/associate/deliver/recover; issue is io/short_write/barrier/inconsistent. Any missing/malformed/blocked incident or incident.tmp blocks its scope; even a clear incident temporary is not housekeeping. No incident reset/repair API exists.

### Permanent creation association control

`creation.json` is **indispensable acceptance/retry custody control**, not a catalogue, View, cache or second lifecycle history. Its exact ordered schema is:

```text
{"format":"ck-ledger-creations@4","custody":<ledger custody>,"ledger":L,"generation":G,"entries":[<accepted association>...],"pending":<null or reservation>}
```

An accepted association has exact ordered fields:

```text
slot,key,change,custody,actor,input_sha256,origin_end,origin_sha256,physical
```

`physical` has exactly `directory_device,directory_inode,lock_device,lock_inode`, unsigned 64-bit values. Slot n is private integer 1–16 and equals entry's allocation position. Pair agrees with grant[n-1]; actor is original owner; key is valid and distinct across all entries and pending. Input digest covers complete canonical creation input. Origin length is 1–1,048,576 including LF; origin digest covers exactly that accepted line. These fields select association/acceptance, but never manufacture missing original input/result. Full typed equality and private delivery require the independently validated member origin.

Pending has exact ordered fields `slot,input,actor,phase,physical`. Slot is entries.len()+1. Phase reserved has physical null; phase ready has the physical tuple pinned from completed installed **initial** member provisioning. Input is the complete valid creation request, including exact What/Why, with pinned ledger/Workspace and unused key. Actor is original owner. Construct the origin against grant[slot-1] and require its canonical length <=1,048,576 before reserving. Generation is exactly `3*entries.len()` with pending null, plus 1 for reserved or 2 for ready. Initial is generation 0/entries empty/pending null; full is generation 48/16 entries/pending null. A pending at 16 entries, duplicate key/pair, noncontiguous slot, wrong grant/actor/phase/physical shape, bad bounds or impossible generation is shared damage, not capacity exhaustion.

Shared validation checks anchor/grant/handles, global inventory, incident and the complete bounded association array/pending schema. Creation.tmp structural classification is separate from any required member-dependent proof; an unresolved classification grants no ordinary-dispatch/private-delivery authority. It does **not** open every accepted member to prove shared control valid. Member acceptance is a conjunctive consumer check: installed accepted association, intact installed member anchor/physical identity, clear member incident, exact checkpoint-selected origin, and agreement on original key/actor/input digest/origin length/digest/allocated pair. A member checkpoint at one without the shared accepted association is only an internal creation candidate, never a listed/selected/deliverable Change.

Missing creation control refuses all collection operations. Missing/damaged A member controls are A damage, not evidence A was never accepted, permission to allocate it again or shared-control corruption. A's indispensable entry remains. Unknown inventory/contradictory shared entries are shared damage; loss of an expected member file is checked locally when that member is consumed.

## Locks, provisioning, acceptance and incidents

One nonblocking exclusive `flock` on the pinned permanent ledger lock is held for the entire host lifetime. It serializes every collection call and member custody access for this fixture. A member lock is acquired only while the ledger lock is held, always ledger → one member; close all member handles before proceeding to another. No simultaneous member descriptors/locks, detached continuation hosts or reverse acquisition. Keep the ledger lock during policy checks, temporary validation, all writes/barriers and final delivery. Expected cooperative contention returns unavailable without inventing an I/O incident. This is not native-resource serializability or folder-wide access authority.

Deliberate fresh ledger provisioning requires explicit unused first-use grant. Exclusive root/lock/members creation, synchronization of files/changed parents and installation of a preparing external anchor precede initial controls. If these identities/anchor are lost before surviving preparation, auto-resume refuses; an empty path is not first-use authority. Resume with intact preparing anchor verifies installed grant/handles, empty member inventory and deterministic initial creation/incident controls, creates only missing initial controls, synchronizes them/parents, then installs and synchronizes installed anchor. No client dispatch runs before installation completes. Unexpected pending/history/bytes refuse. Installed reopen requires all permanent shared controls; it never initializes or migrates.

Initial-only anchor.tmp rules retain the opening profile's strict relationships: canonical preparing-equal or expected installed successor with preparing authoritative anchor; installed-equal with installed anchor; complete deterministic initial inventory required in both cases. Explicit provision/resume may unlink a proved remnant and synchronize, then rerun ordinary validation/create a fresh replacement. Never promote it. Partial/unrelated/backward temporary, incomplete/noninitial inventory or observed cleanup failure refuses/preserves. Ledger initial means no entries/pending/members; member initial means empty trace/zero checkpoint/no pending/clear incident under the exact shared reserved request. Ordinary Reopen/reads do not perform this cleanup; an unexplained anchor temporary blocks its scope.

### Creation sequence and acknowledgment

Under current ledger creation permission and current member creation/disclosure permission for the allocated subject:

1. Validate installed shared custody and resolve accepted/pending original key before allocation. If a ready/acceptance creation.tmp proof is unresolved, use only the exact original create preflight/proof/cleanup path below; all unrelated operations refuse before member access. Then resume from the installed reservation/member state, never from temporary authority. Accepted key needs current authorization for its retained member before member access, then full member/typed-input validation. Exact accepted retry uses barriers/revalidation and returns original stored result; changed input conflicts. It bypasses allocation/capacity, not custody/disclosure.
2. For new input, prove unused key, pending null, remaining slot and feasible canonical origin. Durably replace creation control with reserved pending (generation +1) **before any member provisioning**. Write/sync same-directory creation.tmp, rename over creation.json, sync ledger root and revalidate installed reservation. No acknowledgment yet.
3. Provision that exact member exclusively using its reserved grant, permanent member lock and preparing/installed anchor. It must be deterministic initial custody only. Synchronize member files, directory and members parent. Then replace/sync/revalidate creation control to ready (generation +1), pinning its physical tuple. No origin reservation/append is allowed while shared pending is reserved.
4. Replace/sync member checkpoint with the exact pending request/actor; reconstruct deterministic origin, compare existing suffix, append only missing bytes, sync trace, write/sync checkpoint.tmp, rename over checkpoint, sync member directory and revalidate installed generation-one full origin. This is not yet accepted ledger membership.
5. Validate shared ready reservation and exact member origin/physical grounds together. A ready pending member must have exactly the complete origin bytes, with no unexplained suffix; historical bounded-suffix disclosure applies only after an installed accepted shared association. Replace/sync creation control with its appended accepted association, pending null, generation +1. Sync ledger root/members parent; revalidate the installed shared control and the member acceptance conjunction. This installed conjunction is the creation acceptance point, not any previous rename alone.
6. Fresh barriers cover ledger anchor/parent, creation/incident/root/members and selected member anchor/parent/trace/checkpoint/incident/directory. Revalidate shared and member grounds, recheck both current disclosure scopes and deliver the retained result. A delivery-cut failure or denied response discards private bytes. It does not roll back acceptance; later exact authorized retry returns the same original result.

No series of renames is a cross-file transaction. The durable pending association bridges separately committed member preparation/origin and ledger membership; surviving evidence can show a partially committed creation. All controls stay retained. Storage failure is unavailable, never proof of nonacceptance. Only the exact authorized mutation retry can finish a supported pending cut; reopen/list/select/inspect cannot.

Genuine I/O/short-write/barrier/uncertain-replacement failure immediately latches **its scope** unavailable and discards all private response bytes before further acceptance-bearing delivery. This applies to create, Reopen, list, select, inspect, deferred proof and their delivery barriers. Attempt bounded blocked incident retention in the scope where failure occurred: shared-control/root/ledger-anchor/members-parent failure → shared incident; member-control/trace/member-anchor/member-directory failure → member incident. If classification itself cannot be established, shared latch/incident applies. Retention writes only through independently justified pinned custody handles; a connect failure before such handles exist cannot safely install an incident, and is unavailable with observation/retention failure reported. Never overwrite blocked/malformed evidence or discard incident.tmp. Failed retention does not clear the live latch. Member failure does not mark unrelated members blocked; a failed pending member prevents further new creation because its reservation cannot be bypassed. Intact accepted B remains selectable/inspectable when shared grounds have no unresolved member-dependent remnant; such a remnant blocks unrelated dispatches as specified below.

**Read non-mutation means no lifecycle/acceptance/pending/cleanup mutation, with one observed-failure exception.** A successful Reopen/list/select/inspect, an authorization/malformed-input/unsupported/expected-contention refusal, or deterministic damage changes no file bytes/names/generation. They never initialize missing controls, finish a pending member, append/truncate Trace, replace checkpoint/creation/anchor, clean any remnant or reset an incident. Only a genuine observed read/barrier I/O failure permits and requires bounded monotonic incident retention: at most one blocked-incident construction/replacement attempt per failing call, exclusive creation of that scope's incident.tmp, bounded write/sync, rename over a proved clear incident.json, then parent synchronization. Phase is recover for read/proof/connection failure or deliver for a delivery-barrier failure. The attempt can change only that scope's incident.json/incident.tmp bytes or names; lifecycle files, custody identities and accepted/pending generations stay unchanged. If incident evidence is already missing/malformed/blocked or incident.tmp survives, preserve it without replacement. Do not retry retention recursively or invent a second incident if retention itself fails; keep the original scope latch and report the failure. Required permission unavailable/denied is not a storage incident. A partial or failed incident replacement may leave incident.tmp, which blocks restart; absence after failed retention is not proof the observation was durably retained.

Retained blocked incident prohibits private delivery in that scope even if later barriers succeed. Deterministic damage refuses/preserves without pretending an observed I/O incident. Shared damage blocks all calls; local member damage blocks that member and any list needing it, but not authorized B selection/inspection/accepted retry when no unresolved shared remnant applies. After confirmed predecessor exit, successful member incident retention makes A refuse on the successor while intact B remains usable; a shared read/connection incident makes the successor refuse the collection. No fresh key, clean close or restart erases incidents. If retention failed without any surviving incident evidence, only the live scope latch is guaranteed: a successor may see the same legitimate bytes and cannot recover the lost observation. Complete loss/consistent rollback of all evidence cannot be distinguished from identical legitimate bytes. Ordinary process cuts are not exact-host reboot/power-loss qualification.

### Creation interruption and recovery table

These rows assume valid independently installed shared control and no retained incident in the required scopes. Deterministic refusal preserves every surviving byte/identity; genuine observed I/O/barrier refusal has only the bounded incident-retention exception above. Ready/acceptance creation.tmp rows use the nondisclosing reconnect/deferred-proof path below. Changed input under an installed pending key conflicts after current member authorization and before member provisioning; another new key while pending is unavailable. Accepted retries/reads of unrelated intact members do not finish pending work and are unavailable while member-dependent shared-remnant proof remains unresolved.

### Non-authoritative replacement remnants

Under valid installed controls, creation.tmp may be exactly installed control, its feasible reservation successor (no member files yet), its ready successor (complete installed initial member), or its acceptance successor (installed ready pending plus exact generation-one member origin and physical tuple). Generation/array/pending change must be **only** that prescribed step. Prove all required grounds, including pending feasibility; equality never exempts an invalid installed control. Partial, backward, unrelated, capacity-crossing or multi-step successor refuses globally. A proved temporary is never chosen as authority.

Only an authorized create operation with the associated exact input may unlink a non-equal successor temporary; installed-equal cleanup may accompany an authorized create after all required validations. Synchronize its parent and revalidate before any new replacement. Reads may prove shared-only relationships without cleaning them; member-dependent shared proof is deferred exclusively to exact original create and ordinary reads refuse while it is unresolved. Apart from observed-failure incident retention, reads leave every byte/name unchanged. A proof needing pending member custody first requires current member authorization; denial/unavailability prevents proof, not blind deletion. No other new key can discard an original uninstalled reservation remnant to take its slot.

### Reconnect and deferred creation proof

Reopen validates the installed shared control/anchor/incident, independent grant and global named inventory. It bounded-decodes/re-emits creation.tmp and classifies its **shared-only** relationship, without opening any member or acquiring a member lock:

| Structural classification | Connection outcome / authority |
| --- | --- |
| No creation.tmp, or canonical installed-equal control with valid installed shared grounds | Ordinary owning host. Equality proves only shared control equality, not any member's private acceptance. Dispatch still validates each consumed member; reads never remove the temporary. |
| Feasible one-step reservation successor, same accepted entries, next unused grant/input/actor/generation and no files for that unused slot | Ordinary owning host. Shared-only inventory/feasibility proves this unaccepted relationship; reads may disclose installed entries, but only matching exact create may clean/reserve. |
| Feasible one-step ready successor of installed reserved pending | Nondisclosing owning host with unresolved ready proof. Compare unchanged entries, slot, full input, original actor and grant; only pending phase/physical and generation may change. Tuple syntax is not physical proof. |
| Feasible one-step acceptance successor of installed ready pending | Nondisclosing owning host with unresolved acceptance proof. Exactly one appended association/pending-null/generation step; its key/pair/actor/physical/input digest/origin length/hash must equal the candidate deterministically constructed from installed pending/grant. Construction from shared input is not a member-origin read or acceptance proof. |
| Partial/noncanonical, impossible installed control, incident remnant, unrelated/backward/multi-step/capacity-crossing candidate or unknown global inventory | Unavailable, no host; preserve evidence except required genuine-I/O incident retention. No structural fallback guesses an association. |

The unresolved marker records only the private bounded candidate kind and association already selected by installed reservation/grant, with a retained canonical temporary buffer <=C. It is ephemeral host bookkeeping, not a new file, acceptance control, permission or public response. The returned host holds only ledger custody; no private page/record/count/progress is disclosed by connecting. A structurally eligible but physically damaged candidate may therefore reconnect successfully, but cannot be proved/cleaned/accepted. No supplied mode changes this fact and Resume cannot bypass it. Every dispatch rereads/revalidates shared grounds and the temporary before use; changed bytes/relationship refuse. A stored marker or earlier proof is never a substitute for revalidation.

While unresolved, normal decoding/wrong-dispatch/current ledger/selector/cursor authorization precedence still applies. After those gates, list/select/inspect, any unrelated accepted creation retry and any other new creation return only unavailable, with no pending or selected-member file access and no complete/empty page. They do not check pending member permission or opportunistically prove it. This deliberately narrows unrelated-member availability **only when a member-dependent shared remnant is unresolved**; ordinary pending/local A damage without that remnant retains B isolation. Closing/reopening merely reclassifies; it does not erase the constraint.

Only create_change for the key retained in the installed pending can proceed. Resolve it before any allocation, then check current ledger-create and that allocated member's create/history-disclosure scopes. Deny/unavailable returns the corresponding error before member access; same key with changed full typed input conflicts after these permissions, with no member access/cleanup. For exact input:

1. Reread the valid installed shared control and same canonical candidate, recheck complete pending feasibility and acquire only the reserved member lock in ledger → member order.
2. For ready proof, validate the reserved grant, installed member anchor and actual directory/lock tuple, clear member incident, exact initial zero checkpoint with pending null and empty trace. They must equal the candidate's physical tuple. For acceptance proof, validate installed ready tuple/member anchor, clear member incident, installed generation-one checkpoint and exact complete deterministic origin with no unexplained suffix; compare every field/input/original actor/result and the entire derived association to the temporary. Known member remnants need their own full relationships proved in place; never clean/provision/append merely to make this proof pass.
3. Missing/contradictory/damaged member grounds, blocked incident, unexplained member remnant or failed proof → unavailable, preserve shared temporary/reservation; deterministic refusal writes no incident. Genuine member I/O/barrier failure latches/retains member incident; a shared proof-read/root/barrier fault latches/retains shared incident. Either discards response and leaves proof unresolved. There is no implicit approval, alternate identity or automatic reconciliation.
4. Synchronize/revalidate the required shared/member proof grounds and repeat current ledger-create/member-create/history-disclosure permissions before cleanup. Denied/unavailable proof permission leaves the remnant untouched. Unlink only the proved creation.tmp, synchronize ledger root and revalidate the installed shared control/member grounds; no promotion, rename-to-authority or retained-response delivery. Clear unresolved bookkeeping only after this successful cleanup/revalidation. Failure keeps unavailable with the prescribed scope's incident attempt.
5. Resume the ordinary exact creation sequence from **installed** reserved/ready/member state. Ready proof writes ready afresh before any origin; acceptance proof reuses the already selected original without another append, then writes the accepted shared association afresh. Finish all ordinary acceptance/delivery barriers, fresh validation and final permissions; lost/denied response cannot roll back acceptance or change original actor/result. No new grant allocation occurs.

Every proof member pass/read/hash/decode/comparison/construction/cleanup/retention is charged to this create dispatcher, never connect. The deferred prefix uses at most four shared passes (dispatch classification, proof reread, pre-cleanup verification and post-cleanup verification) and three member passes (initial full proof, barrier revalidation and post-cleanup revalidation), including failed/partially reached passes. These are included, not added above create's S<=16/M<=16 complete-call ceilings; the remaining ordinary same-member sequence shares that finite budget. Known member-remnant proof is charged within those passes/extra-control allowance; no repair/retry loop is introduced. Unresolved ordinary read refusals charge shared structural revalidation only (M=0), not a hidden pending scan. Proven shared-equal/reservation remnants remain untouched by successful reads. A process exit before cleanup repeats full reconnect/proof; after cleanup it follows installed ordinary recovery, without requiring a persisted marker.

Member checkpoint.tmp relationships are exactly installed-equal, feasible zero→pending reservation (empty trace), or exact pending→one accepted successor (complete deterministic suffix). Cleanup is only during exact original creation retry, after installed member/shared-pending feasibility validation; unlink/sync/revalidate, never promote. Reads of accepted members may prove installed-equal temporaries without removing them; other checkpoint successors cannot exist under a valid accepted association. Initial-only anchor rules remain distinct. Any incident temporary is refusal, not a known harmless replacement.

Interruption before proven unlink repeats proof; after unlink but before parent sync, absence is synchronized before mutation, or a surviving remnant is re-proved; after cleanup sync normal same-identity processing resumes. A newly torn temporary refuses. Cleanup failure follows incident retention. Limits on lost observations/rollback still apply.

## Authorization, error precedence and non-disclosure

`LedgerGuard` is trusted composition, not request fields. It supplies authenticated principal and current Allow/Deny/Unavailable decisions for ledger connect/create/list, and member create/metadata/history disclosure. Selection needs metadata and history permission; inspection/accepted creation retry needs history disclosure; creation needs create plus disclosure. They are distinct independently established scopes, not consequences of Workspace membership or collection permission. The single-owner fixture may deny individual Changes without implementing collaboration. Policy stays valid through each serialized call and is checked again at delivery; do not use a cached permission Boolean.

Evaluate in this order:

1. Bound/decode/end-check full closed input. Invalid shape/pair is invalid_input; valid wrong dispatcher unsupported. Neither does private lookup.
2. Current principal/ledger/Workspace/operation guard: unavailable → unavailable, deny/wrong principal/wrong association → denied. For select/inspect, check member permission on supplied selector before existence/path lookup. For cursor, validate parent association/limit and current metadata/history disclosure of its `after` selector before private cursor lookup. Foreign ledger/Workspace cursor → denied; parent/cursor limit mismatch → invalid_input. Association checks use supplied values, not private lookup.
3. Validate shared custody/control/incidents and known inventory; structurally classify creation.tmp without member access. Missing/contradictory shared control or unknown global inventory → unavailable. An unresolved ready/acceptance proof permits only the exact-pending-key create preflight/proof path; other dispatches return unavailable before private member lookup/reads. Otherwise member existence resolves only within installed accepted entries. An authorized absent selection/cursor → unavailable, never a private not-found result for a denied selector.
4. Create: accepted-key resolution then pending-key resolution before capacity/allocation, with the unresolved-proof gate taking precedence over unrelated accepted delivery. Check the resolved member's current required permissions before member access. Accepted exact input/result delivery requires full member integrity and typed equality; changed input conflicts only after these gates. Pending same key changed input conflicts after its current member authorization; exact may prove/clean/complete through the specified path, another new key unavailable. A genuinely new otherwise valid request at 16 entries is unsupported before reservation; installed pending at capacity is damage/unavailable.
5. Select/inspect: validate required member's complete acceptance conjunction/prefix; incident/damage/competing writer → unavailable. Bounded accepted suffix is historical disclosure with blocked progress, not damage to accepted origin. List uses the all-or-nothing authorized validation rules below.
6. Barriers and fresh shared/member validation precede acceptance-bearing private delivery. Any required final authorization unavailable → unavailable; any final denial/revocation → denied, discard entire private response. Delivery/storage cut failure → unavailable and incident path where applicable. Commit remains committed.

Errors retain the existing envelope `{"v":1,"kind":"error","code":"invalid_input"}` plus LF; other codes are denied/conflict/unavailable/unsupported. They are not accepted lifecycle results, not proof of absence/nonacceptance and contain no member/key/path/count/details. A list denial of one member is an exclusion; unavailable is never treated as denial. Timing/work observations are trusted-fixture diagnostics, not client result fields or a side-channel-resistance claim.

## Authorized working-set pages and cursors

Order is ascending bytewise ASCII `change`, independent of physical slot/allocation order. Each call scans **all at most 16 installed accepted associations**, checks current per-member metadata/history disclosure and validates every currently permitted member's complete accepted origin, even members outside the returned page. Denied members are excluded without opening their private member files or returning their identities/counts. If any required member authorization is unavailable, or any permitted member's required custody/accepted grounds cannot validate, the entire page is unavailable; no partial page, error entry or false complete result. Reserved/unaccepted pending members are never included. Unknown/contradictory shared inventory is not silently ignored.

An unresolved member-dependent shared creation.tmp proof makes the entire list unavailable before any member scan, not an empty/complete working set, even if its pending member would otherwise be excluded. List cannot supply that proof or cleanup.

List does not decode long histories: this fresh fixture has one origin/member and a bounded sequential scan. It deliberately pays full permitted-origin validation cost, not an unmeasured metadata cache. Member damage A may prevent listing when A is permitted; selection/inspection of intact authorized B remains supported. If A is denied, its private damage is neither accessed nor reported. Missing A controls never erase its accepted association or retry obligation.

List result has ordered fields `v,kind,ledger,workspace_id,members,next,coverage`; kind is `changes`. Each returned member M is exactly ordered:

```text
{"change":C,"origin":C+":origin","actor":<original actor>,"accepted":{"first":1,"last":1,"sha256":<origin digest>},"progress":<"ready" or "blocked_unaccepted_tail">}
```

Only identity/provenance/accepted coverage/readiness needed to choose an inspection is returned: no What/Why, physical path, custody, key or hidden count. Metadata is selected from validated original record/control agreement, never independently writable metadata. Limit bounds `members.len()` to 1–4, except an empty terminal page is valid. `next` is required null or the exact cursor shape from the request example, with `after` equal to the last returned disclosed Change and limit equal to this request. Emit next only if a further currently permitted validated Change exists; no cursor for an empty/terminal page. No private ordinal, allocation/control generation, global digest, total count, denied identity or pending existence is exposed.

After the two sample creations, with both members currently permitted and intact, the first limit-one page is exactly the following plus terminal LF. The shown digest is SHA-256 of the documented A origin's 496 LF-inclusive bytes, not a fabricated acceptance receipt:

```json
{"v":4,"kind":"changes","ledger":"ledger-1","workspace_id":"workspace-1","members":[{"change":"change-a","origin":"change-a:origin","actor":"owner-1","accepted":{"first":1,"last":1,"sha256":"caf5870bfa76cb94b8e7a380a5e530468272f73a1950740dfbab66e2d0e93b6f"},"progress":"ready"}],"next":{"v":4,"ledger":"ledger-1","workspace_id":"workspace-1","after":"change-a","limit":1},"coverage":{"interpretation":"ck-ledger-page@1","scope":"currently_permitted_after_cursor","complete":true}}
```

Coverage is exactly `{"interpretation":"ck-ledger-page@1","scope":"currently_permitted_after_cursor","complete":true}`. Complete means every installed accepted association's required permission was resolved and every currently permitted member validated for this serialized call; the returned page is the first limit permitted Changes strictly after the cursor (or from the beginning). It does not say all permitted Changes are returned, that none were denied or that pages form a cross-call snapshot. Presence of next refers only to further **disclosable** entries. Unavailable never emits this coverage.

Cursor is a bounded **keyset selector, not a capability, opaque authentication token or stored snapshot**. All its fields are required/nonnullable; `after` uses the opaque Change grammar. A valid cursor must match current ledger/Workspace/parent limit, currently permit disclosure of its after member and resolve an installed accepted member. Forging a cursor grants no authority; choosing another currently authorized after member is a supported seek. Reusing with another page limit is invalid_input; foreign associations denied; now-denied after member denied; absent after member unavailable. Copying a cursor/page/Trace confers no custody/permission. No unconsumed MAC, secret, persistent cursor table or replay cache is introduced.

Within a call the permanent ledger lock plus trusted custody excludes cooperative mutation. Before delivery, repeat current guards for collection, cursor and **all 16 candidate associations**, not only returned entries; freeze that current guard lease through delivery. An allowed membership/disclosure decision changed to deny suppresses the constructed response as denied instead of returning a newly inconsistent page; any unavailable decision suppresses as unavailable. A previously denied decision becoming allow also suppresses as unavailable because that newly permitted member has not been validated for this response; retry from a fresh call, without an internal rescan loop. Stable denial remains exclusion. Fresh validation/barriers cover every permitted member again sequentially, then final shared validation/guard and delivery. Do not retain one descriptor/origin buffer per member. There is no cross-file atomic snapshot claim outside these trusted/excluded-writer conditions.

Between pages creation is allowed only by another host after the predecessor releases custody/exits as required. A new permitted Change sorting after cursor may appear on the next page; one sorting at/before cursor is omitted from this traversal and appears after restarting with cursor null. No duplicates of unchanged identities arise from keyset order. Denial/revocation/damage can make later pages smaller, unavailable or denied under the rules above. A revoked cursor anchor is denied even if other members remain allowed; restart from null under new authority. Restart alone does not invalidate a still-authorized cursor. No generation-staleness check is claimed. A returned terminal page means termination for that call's permitted set, not that later creation cannot occur. This explicit live-pagination interpretation replaces any implied snapshot/completeness promise across mutations.

## Finite capacities and complete-call work contract

These are selected implementation ceilings, **not observations**. Let C=1,048,576, T=2,097,152, Q=2,097,152, L=65,536. Every request/result/origin/control including LF is <=C, every member's total trace including unaccepted suffix <=T, one selected origin <=C, inspection <=Q, list/selection <=L. What/Why bounds remain 65,536 each. Ledger has at most 16 non-recyclable accepted/reserved slots and at most one pending; page limit 1–4. Canonical length feasibility, including full shared control with prospective entry/pending, is checked before any reservation/replacement. Equality with all capacities is permitted; overflow of new otherwise admissible creation is unsupported before reservation; oversized retained bytes/invalid pending is unavailable and preserved. The finite text/grant/schema limits fit shared C; no growth knob or eviction is provided.

Every bounded file read checks regular/no-follow identity and length, uses a limit+1 refusal sentinel at most, and stops on overflow. No unbounded I/O retry, directory recursion, rescan-until-stable loop, authorization loop or implicit restoration is allowed. Known temporary cleanup is at most one per control/anchor per call; a subsequent unexplained temporary refuses. Inventory entry visits include the first refused name: ledger root <=7, members parent <=34, one member <=7, external configured anchor siblings by direct named lookup only. Stop immediately on unknown/extra names. Linux NAME_MAX bounds a refused directory name to 255 bytes; this is not an input text buffer allowance.

For **one entire dispatcher call**, including failed attempts, cleanup, discarded reply/error emission and incident retention, choose conservative common ceilings:

| Work category | Ceiling / interpretation |
| --- | --- |
| Shared validation passes S | <=16. Count entry even if refusal precedes all controls; ordinary read normally two plus final shared verification, creation adds each reservation/ready/acceptance verification and permitted cleanup. No cached validation replaces a pass. |
| Member validation passes M | <=64 total across all members, not 64/member. List ordinarily two sequential sweeps of at most 16; create/select/inspect/retry operate on one member with at most 16 passes including provisioning, deferred physical/origin proof, proof barriers/revalidation, cleanup and delivery. Unresolved ordinary-dispatch refusal has M=0. No pending-member proof work occurs in connect. |
| Buffered bytes read | <=S*4*(C+1)+M*(4*(C+1)+(T+1))+32*(C+1). Shared pass reads anchor, incident, creation and optional temp; member pass reads anchor, incident, checkpoint, optional temp and trace. Incident.tmp takes the refusal branch instead of continuing. The 32-control allowance covers initial/provisioning/remnant/installed-reservation/retention reads outside passes; never hide them in connect. |
| Trace read / accepted hash | <=M*(T+1) buffered trace bytes; <=M*C accepted hash bytes plus <=32*C canonical input/candidate/temp-extension hash bytes outside selected-prefix hashing. Suffix is not hashed as accepted without a proved candidate relationship. |
| Decode/re-emission attempts | Ingress <=1; member origin <=M; shared/member controls <=4*S+4*M+32; sum <=1+4*S+5*M+32. An invalid shape/refused control may complete fewer. Requests are not reparsed per member. |
| Domain/record/control construction attempts | <=256 per call, including pending/candidate reconstruction, canonical feasible control/result, incident attempt and rejected construction. Selected records are not repeatedly emitted solely to measure comparisons. |
| Association/key work | Per shared pass at most 120 entry-pair uniqueness comparisons, 16 entry/pending key predicates and 16 lookup/selector predicates; outside passes <=512 such predicates, including cursor and new-key/allocation checks. | Canonical / semantic / physical / schema comparisons | Canonical object equality <=4*S+5*M+32; record semantic equality <=M+32; pending/temp whole-control relationships <=16*S+16*M+64. Small fixed-field/map/presence/physical predicates <=512*(1+4*S+5*M+32+256). Fixed field schemas include bounded arrays; duplicate masks are per declared element, not an arbitrary map. Unknown member name is bounded by ingress/control C, not a presumed small literal. Publish reached boundaries, not inferred equality counts from codec completions. |

Validate sequentially; release member/key/temp buffers before another member/pass. Headers/fixed structs/hash state/descriptor tables/stack are separately observed, not claimed RSS. Connection is separately bounded and reported: S<=16, M=0 (shared-only connect), buffered reads <=4*S*(C+1)+32*(C+1), control decode/re-emission attempts <=4*S+32, and <=32 additional initial/control/anchor/incident reads/constructions. Inventory limits and the same 64-MiB named-payload ceiling include the retained deferred buffer, failed connection/host disposal, guard refusal and at most one bounded shared incident-retention attempt. No member origin/anchor/checkpoint/incident/lock is accessed. Deferred proof and pending-member creation occur only in the exact create call, within its M<=16 and existing whole-call ceilings, not hidden in connect or charged a second time as connection work. Ordinary unresolved dispatches revalidate shared shape within their S bound and use M=0. Failed authorization/malformed request also falls within complete-call observations, with zero private work if refused before custody. Incident retention for an observed read/barrier fault is included in the existing 32-control allowance, construction/read/codec/comparison counts and simultaneous capacities; there is at most one nonrecursive attempt, not an unbounded failure loop.

Comparison observations distinguish attempts/completions/outcomes from codecs/constructions. Publish conservative one-sided operand charges: byte equality max operand length; typed equality max sum of operand string/byte payload lengths, plus fixed schema/scalar words; suffix-prefix proof only the guarded compared range. For malformed huge member names charge available bounded name lengths/candidate ranges, not a small-name assumption. These are available operand ranges, not actually scanned bytes, machine instructions, RSS or disk traffic. Preserve R25's accounting meanings without relabeling its totals as ledger performance. Observe logical groups at concrete reached sites and fixed counter overhead without extra scans/emissions merely to count. If selected bounds cannot hold, report before changing them.
