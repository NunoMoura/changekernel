# Guarded Effect Validation Fixture

**Adopted source contract, not runtime qualification.** Implementation/qualification state lives in the temporary status note and Git. Profile **`ck-ledger-notice-effect@7`**, JSON `v:7`, consumes the user-selected [SQLite validation resource](../../product/plan.md#guarded-effect-validation-fixture). SQLite retains application State/policy/native receipts, never Change history. JSONL alone retains adopted intent/operation/Check grounds, attributable attempt, uncertainty and actual outcome. No repository publication, model call, scheduler, generic adapter framework, migration or controller authority is selected.

## Fresh composition and unchanged contracts

Use fresh ledger/member custody and a fresh resource. Incorporate v6 [independent grants/native opening](ledger-continuity.md), v5 [closed ingress, canonical records, accepted-prefix/retry protocol and Views](ledger-history.md) by reference, with JSON version 7 only in this new composition. Old profiles remain unchanged and reject this surface. All seven inherited operations keep their existing meanings; `run_check` remains the old fixed Check and does not approve a notice effect.

The new format family is `ck-ledger-notice-effect` with exact suffixes `@7`, `-anchor@7`, `-creations@7`, `-member-anchor@7`, `-member-prefix@7`, `-incident@7`, `-member-incident@7` corresponding to v6's seven format roles. Shared anchor/creations and member anchor append required final field `notice:NoticeBinding` to their inherited ordered shape. Other control fields/barriers/incident meanings remain unchanged except the v7 member-pending observation field defined below. `NoticeBinding` is exactly `installation:Hex,resource:Id,resource_subject:Hex,effect_change:Id` and must equal the independently installed binding. There is no import of a v6 anchor or old SQLite profile.

One resource is bound once to one physical ledger and one **effect-eligible Change** named by trusted installation. Other Changes retain inherited operations; notice ingress for them is denied. The one-pending rule is **resource-global**, not per caller/key; this deliberately narrow scope makes its authoritative derivation the eligible Change's validated Trace, not a second reservation database. More than one unsettled core attempt is damaged custody. A trusted application-native writer can still change the resource at its own conditional revision under the installed native boundary; that is not another core attempt or Change history. New eligible-Change mutations other than that attempt's uncertainty/outcome (including revise_intent/run_check/prepare) and another application key are refused until settlement; exact already accepted replay remains read-only; native grant changes remain possible between calls. A historical Check/outcome does not become current authority.

## Closed types and exact new shapes

All tables give ordered, required fields. No omitted/unknown/duplicate fields, implicit defaults, nullable substitute for absence, text normalization or caller-created evidence. Ingress may reorder JSON members/spelling; retries compare decoded values. Retained/output bytes use the inherited compact formatter, unsigned minimal decimals, lowercase `\u00xx` for every control, required quote/backslash escaping, unescaped solidus and one LF. Nullable fields below always appear.

The short type names below describe wire values. The deterministic Check's precedence is: text length >80 → `passed:false,feedback:"value_limit"`; expected revision differs from observation → `revision_mismatch`; observed revision is maximum → `revision_exhausted`; otherwise `passed:true,feedback:"passed"`. They are backend-only shapes, rejected as public ingress. Their result key/actor come from the original application, not a new caller. Sequential validation reconstructs preparation/Check, current preparation head, attempt identity/reservation and phase/result correspondence. Attempt Operation must equal the prepared revision/text and recomputed scoped key; scope must match installed NoticeBinding and proved ledger/member subjects. Receipt Operation/actor must match that attempt; applied requires revision=expected+1 and text=proposed, guard_conflict requires revision!=expected. It does not promote arbitrary JSON or native receipts to accepted facts. Native outcome authenticity additionally requires the installed original-owner proof/lookup.

### Preparation reservation and recovery

V7 member checkpoint keeps the inherited outer fields `format,custody,change,generation,end,sha256,pending`. Its non-null member `pending` is exactly the ordered shape `input,actor,observation`. `input` is the complete reserved request and `actor` is independently established `owner-1`. The required `observation` is an `Observation` object if and only if `input.op` is `prepare_notice`; for every other member reservation it is required null. Missing, extra, duplicate, wrong-kind or malformed evidence is damage, not permission to observe again. Shared creation reservations are unchanged. V1–v6 retain their original pending shape and reject this new field; no old decoder or serializer is widened.

For a genuinely new preparation, the trusted producer obtains one bounded Observation from a successful healthy-owner committed read under the installation lease and current disclosure/PrepareNotice authority. It preflights the complete canonical candidate and control, then durably reserves that exact input, actor and Observation before any candidate append. All subsequent candidate construction, suffix comparison and acceptance use the installed pending Observation, not a fresh native sample or an in-memory-only cache. The ordinary record's input remains the complete public preparation ingress; its result contains that same historical Observation and the deterministically reconstructed Check. No new public ingress field, internal preparation input, sidecar reservation store or full native snapshot is introduced. Clearing pending accompanies acceptance of that exact fact, never loss of its evidence.

Pending feasibility reconstructs the candidate from the accepted prefix, installed binding and complete reservation, including its historical Observation. The physical suffix may be empty or any exact byte-prefix of that candidate, including a prefix ending before the observation bytes. A mismatching suffix refuses; it is never truncated or rewritten. Same-installation engine reopen validates without appending, and only an exact currently authorized mutation retry can finish the reserved candidate under the inherited barriers. Current native custody, healthy-owner proof and rights are still required. A supported native writer or policy update may have advanced the snapshot from S1 to S2 between calls: that does not replace S1, change the historical Check or invalidate the reservation merely because its digest/count/Notice differs from S2. A later application still uses current authority and native CAS; this historical observation is not proof of current freshness, permission, committed effect or absence.

Known temporaries retain the inherited selection and cleanup rules. Prove a prospective reservation temporary using its own Observation before any authorized cleanup; because it was never installed, its removal does not accept that observation, and a new normal reservation may take a new verified sample. Equal installed-control and exact accepted-successor temporaries must agree with the installed reservation's full evidence/candidate. Reads and reopen do not clean or publish. An I/O incident, quarantine or failed custody proof still blocks; the added field does not authorize incident repair or whole-process Owner reconstruction. Internal uncertainty/outcome inputs already retain their typed cause/receipt/absence and keep their specified native-evidence revalidation rules.

The pending Observation is bounded by the existing 4,096-byte single-evidence cap; the complete member control remains bounded by C. Account its actual normalized capacities and overlaps with input, candidate, parsed control and native evidence, including failed/discarded work. No accepted-record count, Trace byte cap, native snapshot cap or effect-slot reservation increases. Preparation interruption tests must retain the original candidate across empty, partial-before-observation and complete unaccepted suffixes after a native writer/policy change; malformed or suffix-inconsistent evidence must refuse. These are acceptance-control cuts with the same held installation, not claimed process-crash or reboot qualification.

### Result delivery and Views

Success delivers the exact accepted preparation or final outcome result. Nonfinal proved absence delivers exactly `v:7,kind:"notice_pending",ledger:Id,workspace_id:Id,change:Id,key:Id,attempt:Ref,state:"no_committed_effect",uncertainty:Ref|null,absence:Absence,accepted:Prefix`; `Prefix` is the inherited View prefix `first:u64,last:u64,end:u64,sha256:Hex`, not the mutable member control containing pending input. Unknowns return the generic v7 error envelope, never invented after-State/private details. Codes remain `invalid_input,unsupported,denied,conflict,unavailable`; an error is not a final lifecycle fact or rollback proof.

History returns complete accepted new facts under inherited pagination. Context appends field `notice` exactly `{resource:Id,prepared:Ref|null,adoption_current:bool,attempt:Ref|null,uncertainty:Ref|null,outcome:Ref|null,status:<none|prepared_false|prepared_true|pending|unresolved|applied|guard_conflict|not_applied>}`. At the selected cursor, prepared is the latest preparation; attempt is the latest attempt for that preparation, and uncertainty/outcome belong only to that attempt. Null preparation means status none; otherwise choose its latest outcome status, else unresolved if uncertainty exists, else pending if attempt exists, else prepared_true/false. adoption_current compares that preparation with the live preparation head, live-tip intent and installed policy. It is **not** native freshness, permission or execution eligibility. Receipt Notice is the actual result at its recorded revision, not current State after later writes. Effect-eligible history/context/result delivery also needs current native disclosure rights.

## Identity bound to original physical subjects

Define `H(domain,args...)` as lowercase SHA-256 of each argument **including domain**, framed in order as unsigned 64-bit little-endian byte length then those bytes. Strings use UTF-8; numbers used below use minimal unsigned decimal ASCII; native identity objects use inherited canonical JSON without LF. These domains and argument orders are exact:

| Digest | Domain and ordered arguments |
| --- | --- |
| `ledger_subject` | `changekernel.fixture-notice.ledger-subject@7`; original proved ledger-directory, ledger-lock, members-directory native identity objects. |
| `member_subject` | `changekernel.fixture-notice.member-subject@7`; ledger_subject, member custody Id, Change Id, original proved member-directory and member-lock identity objects. |
| `resource_subject` | `changekernel.fixture-notice.resource-subject@7`; installation, resource Id, original parent dev/ino, resource-directory dev/ino, raw DB pin dev/ino, owner-lock dev/ino. These are observed `u64` components, not ingress labels. |
| Native `Operation.key` | `changekernel.fixture-notice.operation@7`; installation, resource_subject, ledger_subject, member_subject, ledger Id, Workspace Id, Change Id, application key, accepted attempt Ref. |

`installation` is a nonzero 32-byte OS-random provisioning nonce encoded as Hex, issued once by the trusted fresh-owner factory, held independently of DB bytes; one Linux getrandom attempt with GRND_NONBLOCK must return exactly32 nonzero-as-a-whole bytes; errno/short/all-zero failure refuses without fallback or retry. It is **not** original-custody proof by itself. A supplied/copied UUID or hash cannot mint an installation. The immutable held-native binding plus proved ledger/member tokens bind reused printable labels to distinct physical subjects. The stable operation key deliberately does not change for changed payload/actor under the attempt: the native receipt's exact Operation/actor comparison then conflicts, while the engine rejects changed application input before invocation. The accepted preparation binds every other exact intent/Check/policy/value field. Never regenerate an attempt reference or rehash against a replacement baseline on retry.

## Original owner and native proof limits

Consume the reviewed primitive at `dbb35e0b22e2f10403f4db90e8b2e75ef8f27b58`, not an imagined richer receipt/settlement service. Its raw parent/directory/DB/writer descriptors, flock, named `fstatat` bindings and exact successful-commit SQL snapshot prove **held-owner** custody. Pin the raw DB before opening SQLite; keep it until all SQLite sessions close. All sessions may be dropped and later reopened while this original Owner/snapshot/pins remain. There is no required keeper SQLite connection. Closing auxiliary DB fds while SQLite is live can cancel POSIX locks; proof uses metadata/pinned reads, never repeated raw DB opens/closes. No aliases, replacement, fork-inherited connections, direct file/SQL mutation or hostile same-UID/rollback resistance is claimed.

Provisioning adopts fixed protected fixture-lifetime retention: exact observations/Check grounds and native receipts are retained without pruning/eviction; actor read denial withholds delivery, not the service's protected baseline. Required purge/expiry/sharing policies are unsupported here. All access is actual unprivileged SQLite/VFS access; transactional application-grant revocation does not pretend chmod revokes an already-open fd.

Completeness is a bounded scan of **one Notice, four policies and up to32 receipts**, equality with the owner's exact last successful-commit snapshot, plus native namespace proof; it is not an indexed single-row proof. Its snapshot_sha256 is plain SHA-256 of canonical ordered `notice:Notice,policies:[{actor,read,edit,admin}],receipts:[Receipt]` **without LF**, actors/keys ascending ASCII. `Observation`/`Absence` expose its digest/count, not the full private snapshot or a caller bool. Absence is valid only after successful healthy-owner committed lookup with no live transaction/in-flight operation. A missing previously retained receipt or changed snapshot quarantines/refuses; it never becomes an ordinary miss.

Observe/lookup/disclosure use actual READ_ONLY/NOFOLLOW SQLite sessions; invocation/admin updates use READ_WRITE/NOFOLLOW, never CREATE on reopen. Original-result lookup does not require write-mode access. DELETE/EXTRA is configured/read back; native wait is **0 ms** and there is no retry loop. Native CAS and exact receipt commit together; checked row count distinguishes applied from guard conflict. Even equal text needs a real revision advancement. Positive revisions never wrap/reuse; receipt capacity is32. All supported native writer text/result values may reach256 bytes, including competing writers, even though the core proposed-text Check permits only80.

**Any COMMIT error permanently quarantines this Owner**, including a read/proof commit. There is no settlement/reset API in this slice; failed explicit rollback or damaged snapshot/custody also quarantines, not a rollback/absence proof. A row visible in that failed transaction is not committed evidence. Drop/rollback/another successful barrier cannot clear quarantine. Engine uncertainty stays blocked unless independent supported evidence exists; this proposal provides no such owner recovery. Native success with lost return or Trace failure is different: the healthy Owner updated its snapshot after successful COMMIT and can look up that exact receipt.

Needed additions to P's primitive are the installed lease/nonce/physical-subject bridge, bounded verified-view digest/absence witness and typed core/native result/error mapping. No before-value column, richer lifecycle receipt, indexed completeness shortcut or COMMIT-error settlement API is required. Whole-process resource-owner restart/reboot remains **unsupported**: original association, independent native identities, retention policy and complete snapshot would need separately consumed persistent proof. SQLite/Trace bytes or process `dev/ino` alone cannot restore it.

## Executable transitions and refusal precedence

An attempt is pending until an accepted outcome. One first uncertainty fact consumes one reserved slot; it is not final. Generic denial/conflict/unavailable errors never close an attempt. Only applied/conflict receipt settlement or explicit `close_if_absent:true` with proved absence produces a final outcome and releases its reservation. Permanent native quarantine may therefore leave the resource blocked indefinitely; no new key conceals that state.

| Accepted state + native proof | Application retry | Reconciliation | Reservation/result |
| --- | --- | --- | --- |
| No attempt | Require Invoke/Settle, current native read/edit, passing applicable preparation and capacity; durably accept attempt, then invoke. | Well-formed missing/wrong-kind attempt reference → conflict; foreign reference → denied. | Reserve global resource and three fact slots/bytes before invocation. Pre-attempt denial/failure creates no attempt/reservation. |
| Pending + exact committed receipt | Require current History/native read and Settle; append actual outcome, **no edit/Invoke grant needed**. | Same; close_if_absent ignored because receipt wins. | Final immutable applied/conflict result; release reservation only after durable accepted outcome. |
| Pending + proved absence | Require current Invoke/Settle/native edit and still-current preparation, then invoke the **same** Operation. Current denial returns denied; stale grounds conflict; no invocation/final fact. | False → nonfinal notice_pending; true + Settle → final not_applied with Absence, no edit/Invoke/current preparation required. | False/denial/staleness keeps reservation. True releases it only after accepted final fact; later original-key application delivers not_applied and never invokes. |
| Pending + busy/capacity/denial before mutation | Revalidate original lookup before any next invocation. Never interpret the error as a final no-effect result. | Healthy authoritative absence can observe/close as above. | Generic error; record first uncertainty if authorized/durable; remain reserved. A granted retry still checks current rights. |
| Pending + unknown COMMIT/quarantined/missing custody/receipt evidence | Unavailable, no invocation. Current edit denial cannot downgrade the earlier unknown into not_applied. | Unavailable, even with close_if_absent true. | Retain first uncertainty where safe; preserve attempt/reservation/live refusal. No cleanup/reenrollment/reset. |
| Accepted final outcome | Exact original-result delivery under History/current native read; no new fact, edit grant or effect. | Same result under disclosure rights. | Already released logically. Lost custody/required native evidence still refuses delivery; never erases the final fact or reexecutes. |

Preparation needs PrepareNotice plus current native read, not native edit. New application/absence continuation needs InvokeNotice and SettleNotice plus native read/edit. Retaining a found outcome or explicitly closing proved absence needs SettleNotice and native read, not InvokeNotice/edit. Already accepted result delivery needs only current disclosure rights. These gates are held, not reinterpreted as a final result when denied.

Named precedence for a call is:

1. Public input marker/closed JSON/type/version/reference grammar failure → invalid_input; decoded known operation passed to the wrong named method → unsupported. Foreign Change/resource scope → denied before private lookup.
2. Acquire installation lease (failed/reentrant borrow → unavailable), authenticate fixed principal and current Connect/History scope → denied or unavailable before private delivery.
3. Prove original core custody, incident state and accepted/pending prefix/lineage, plus native custody for notice operations/effect-bound Views. Damage/quarantine/contradiction → unavailable. Read current native disclosure policy only under that proof; denial → denied. No historical result bypasses it.
4. Resolve original preparation/application key: changed complete input → conflict. Accepted final outcome requires its exact retained native receipt/absence and valid current proof; missing/changed evidence → unavailable, not a miss. A historical absence digest/count need not equal today's changed snapshot: current healthy lookup must still prove that Operation absent; a later receipt for a closed not_applied attempt contradicts it. A native key collision with different exact input is conflict only for a new unaccepted invocation; contradiction to an already accepted attempt/receipt is unavailable.
5. Pending original attempt: committed receipt lookup precedes current edit/Invoke/freshness/capacity. Outcome append needs Settle. Authoritative absence takes the transition table; unproved absence/unknown wins as unavailable over later edit denial. A different application key while pending → conflict.
6. New prepare/apply or explicit absence continuation: require current mutation capabilities/native edit where applicable **before** revealing freshness/capacity details. Stale/false preparation or blocked eligible-Change mutation → conflict; native/Trace quota exhaustion → unavailable; native contention → unavailable. Check false is an accepted preparation result, not a refusal or effect.

Before native invocation, finish only the exact feasible reserved acceptance step under inherited pending/barrier rules; unrelated acceptance pending/unaccepted tails block invocation. Internal outcome pending must revalidate its matching native evidence before completion. History/context/reopen never append or invoke. A Trace I/O incident stays blocked: native receipt cannot clear it. Native commit then Trace failure retains a healthy original receipt and unresolved attempt, not invented rollback.
