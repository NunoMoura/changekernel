# State and Persistence

A **Workspace** is the persistent subject; **State** is its scoped, version-/time-bound representation. Native values, adopted obligations and supported knowledge have distinct owners and meanings, with relevant gaps, conflicts and unknowns explicit. An observed State, a desired State and a proposed candidate are not interchangeable. Authoritative source content does not make every assertion verified reality, and a desired outcome does not establish fulfillment. State is transitory in what it represents, not necessarily ephemeral in storage: retained observations remain evidence. No universal giant snapshot, Markdown representation or duplicate current-state database is required.

A Workspace may have many representations over time, coverage and authorized visibility; each belongs to that Workspace. A Change can reference many observations and intermediate results, and can exist before complete before/after representations are known. Failure or uncertainty must not become an invented after-State. The [primary design](../../product/changekernel.md#relationship-cardinalities) owns the complete cardinality model.

## One authoritative current representation

Existing application rows, files and service resources remain authoritative in place. Qualified bindings expose observation, identity/version checks, preparation, publication, outcome lookup and supported recovery. File-first Change history does not require file-only application State or copies of native rows. If a generic representation is needed where no native resource supplies the meaning, settle that capability's storage/identity contract before promising it; never create a second independently writable owner of an existing entity.

The default working cache is bounded and in memory, holding request-relevant entities, relationships and constraints obtained through authorized native bindings rather than an application mirror. Hypothesized concepts remain distinct from observed native resources. Reuse structure/operation metadata only within compatible source/version and visibility boundaries; multiple users' activity does not make private records or requests shared knowledge. Cache eviction is allowed only when it does not erase required grounds: retain what decisions and continuation rely on through qualified native history or Trace custody, and recheck what actions depend on.

[Compiled binding definitions](../../product/changekernel.md#discovery-and-bindings) are versioned application integration/build artifacts, not a second independently writable entity database or a grant of native authority. Retain the exact definition used where historical interpretation or continuation depends on it, through qualified application/release history or Trace-referenced custody. Record its exact reference with dependent decisions and Work. Recompilation, especially semantic regeneration, cannot substitute new meaning for a missing historical definition. Current compatibility, native permissions and source guards remain runtime obligations; credentials and private live records are not classifier catalogue contents.

Workspace setup exposes bounded resources/operations under established native authority. Tracking is not write permission, read-only dependencies can constrain effects, and a creation boundary can cover future resources without enumerating every filename. Discovering a resource, copying configuration or identifying a file does not adopt its assertions or grant retention, disclosure, mutation or deployment rights. Observe relevant scope on demand rather than loading every accessible resource.

Identity includes native source, scope and resource identity, with version and locator recorded separately. Same-name recreation may be a different resource according to the binding's declared semantics. Relocation cannot guess continuity; uncertain mappings require explicit rebinding and applicable reassessment. Different Workspace IDs do not isolate overlapping resources or create new budgets. Source/version/selection coverage, not filenames or hashes alone, determines what an observation establishes.

### Native authority and delegated access

Follow the [State-access and Change-authorization model](../../product/changekernel.md#state-access-and-change-authorization): reuse the source's existing permissions rather than create a second authoritative State ACL. For Linux files this includes actual ownership, modes, ACLs and applicable native security restrictions. Future Windows bindings use native access tokens/security descriptors and platform controls; future macOS bindings use native permissions/ACLs and platform protections. Do not flatten their different semantics into a copied cross-platform read/write Boolean or claim support before qualification. Non-file State continues to use its native application, database or service authority.

A binding distinguishes the actual resource, authenticated acting subject, requested native operation, relevant scope and current authorization result. These are contract responsibilities, not a frozen public record layout. State may retain an observation of access grounds with its context and time, but that observation cannot grant or permanently cache authority. Let the native operation enforce its actual rights under the qualified subject; do not replace that with `access()` followed by a differently privileged open, a mode-bit calculation or a service-side reopen. The trusted host must still establish whose native context is being used. A path, UID, source FD or client-generated result is not sufficient independent evidence.

Read, write, append, execute, create, rename, delete and permission changes are distinct native operations with platform-specific prerequisites. Writing need not require reading; deletion or replacement can depend on a parent directory rather than the target's write bit. Expose only supported operations and include every affected resource in scope. Disclosure, retained history and provider submission retain their own authorization even when local reading is possible. Native denial is never a request to retry through a more privileged source adapter.

The host derives a worker's maximum access from current native authority intersected with its Work delegation and applicable Change controls. The [Linux Rust Landlock direction](agent-execution.md#repository-contained-worker-sandbox-rust-landlock-direction) restricts the worker further; it does not edit repository ACLs, confer ownership or prove that all writes inside an allowed tree realize the intended transformation. Permission-policy changes are themselves guarded effects under the current rules, not a candidate's way to approve its own expansion.

At point of use, preserve the binding's native permission and revocation semantics. Already opened or transferred handles may remain usable after pathname permission changes; a startup ruleset or permission observation cannot promise immediate revocation of every in-flight operation. Revalidate current delegation and applicable guards before admission/publication/delivery, fence future work after withdrawal, and reconcile started effects under the declared source protocol. Any stronger revocation promise needs concrete enforcement and qualification. This clarification does not relax existing source-context, protected-custody or continuity requirements, and does not authorize a new authentication subject or privilege-changing helper.

### In-place source enrollment and continuity

The [ordinary-client host direction](agent-execution.md#ordinary-client-host-direction) prefers keeping repositories in their existing locations. Protecting custody directories and identifying application-source directories are different responsibilities: the former require an independently protected writer boundary; the latter require qualified native identity, scope and access. Do not infer a requirement to move every repository under administrator-owned parents from the custody requirement. Equally, retaining a pathname does not prove that its source stayed the same.

A candidate in-place binding keeps the approved native locator and exact repository topology in protected service controls, not in a user-writable marker claimed to authenticate itself. It identifies the native repository objects separately from their content/version and from the Workspace/Change IDs. The narrower identity route to assess is:

1. During explicit enrollment, a protected helper freshly opens the proposed source under the qualified native authority context. Establish source/ancestor and filesystem/mount-view identity before recording the binding. A client supplies a proposed locator, not an authenticated object or permission receipt. A linked Git worktree requires separate binding of the worktree, private Git directory and common object directory; matching `.git` text is not that identity proof.
2. For each later source-dependent operation, resolve the current locator afresh under current native permissions, compare the opened object and topology with the enrolled binding, then constrain the actual operation to those verified objects. A retained root FD is an identity anchor, not continuing authorization. A check followed by a pathname-based reopen can race and is not the protocol. Relative descriptor traversal must preserve the declared scope and native checks, including supported mount crossings, symlinks, ancestors and concurrent rename behavior.
3. Same-lifetime pinned object references can assist comparison without trusting a replaceable name. After restart/reboot, require a qualified persistent filesystem/object identity or an explicit supported continuity procedure. A candidate is a native file handle combined with authenticated persistent filesystem identity and current mount-view validation; neither inode numbers nor mount IDs alone suffice. Filesystem support, handle stability, stale/reused identities, copied filesystems and remounts must be qualified for the actual supported profile before selecting a descriptor grammar.
4. Replacement, unknown topology, stale identity or unproved continuity blocks dependent source work. Do not automatically enroll a same-path replacement, mint a new source identity during retry or rewrite immutable Change origin. An authenticated user choosing a new binding is not proof that the old object continued. Current private historical delivery and original-result reconciliation remain separately available only where their own accepted-prefix and disclosure grounds survive.

Linux [openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html) supplies constrained lookup, not a transaction holding a pathname tree fixed after return. [`name_to_handle_at(2)`](https://man7.org/linux/man-pages/man2/name_to_handle_at.2.html) documents filesystem-specific handles, stale-handle failure and the nonpersistent nature of mount IDs. These offer an identity candidate, not generic reboot continuity or rollback detection. `open_by_handle_at` requires `CAP_DAC_READ_SEARCH`; it must not replace a fresh authorized path open or turn the custody service into a source-permission proxy. An administrator's assertion, filesystem UUID, Git commit hash or copied descriptor alone cannot authenticate continuity against every replacement/restoration. Explicit restoration retains its separate recovery gate.

There is still a material distinction between **observation** and **guarded publication**. Capturing exact authorized objects/versions does not lock other writers out, preserve the current pathname meaning forever or make a multi-file effect atomic. Existing [committed-source observation](#native-committed-source-observations) requires host-protected topology for the duration of capture; adding a preliminary root check does not qualify its path-based subprocess access against mutable ancestors. A concrete descriptor-bound reader or qualified source guard is needed before claiming that support. Publication additionally needs serialization against relevant competing writes, exact expected targets, current native authority and outcome/reconciliation evidence. Without source cooperation, outside writes remain separately observed drift, not governed effects. If the eventual publication contract requires a protected target boundary or working arrangement, explain that specific cost rather than impose relocation on all observation/history operations.

Qualification must cover replacement by an equal-content repository; rename/symlink/mount races before and during actual reads; linked-worktree pointer substitution; parent search-permission withdrawal; stale descriptors after revocation; inode reuse; ordinary restart/reboot with unchanged source; unsupported filesystem handles; and explicit restore/clone. Missing mechanisms remain engineering blockers, not approval requests for a weakened guarantee. This is an in-place design candidate, not adoption of a handle codec, a new filesystem dependency, a changed observer contract or permission for privileged experiments.

## File-first Change Trace custody

The desired lifecycle authority is **one append-only JSONL Change Trace log per Change** in protected, authenticated user-bound custody. Each bounded typed line records one operation. Retain original and revised intent, exact Kernel/Check/plan references, assessments, Work, attempts, failures, decisions and actual outcomes with attributable actors. A proposed or attempted operation is not a receipt for its effects. Large artifacts, prior values and private runtime transcripts may be referenced rather than embedded in every record.

The user's folder can hold Changes from multiple Workspaces and must never be shared as a whole. Individual files/material can be shared only under applicable disclosure rules. Folder path, owner metadata, file possession and a matching digest do not authenticate ownership or confer continuation authority. Protect log/control writes independently of ordinary workers and generic file-mutation bindings. Storage belongs in persistent application/user data, not installed release bytes or an ephemeral execution directory.

A Change has one authoritative logical history through its lifetime. Borrowing moves active continuation without changing its owner or fixed Workspace; inactive checkpoints, backups and read-only copies do not become independent writers. Forking creates a different Change with exact origin provenance, not a competing history under the same identity. The [routing contract](../../product/changekernel.md#routing-borrowing-and-forks) owns these relationships; [execution](agent-execution.md#change-handoff-and-continuation) owns their interaction with outstanding Work.

Trace custody is one logical persistence responsibility, not a promise that only JSONL bytes survive. It covers the Change log and necessary acceptance, execution and evidence custody, with explicit ownership for supporting records; it does not absorb native resource or host policy authority. No mandatory database service, SQLite index, independent entity/task/memory database or database/process/repository per Workspace is implied. Native effect receipts and protected execution reservations/results may have distinct responsibilities, but must not duplicate lifecycle authority. Derived Views/indexes are rebuildable only when sufficient retained grounds and a qualified reconstruction contract exist. A missing authoritative head, identity or custody record is not automatically a cache miss. JSONL design does not retroactively turn current SQLite heads/retry bindings into disposable indexes.

### Backend-only authoritative writes

The Change Trace log is a persistence format, not a client editing interface. Human interfaces, agents and integrations request typed domain operations through the current custodian's authorized backend. They do not submit arbitrary log appends, replacement files or caller-constructed authoritative events. A trusted internal storage port is not an untrusted endpoint. Borrowing may change the authorized backend; it does not require the original host to remain the permanent coordinator.

For each supported operation, the backend resolves authenticated user and delegation independently of request claims, establishes current custody and native authority, validates bounded input and expected subjects/versions, applies applicable lifecycle requirements and constructs the attributable record. The backend owns deterministic encoding, serialized accepted-prefix advancement, exact retry reconciliation and durable acknowledgment. A duplicate request may return its retained result only under current delivery authority; changed input cannot reuse an earlier operation identity. Deterministic recording does not make semantic assessments deterministic, prove claims true or establish that a proposed effect happened.

Client messages claiming approval, Check success or execution completion are contributions to assess, not authority to fabricate those records. Bind authoritative assessments to qualified evaluation and exact subjects; derive effect outcomes from the source's qualified outcome protocol. Retain an authorized human decision as that person's decision, not as an invented passing Check. The same operation guards apply to human and agent clients, without an additional approval merely because an agent made the request.

Backend-only writing must be enforced independently of cooperation. Workers, evaluators, client applications and generic file/resource APIs must not be able to rewrite the Trace, checkpoint, identity/custody bindings or live policy through filesystem access, aliases, inherited handles, process access or another write route. Use native protection and qualified isolation; a process with the same effective storage privileges can bypass an API convention. Logical user ownership of a Change does not require clients to have raw write access to its authoritative files. Authorized views and exports are not writable continuation authority.

### File-first domain interface boundary

The operational file-first host will expose a new, explicitly versioned domain interface and persistence profile. It will not present a file implementation of the frozen [native continuation v1 contracts](#native-continuation-api-and-storage-v1) while silently changing their meanings. In particular, native revision/candidate retries have container-and-actor-scoped, separate operation namespaces; the file-first existing-Change contract below instead reserves a request key across actors and operation kinds within the installed logical Trace identity. Those are different protocols, not interchangeable storage adapters.

Keep existing SQLite formats, identifiers and public library behavior intact. Reuse bounded values or pure validation only where their meanings really agree; do not reuse an old receipt, revision identifier or `container_id` as an implicit Workspace/Trace authority. The new host resolves its installed Workspace/Change context and authenticated actor independently of request claims, then applies its own closed typed operations and exact retry rules. Legacy library ports do not become raw IPC endpoints. Any future import or migration requires a separate explicit protocol; this boundary does not authorize one.

This selects the interface separation, not the still-unsettled public message encoding, operation result references, persistent inventory or creation/recovery algorithm. The [Linux packet adapter](agent-execution.md#linux-local-packet-ingress) is deliberately below that boundary: verified packet credentials and opaque bytes do not settle domain acceptance, source permissions or any of those formats.

### Protected accepted prefix and recovery boundary

The first local file-first direction uses a protected JSONL Trace for lifecycle history and a separate protected checkpoint identifying its accepted prefix. This checkpoint is authoritative acceptance control, not another lifecycle history or a rebuildable cache. Its exact representation, identity binding, writer exclusion and joint creation/commit/recovery protocol must be settled before implementation. A second file or a hash alone supplies none of those guarantees.

| Situation | Required behavior |
| --- | --- |
| Clean writer shutdown/restart or ordinary host reboot | Reopen the same Change under intact protected custody and a qualified restart-admission protocol. Preserve accepted history, exact version bindings and unresolved Work; re-establish current authority and any required native source identity/permission checks before dependent progress. |
| Unexpected writer loss or storage I/O incident | Fence live storage errors and retain incident evidence. A surviving incident blocks affected acceptance and delivery until qualified recovery. Apply the [first local recovery profile](#first-local-recovery-profile) when no incident evidence survived; do not claim to distinguish a lost error from fail-stop interruption by matching files or re-syncing them. |
| Interrupted append or lost acknowledgment | Reconcile the exact operation against intact protected custody. Distinguish accepted bytes from an unacknowledged suffix under the qualified failure model; do not guess acceptance or silently truncate uncertain history. |
| Old log with surviving newer acceptance control | Refuse continuation of the stale prefix. Recover necessary retained bytes through a qualified path or remain unavailable; a current digest cannot reconstruct missing history. |
| Explicit copy, import or backup restoration | Do not promote the supplied pair to active authority. Require independently surviving current custody evidence and the qualified admission/reconciliation protocol; otherwise allow only authorized non-authoritative inspection or refuse. |
| Unannounced rollback of the entire custody domain | An old internally consistent log/checkpoint pair cannot reveal its own rollback. Do not claim detection or safe automatic continuation without an independently surviving freshness authority. |
| Lost or uncertain source-effect outcome | Use the qualified source receipt, exact-operation idempotency or reconciliation protocol. Restoring local history does not undo a booking, payment, publication or deployment; never hide uncertainty with a new operation ID. |

The first operational local profile must support clean shutdown/restart, ordinary reboot and authorized history reopening under explicit custody and storage assumptions. Change lifetime must not depend on one continuously live process; a gate that refuses every successor is not that operational profile. Reopening does not itself launch work. Historical delivery and readiness for new effects are distinct: a qualified incident gate may permit delivery from an intact accepted prefix while blocking progression, without certifying an uncertain suffix or head. Ordinary restart is not an implicit import or proof against whole-host restoration. Whole-custody rollback-resistant continuation requires separately qualified surviving authority, such as suitable native application custody or protected monotonic state outside the restored domain. No particular cloud service, hardware or cryptographic dependency is selected. A weaker local profile must state that limit; full-domain rollback resistance and automatic restoration remain unavailable until established. Even a freshness witness detects loss rather than recovering bytes or proving external effects.

### First local recovery profile

The first dogfood release explicitly accepts a **lost-incident limit**. If a predecessor observed a storage I/O error and died before reliable incident evidence survived, a successor may resume through the qualified recovery protocol after validating protected custody and current eligibility. This deliberately gives up the stronger guarantee that every such earlier error remains distinguishable after restart. It does not establish that an earlier syscall/barrier returned success or that the preceding epoch was error-free. Neither matching bytes nor a fresh successful sync proves that historical fact.

Live observed I/O errors still fence the affected writer and custody scope immediately: no new acceptance-bearing acknowledgment or affected historical delivery follows while the incident is unresolved. Retain incident evidence through the protected writer path when possible; failure to persist it does not permit the live writer to continue. Surviving incident evidence remains authoritative refusal input and must not be erased, reset or bypassed by a routine restart or re-sync. Error scope requires evidence; unscopable custody-health loss blocks the root. Expected absence and attributable logical damage are not automatically root-wide physical incidents.

Successor admission still requires excluded predecessors, authenticated installed custody identity, current authorization, validated authoritative acceptance control and its exact accepted prefix, required retained grounds, and the profile's explicit storage/barrier/recovery rules. Absence of an incident record alone is not admission evidence. Missing/damaged control must not be rebuilt from a log; an unaccepted suffix must not be promoted or silently truncated; an uncertain native effect must not be repeated without its qualified receipt/idempotency/reconciliation path. Reopening does not launch Work. Historical delivery and eligibility for new progress remain separate decisions.

The exact versioned custody and recovery protocol must identify which surviving states are admissible, blocked or repairable and how current durability is established before acknowledgment. Source tests and release qualification must exercise both retained-incident refusal and the explicitly permitted loss-of-incident case without claiming to distinguish identical surviving evidence. Ordinary clean shutdown/restart and reboot remain supported outcomes, not permanent refusal. This limit does not relax worker isolation, native source permissions, exact retry identity, retained intent/evidence or source-outcome obligations. Whole-domain rollback detection and automatic restoration retain their separate limits. No hardware witness, external service, recovery reset or new database is selected by this profile, and existing native storage profiles are not silently migrated or reinterpreted.

### First local recovery admission protocol

This selects the logical recovery protocol for the approved local profile, not a storage codec, installed host or implementation release. The complete control inventory, byte grammar and host identity/enrollment contracts must be frozen together before dependent source work. The earlier witness-dependent `VIRGIN`/`DIRTY`/`CLOSED` proposal is not this protocol. Routine process exit is not itself a storage incident; a missing previous clean-close marker does not refuse every successor. No witness, new database or second authoritative history is introduced.

**One writer and observation boundary.** One protected service process owns all custody syscalls: root/registry enumeration, control and Trace reads/writes, exclusive creation, replacement, barriers, cleanup, errors and acceptance-bearing delivery. Opening the root is already observed I/O; an in-memory incident latch exists before that first syscall. Parsing and domain logic receive bounded values, not writable custody handles. There is no separate host-control writer whose error can escape the Trace gate. Mutations and deliveries serialize under the current policy/enrollment guard and permanent deployment lock; per-Change locks follow the deployment lock. Retained lock objects are never removed or replaced to gain admission.

A successor needs both qualified process/handle fencing and the exclusive lock on the verified original lock object. A PID, idle timeout, socket disconnect, matching lock-file contents or lock acquisition alone does not prove that an old writer or descendant retaining a writable handle is fenced. The selected supervisor must establish predecessor termination and exclusion of surviving writable/lock handles under the process-isolation contract. Missing fence or lock identity leaves custody unavailable. No storage descriptor passes to clients, checkers or workers; close-on-exec alone does not prove exclusion of fork inheritance. The concrete supervisor/handle proof remains a host prerequisite, not a receipt reconstructed from Trace.

**Initialization differs from reopen.** Administrator provisioning establishes installation/root identity, protected ancestors and independently justified first-use state before custody initialization. Under the same fencing/observation boundary, the writer exclusively creates every permanent lock, required parent and control, synchronizes each control and each parent whose namespace changed, then validates the complete initialized inventory before requests. The installation handoff must distinguish unused custody from failed or previous initialization. Empty, partial, missing or restored custody is never inferred virgin from absence; retry never creates a replacement deployment identity. Failed initialization remains unavailable until its same-identity state has a qualified outcome. Provisioning-record encoding, placement and handoff remain host dependencies; an unencoded “virgin” flag is not authority.

**Reopen ordering:**

1. Establish current installed deployment identity, protected ancestors and predecessor fence; acquire and verify the permanent lock. Do not create missing locks or root controls during reopen. Establish current enrollment/disclosure authority before private delivery; inability to authorize one principal must not become permission for anonymous delivery or automatic damage to another principal.
2. Read the bounded complete control/namespace inventory through the writer. Check versions, types, permanent identities, associations, capacity and incident evidence before treating a lookup as absence. Unknown entries, conflicting identities or missing required controls are damage, not capacity, a new principal or a new root. Enumeration and hashes cannot detect an internally consistent whole-domain rewind; that remains outside this profile's guarantee.
3. Retained incident evidence blocks affected custody. Genuine or unscopable storage incidents fence the deployment. Independently classified logical damage may fence only its attributable Change, leaving unrelated intact Changes deliverable. Malformed/unreadable incident controls cannot mean “no incident.” Incident evidence is never a routine temporary file deleted at startup.
4. For an otherwise admissible Change, decode its intact protected checkpoint and validate exactly its selected prefix: deployment/Workspace/Change/source associations and generation, framing and lengths, sequence and predecessor chain, accepted head/end coordinates, typed event/result envelopes, and required delivery/retry grounds. A longer plausible Trace does not select a newer head. Missing checkpoint or grounds cannot be rebuilt by scanning the log. An active creation control without its matching accepted origin is unavailable.
5. Complete fresh barriers for the validated Trace, checkpoint and authoritative namespace parents needed by that prefix before acceptance-bearing delivery. Recheck exact checkpoint/prefix identity and current disclosure authority under the held guard. These barriers establish current durability under the approved profile; they do not prove an earlier acknowledgment, clear retained incidents, settle effects or detect rewind. A new storage error takes the incident path, not a retry loop that erases it through later success.
6. Admit only operations justified by that state. A healthy exact end may admit append once the full operation contract is frozen. Bytes beyond the checkpoint, interrupted control replacement and private origin preparation are not automatically accepted. A validated accepted prefix may be delivered with append blocked only when the suffix/control condition is independently classified, disclosure/retry grounds remain intact, no retained incident applies and fresh barriers succeed. Otherwise the Change is unavailable. Do not truncate, promote, rewrite or execute the suffix to gain admission.

**Commit and acknowledgment.** For an already active Change, validate current authorization and the original operation key/subject/input under the guard before new work. A new append writes its canonical record, synchronizes Trace, writes and synchronizes a unique same-directory checkpoint temporary, atomically replaces the checkpoint and synchronizes its parent. The writer validates the installed checkpoint/prefix and retained grounds, rechecks delivery authority and releases the exact accepted result/reference. Trace bytes or successful rename alone are not acknowledgment. A temporary checkpoint never substitutes for the installed checkpoint. Creation additionally requires the still-unfrozen pending reservation → private origin preparation → active association → final certification contract; ordinary append does not close bootstrap.

Resolve the original retry key before new source observation, identity minting or initialization. An accepted exact retry compares the complete original typed subject/input and returns its retained result plus original derived reference/head under current disclosure rights. It does not regenerate results, advance expectations or rerun effects. Historical private delivery can survive current source unavailability where its own grounds survive; source-dependent continuation requires fresh source authority. An occupied, damaged or uncertain key cannot become a new Change or operation under another identity. Source-effect uncertainty needs its own reconciliation; custody barriers cannot settle it.

**Incident handling is monotonic within a writer lifetime.** A short write, uncertain barrier, genuine I/O failure or unclassified storage outcome latches refusal before further acceptance-bearing reply. The writer attempts bounded incident retention through the same protected route, preserving observed failures; retention failure does not clear the live latch. Expected exclusive-create contention and justified absent lookup are not automatically device incidents; unexpected absence of authoritative control remains damage. Later successful syscalls, reopen or administrative deletion cannot clear retained incidents. Incident scope/classification and persistent grammar remain part of the full inventory freeze.

If the writer disappears before incident evidence survives, a successor cannot recover the lost observation. It may use the validation/barrier protocol only under the approved lost-incident limit; it must not claim “no previous error,” complete recovery of earlier acknowledgments or witness-certified health. A new root marker cannot remove that limit without independently surviving authority, and none is selected.

Qualification must challenge clean process restart/reboot; competing successors and inherited/stale handles; every file/parent barrier and checkpoint-replacement cutpoint; lost reply; retained incidents and failed retention; unknown/missing controls; accepted prefix with unaccepted suffix; exact retry after source revocation; active association without accepted origin; and scoped logical damage versus deployment-wide I/O failure. Same-UID unit tests cannot establish installed isolation, physical persistence, account lifecycle or effect recovery. The [package testing and qualification policy](package.md#testing-policy) remains binding.

The syscall premises are narrower than the operational claim: [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) requires separate directory synchronization and documents write-back errors; [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html) is advisory on the supported local profile and shares locks through duplicated/forked file descriptions; [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) supplies namespace replacement, not durability certification. These premises justify barriers and handle fencing. Documentation lookup is not installed qualification.

### Record, replay and durability requirements

Before implementing a file-authoritative profile, settle its exact versioned schema/encoding, bounds, accepted-prefix identity, writer arbitration, acknowledgment point, exact retry/replay/import rules, retention and interruption/corruption behavior. Preserve accepted history; never silently skip malformed operations, reconstruct lost intent by inference or accept a divergent prefix through text merge. Distinguish an interrupted unacknowledged tail from damage to accepted records under the qualified failure model. Successful acknowledgment must meet the declared durability contract, not merely mean that an append API returned. Source/storage errors remain unavailable or uncertain rather than fabricated success, absence or denial.

Replaying validated accepted records may reconstruct derived lifecycle views; it must not rebuild missing authoritative acceptance control from the log. Conversation restoration and executable trajectory replay are not this operation. Re-running saved generated code requires execution admission and outcome reconciliation, even when no new model call is made. Preserve exact retained decisions/results rather than repeating inference to manufacture missing grounds.

A hash cannot prove that a valid old copy is latest, prevent authorized-path bypass or recreate missing bytes. Exclusive continuation and rollback/replay detection require a qualified acceptance/custody protocol, including stale copies and restart. Required grounds must be retained or supported by qualified native history. Missing/corrupt required grounds block dependent progression; no new operation identity may conceal an unresolved old outcome.

Backend-only writes and the first local Trace/checkpoint authority roles are selected requirements, not a selected serialization or commit algorithm. The [dependency gates](../../product/changekernel.md#dependency-gated-implementation) block affected persistence formats/interfaces until their contracts are resolved and reviewed. Existing native profiles below keep their exact storage and retry meanings; no implicit migration, JSONL dual-writing or automatic import is authorized.

### Git, sharing and encryption

For the first local file-first profile, Git serves history, diffs, transport and checkpoint evidence, not live Trace acceptance. Git's expected-old ref check alone does not prevent an authorized writer from moving a ref backward. A later Git-authoritative profile would need a separately specified and qualified acceptance/durability protocol; it is not implicitly enabled by this role. A Git commit, authorship field, merge or ref name alone does not authenticate a participant, authorize a transition or make unrelated effects atomic. Incoming changes require identity, prefix, semantic and authority validation; do not merge authoritative Change histories. Adopting results from other Changes retains provenance and checks the actual combined candidate.

Use established authenticated cryptography for supported encrypted storage/transfer rather than inventing a cipher. Concrete formats, authenticated identity/key distribution, rotation, revocation and metadata visibility remain preconditions for confidential-sharing claims. Encryption does not enforce exclusive continuation, prevent repeated submission or recall plaintext already disclosed. Share a whole Change only when recipients may see all disclosed contents; otherwise use authorized material/views without pretending that a partial copy is another complete authoritative history. UI filtering after replication is not access control. Credentials and private execution scratch do not belong in portable Change files.

A local protected-custody profile may be qualified before remote sharing, but must report unsupported transport/sharing as unavailable. File placement, Git synchronization and encryption are not substitutes for enforcement at resource write routes.

### Multi-tenant scope and ownership

Track native resource identity together with its source binding, Workspace, authorized ownership or sharing scope, and observed version/time and coverage. A tenant label supplied by a client or agent is not authority. The trusted host resolves the responsible user and scope using the application's existing authorization layer; bindings must preserve its constraints, native handlers and current permission checks rather than bypass them with privileged generic database access.

Tenant-owned values, explicitly shared resources and developer-owned code/schema may coexist in one physical database. Bind their differing authority explicitly without requiring separate databases or copying their current State. Queries, history, retained evidence, derived indexes and any supported synchronization must respect the relevant permissions; viewing the system does not imply visibility into every tenant. Shared learning follows the owning system's sharing and adoption rules, not automatic promotion of private experience. These are desired binding obligations, not a claim that the single-owner native profile implements delegated membership or general multi-tenant authorization.

## Sources, observations and retained research

Read on demand, retain what decisions rely on, and recheck what actions depend on. Sources hold native material; adapters report attributable observations; Evidence establishes what those observations support or challenge; Change memory records their use; adopted State knowledge records the current accepted conclusion and limits. A connected source can expose governed resources, read-only evidence or both. Connection, capture, a trustworthy publisher or a matching digest alone does not adopt its assertions as governing truth.

Need is derived from intent, applicable procedures, constraints and affected dependencies, not only an agent's preferred searches. Catalogs and binding metadata may be known upfront without loading all contents. Obtain bounded authorized material, expand when dependencies or uncertainty require it, and expose missing, denied, partial, truncated or outdated coverage. Checks consume exact supplied inputs; authorized Work gathers missing observations. No-result searches do not prove nonexistence. Explicit scoped monitoring is also a legitimate need; it does not require mirroring every source or authorizing subsequent effects.

Authorized research may discover and retain a new source resource during a Change. Bind its stable identity, original location/publisher where available, acquisition time, exact captured version, content identity, transformation history, discovering Change/Work, scope, visibility, retention and permitted use. Preserve source bytes or qualified exact native history where required; a derived extract identifies its original capture and transformation. Treat later retrieval as another version/observation, not an overwrite of historical grounds. New retained material is subsequently consumable through ordinary qualified source interfaces; no separate research-memory authority is needed.

Raw research may be retained in protected custody before its conclusions are assessed, like a private candidate. Retention does not publish adopted knowledge. Reuse or broader visibility requires applicable authority; private capture is not an implicit shared library. Registering material is distinct from installing an adapter, granting credentials or enabling a new capability. Source text cannot execute instructions, load plugins, confer permissions or revise procedures. Such configuration and authority changes follow their own protected transition requirements.

| Material needed | Custody rule |
| --- | --- |
| Exploratory material not relied upon | May remain temporary or cached within its declared policy. |
| Required grounds with protected native history | Pin exact versions and establish that access/retention obligations are supported. |
| Required grounds from mutable or expiring sources | Retain an authorized exact bounded capture rather than rely on a live link. |
| Recovery input | Protect necessary prior values, differences or supported compensating instructions before effects. |

Bind observations to source/binding identity, actor-authorized scope, resource/version, observation time and relevant query parameters, projections, selection/membership, consistency, coverage and omissions. For derived results, retain the method and necessary inputs or qualified references. Preserve exact supplied assessment context and relevant counterevidence, not merely favorable citations from an answer. A path, timestamp or digest cannot recreate deleted bytes. If required retention or access cannot be supported, block the dependent guarantee or progression rather than silently weaken it.

Reading permission does not automatically authorize retention, sharing or disclosure to a model. Copies, summaries, indexes and learned guidance can carry sensitive information too. Apply current custody/delivery policy to them and their metadata. Source revocation, permitted historical custody and authorized redaction/deletion need explicit policy; no cached copy may invent a new access route. Distinguish denied access from absent data. Historical captures establish what was observed then, not what remains true now.

Freshness follows link meaning. New live data does not rewrite old evidence. A changed execution dependency, selection membership or governing assumption can invalidate readiness or require procedure reassessment; unrelated source changes need not invalidate proven equivalent inputs. If a consumer is added after an interface assessment, unchanged previously observed files do not establish complete current coverage. Where bindings cannot support suitable comparison or guards, required freshness remains unresolved. Observing native outside writes exposes current values and drift rather than fabricating approved Changes or allowing stale memory to override the source.

### Scoped monitoring and trigger grounds

[State-triggered automation](../../product/changekernel.md#state-triggered-automation) uses adopted standing intent and ordinary qualified source bindings. Monitoring specifies authorized source/resource selection, relevant values or events, observation cadence or subscription semantics, freshness/coverage needs, retention and resource limits. It does not copy every accessible resource, confer write authority or introduce another definition of a container. Source payloads remain data, not instructions to the host.

An attributable occurrence binds the exact adopted rule version and scope, owner/current delegation, source/binding identity, observed versions/events and times, condition inputs/result and required retained grounds. The rule defines edge/level/event behavior, time windows, coalescing or cooldown and the meaning of a later independent occurrence. Missing, stale, denied, partial or conflicting observations are explicit outcomes, not a satisfied condition or proof that nothing happened. Multi-source observations do not imply a global snapshot.

Before implementing automatic triggering for a binding, settle duplicate delivery, out-of-order or corrected events, sampling gaps, cursor loss and restart behavior. Polling, callbacks or source events may supply observations; none provides exactly-once effects by itself. Retain the association between an admitted occurrence and its original proposal/continuation operation and result. Resolve that association before new creation or dispatch after a retry/crash; uncertainty must not produce a replacement operation identity. Cursor or deduplication records are bounded supporting custody with an explicit owner and failure/retention model, not an independently writable Change history. Their loss must not erase an accepted Change or become permission to replay an effect.

A Change retains the standing-intent version and exact triggering grounds used at its origin or continuation. Later observations and rule revisions never rewrite those grounds. Current eligibility can change: withdrawn delegation, retired rules or stale source conditions block dependent new progress according to the admitted withdrawal policy. Current private history may remain deliverable under its own rights. Stopping monitoring or cancelling a pending proposal does not prove that an already dispatched effect stopped; native outcome reconciliation remains necessary.

Before claiming automatic progression, qualify sustained conditions, repeated/corrected events, missed observations, rule revision/withdrawal, concurrent triggers sharing a budget, restart between observation and accepted creation, lost acknowledgment and unknown external outcome. Preserve existing source permissions, retained-ground custody and guarded publication requirements. Monitoring/trigger codec and recovery contracts remain prerequisites, not inferred additions to the frozen SQLite or first file-first profiles.

## Different retained things have different lifetimes

| Material | Retention responsibility |
| --- | --- |
| Re-fetchable observation or derived index | May be cached or rebuilt if its loss does not destroy required grounds. |
| Retained research resource | Preserve exact captured material or qualified native reference with provenance, visibility and declared retention; later observations do not overwrite it. |
| Intent and decision history | Preserve original request, interpreted/admitted revisions, attributable decisions and exact references to continuing State obligations. |
| Pending candidate | Retain exact approved/generated values or patches durably until execution, reconciliation, Review and retention obligations permit removal. |
| Assessment input and result | Preserve exact inputs, evaluator/settings, source roles, outcome and limits needed to explain and verify decisions. |
| Effect receipt | Retain source identity, stable operation identity, actual outcome and exact effect/history references. |
| Recovery grounds | Protect needed prior values, differences, native versions or compensating instructions before effects occur. |
| Change Trace log | Own the Change's append-only lifecycle history and link exact grounds without duplicating every payload. |
| Adopted procedure or rule | Keep a versioned current artifact with scope and adoption/revision/retirement history. |

A transaction identifier alone is not a historical archive. A row that changed from €900 to €1,200 and later to €1,500 no longer reveals the earlier assessed values. PostgreSQL [removes obsolete row versions](https://www.postgresql.org/docs/current/routine-vacuuming.html); its [transaction identifiers](https://www.postgresql.org/docs/current/transaction-id.html) do not replace retained historical values. Reuse qualified native history where available, otherwise retain the differences or prior values needed for the declared guarantees. A universal full-version mirror is not required.

Thin Change Trace logs need durable, authorized targets. A local path or expiring provider link is insufficient for promised continuation. Preserve reference integrity, access restrictions and explicit retention limits. Cache deletion must not erase an unexecuted approved candidate or the only recovery grounds.

## Intent, Change memory and procedural State

The Change Trace log owns the immediate pursuit's history: original request, interpreted intent with stated/inherited/inferred/unknown provenance, outcome and success observations, scope/exclusions, commitments, material alternatives, decisions and attributable revisions. Preserve original input and supersession relationships; do not rewrite accepted intent to fit delivered output. Work and related Changes reference the relevant versions instead of producing competing intent documents. Continuing goals, requirements and preferences belong in State, referenced by the Change. Current design describes desired behavior; Change history explains its adoption and revision. Release changelog entries are not this record.

Change memory retains case-specific experience: selected assumptions and source versions, attempts and rejected hypotheses, exact procedures and assessment inputs/results, candidates, effects, outcomes, failures, repairs, proposed lessons and unresolved consequences. Keep concise rationale and durable references rather than every conversation or private reasoning transcript. Retention and access rules apply to summaries and to their targets. A fresh worker must recover what was intended and known then, what happened, and what remains safe now; reconstruction must not rerun inference or effects.

State memory retains current adopted knowledge and guidance with identity/version, owner/scope, purpose/applicability, content or exact native reference, preconditions, limits, supporting grounds and adoption/revision/retirement history. An authoritative runbook or executable policy stays in its native source when that source owns its meaning. State represents the adopted meaning held by its authoritative resource; it does not require copying procedure text into generic storage. A reference to current adopted content and its meaning must not silently advance when an outside file changes.

| Link role | Required meaning |
| --- | --- |
| Historical support | Pinned Changes, observations, standards and counterevidence explain why this procedure version was adopted. |
| Required operational input | A parameterized observation requirement describes what a particular future use must collect under current scope and freshness rules. |
| Applicability dependency | A governing assumption, rule or source relationship can make guidance stale or inapplicable when it changes. |
| Actual use | A Change identifies the exact procedure and observations it relied upon, not whatever is current when history is read. |

Adopting, revising or retiring knowledge/procedures is a semantic State effect governed by the same Change pipeline. Internal learning code can collect experience, suggest improvements and prepare candidates, but has no alternative publication authority. A memory update can be part of an existing Change; learning after closure can become a linked Change. Collection/custody records, indexes, caches and derived freshness indicators can be maintained internally without adopting new meaning. There is no nested Change for each download or lookup and no mandatory model or human call for every exact update.

Automatic learning needs delegated authority and applicable assessments, not mere repetition. Preserve failures as well as successes; useful learning does not retrospectively complete a failed goal. Proposed guidance cannot weaken its own governing adoption rules. Own summaries are not independent corroboration. Reliable mechanical lessons can become code/tests rather than additional prose. A privacy-sensitive finding is not automatically safe to generalize or share.

Retrieve within permissions before relevance ranking, then distinguish historical context, proposed improvements and current adopted guidance. Required observations must be obtained for the actual use rather than copied from an old incident. Retired guidance remains available only as authorized history, not an active instruction. A bounded generated brief is a view, not another independently editable intent or memory store. Typed references and scoped queries suffice for an initial implementation; no separate memory database, universal index or semantic-search service is required. Memory can guide recovery but cannot replace protected prior values, receipts, current source observations or process custody.

### Structured history access and context projections

Keep three responsibilities separate:

| Material | Meaning and authority |
| --- | --- |
| Change Trace log and protected controls | Accepted lifecycle history and continuation authority under the qualified custody protocol, with exact references to retained grounds. |
| Runtime transcript or trajectory | Attributable interaction history for an execution attempt; not an approval, source-effect receipt or replacement lifecycle store. |
| Working context | A bounded selection, summary or transformation used by a person or model; derived from identified inputs, not independently authoritative. |

Authorized workers must be able to inspect relevant retained history programmatically rather than depend only on lossy summaries or relevance-ranked retrieval. Support bounded exact lookup, text search, filtering and scoped inspection where the binding permits them. Preserve source roles, versions, record/artifact references, coverage and omissions; permission filtering precedes retrieval. Absence from a view is not evidence of absence from the source. Retrieved instructions remain source material unless separately adopted under applicable authority.

Context compaction or delegation does not retire governing requirements or delete necessary original intent, candidates, decisions or recovery grounds. Carry exact instructions and references when needed, plus derived progress summaries with their limits. Durable identifiers and qualified retained targets must replace process-local object identity across restart; neither a pathname nor a summary can reconstruct erased bytes. These requirements do not mandate retaining every conversation, disclosing entire private folders, a new memory database or a particular query language. The [execution contract](agent-execution.md#programmable-strategies-and-bounded-delegation) governs how runtimes consume these views.

## Native Rust intake

**Existing bounded profile, not the new Workspace/file-first protocol.** Its container names, identifiers, store layout and retry rules below remain unchanged until an explicit supported disposition. No general membership, user-Kernel selection or portable Change-file authority is implied.

The first native intake capability is a library boundary for retaining original intent, not admitting pursuit or publishing State. It supports a single authenticated owner per container and multiple containers in one application-chosen store. SQLite is the first local/new-application binding, not a mandatory sidecar or the engine-wide database choice. Source files remain authoritative in place; intake writes only its own protected bookkeeping.

The host authorizes store initialization, supplies a persistent file path, authenticates the actor on every call, and protects storage against ordinary worker access. An actor value or a Rust type does not authenticate anyone. Actor context is supplied separately from proposal content; no request field, natural-language instruction, guessed identifier or implicit membership grants access. This boundary does not yet support ownership transfer, delegated membership or a network transport.

| Operation | Required meaning |
| --- | --- |
| Create a container | Bind its supplied identity to the trusted actor. Repeating this for the same owner returns the same container; another actor cannot take it over. |
| Open a container | Verify current owner access without creating missing containers or adopting anything. |
| Propose intake | Retain the trusted actor, container, stable request identity, exact What and available Why; return a stable container-scoped Change reference and the retained intent. |
| Read retained intake | Recheck actor/container access and return the exact retained record, or report denied/unavailable access without reconstructing or repairing it. |

Container, actor and request identifiers are opaque, nonblank text of at most 256 UTF-8 bytes, without control characters; namespace prefixes are not required. What is nonblank text of at most 65,536 UTF-8 bytes. Why is optional text with the same size bound; absent and present-empty remain distinct. Accepted text is retained exactly, including whitespace and Unicode representation, without trimming, normalization or an invented rationale. These are bounds for this native capability, not a retroactive change to the TypeScript prototype's validation rules.

Retry identity binds container, trusted actor and request identifier. An identical retry reconciles the retained outcome and returns the same Change reference and intent, even after a lost reply or process restart. Different What or Why under that identity conflicts without overwrite or a second record. Distinct containers do not share retry bindings. Concurrent first submissions must converge to one retained outcome: identical proposals receive it, while different proposals produce one winner and a conflict. No particular contender must win. Change references are opaque and container-scoped; prototype hashes and globally unique bare identifiers are not required.

The persistence binding owns atomic container ownership and retry constraints. A successful proposal is returned only after its record and retry binding commit together. Keep transactions short and perform no model calls, worker launches or application-source effects. A storage error can leave the outcome unresolved; it is not proof of rollback or permission to invent another request identity. Retrying the same intake identity must reconcile before inserting. A known failed insertion can be repaired externally and retried without reserving a false success or creating duplicates.

The SQLite binding uses an explicitly supplied persistent file, bounded lock waiting and full synchronous writes with transactional journaling. It rejects in-memory/URI shortcuts and implicit storage discovery. Initialization and reopening are distinct caller intents: opening an existing store fails on a missing file or schema rather than creating a replacement. Authorized initialization accepts only an empty store. The binding identifies its native schema separately from prototype storage and refuses unsupported, partial or unrecognized schemas rather than resetting or silently migrating them. Validate retained field types, identity/context and a stable integrity digest before returning a retained record; detected corruption or missing grounds under a retained identity remain unavailable, not reconstructed. The digest encoding must be explicit and versioned, not a language's default hash or debug formatting. A digest detects inconsistent retained data; it does not protect a database from an attacker who can rewrite both data and digest. File protection remains a host obligation.

The result means only retained intake awaiting assessment. It grants no Decision approval, execution eligibility, Check success, publication or completion. Original intent is immutable in this boundary; later clarification/revision, candidate custody, Work, publication, retention cleanup and recovery of application effects require separately supported capabilities. Process-interruption, lock-contention and retry tests establish only their declared local behavior, not physical power-loss durability, backup qualification or cross-store recovery.

Keep native types and validation in the Kernel, coordination in Application, the atomic persistence contract in Ports and SQLite machinery in its Adapter. Expose only the bounded library operations needed here. No generalized repository framework, speculative modules or second authoritative copy of source State is required. The existing plain-JSON intake cases are shared semantic evidence; SQLite fault injection and schema inspection stay in implementation-specific runners. Additional recovery cases cover a committed intake whose reply is lost, competing first submissions with different content, contention followed by retry, and the same request identifier in independently owned containers. TypeScript reference success does not establish Rust conformance.

## Native committed-source observations

The first native source observer captures a bounded, explicitly selected Git commit view. This is a read-only library capability that supplies possible grounds for later candidates and assessments, not a live working-tree reader, automatic discovery, baseline adoption or a second authoritative source store. Dirty and untracked files are outside this view; never describe a committed snapshot as the current workspace or as fresh enough for an effect merely because it was readable.

The host supplies the authenticated actor, owning container, source identity, approved repository and Git executable paths, allowed file paths and exact full commit identifier. Source bindings and tool selection are trusted host configuration, not fields inferred from What/Why or instructions in repository content. Reuse the intake container-access boundary before observing; a guessed source identity or commit grants no access. Preserve operational unavailability as distinct from authorization denial; a locked or failed store does not prove a permission decision. Returned observations bind the container, source identity and exact commit. The host must protect configuration and source access; this library is not operating-system containment.

Support ordinary repositories with an in-place `.git` directory and the explicitly host-bound linked-worktree form below, using locally available objects. Arbitrary `.git` indirection, bare repositories, external alternate object stores, partial/promisor repositories, symlink traversal and submodules remain unsupported. Use the explicitly configured Git executable without a shell. Repository hooks, aliases, filters, pagers, replacement objects, inherited Git configuration/environment overrides and automatic fetching must not redirect observation or execute source-selected code. Missing objects or an unsupported reader/configuration produce unavailable results, not a fetch, fallback or reconstructed source.

An observation request contains at most 64 distinct, explicitly allowed, forward-slash relative paths. Each path is valid UTF-8, at most 1,024 bytes, and contains no control characters, empty segments, `.` or `..` segments; preserve accepted spelling without normalization. A present ordinary file returns its exact bytes, executable/non-executable mode, native object identity and a versioned SHA-256 content fingerprint. Support binary contents without text conversion. Capture at most 1,048,576 bytes per file and 8,388,608 bytes in total. Metadata and diagnostic output also need finite bounds. These are bounds for this profile, not universal limits on application State.

Readable Git objects are not proof of their advertised identities. Verify the exact captured commit, each selected tree edge and each returned blob against its native object identity before using those bytes. Derive lookups from the verified tree bytes, not a second potentially different read. This verifies the selected chain, not the entire repository or its history.

Absence is a distinct result, supported only by successful lookup in the selected immutable tree. A failed lookup, denied access, missing object, unsupported entry or unsupported ancestor is not evidence of absence. Every returned path belongs to the same selected commit. Return the complete requested result or a failure, not a misleading partial success or silently omitted path. Results cover only the requested paths; they do not assert whole-repository completeness or current-ref freshness.

Child execution has a finite deadline, bounded input/output and explicit cleanup on every exit, including success, nonzero status and cancellation. Leader exit or closed output streams do not prove descendant cleanup. Settle the owned process group and I/O workers before reporting success; if cleanup cannot be confirmed within a bounded grace period, report unavailability rather than successful custody. Observation must not alter repository files, references, index, configuration or source bookkeeping, and must not create a durable capture archive or modify intake storage. Permission to read is not permission to retain, disclose, adopt or publish. Later use as assessment grounds requires separately supported retention, disclosure and freshness checks. Test in disposable external repositories, including hostile configuration, unsupported source forms, oversized output, missing/corrupt objects and attempted path/scope escapes. No successful capture is a Check result, approval, publication or completed Change.

### Explicit linked-worktree observation

The self-development source may be a linked Git worktree. This read-only extension uses the existing `observe_committed_source` application path, source identity, exact commit/path selection, native result and access checks. It does not create a compiled binding definition, alter historical `container_id` or retry meanings, reopen the frozen candidate writer, or supply native permission, source continuity across reboot, custody, publication or restart authority. Its filesystem topology remains trusted host configuration protected for the duration of capture, not an authorization inferred from repository contents.

Keep `GitSourceObserver::new(container, source, repository, git, allowed)` restricted to an ordinary in-place `.git` repository. Add `GitSourceObserver::new_linked(container, source, worktree, git_directory, common_directory, git, allowed)` with the same return/error type. The host supplies all three source directories independently of the request. Do not discover or enroll a source by following its pointers, running `git worktree list`, searching parents or resolving an arbitrary `.git` file. No new runtime dependency, library export type, persistence format or launcher command is needed.

The bounded linked form has the following contract:

- `worktree`, `git_directory` and `common_directory` are absolute, non-symlink paths with valid UTF-8 spellings, no control characters or dot/parent components, and at most 4,096 bytes each. The common directory is the in-place `.git` of a non-bare primary repository. The private directory is exactly `common_directory/worktrees/<one-name>`; the name is a single ordinary component, not a traversal instruction.
- On each capture, before Git execution, revalidate the supplied paths and bounded regular control files. The worktree's `.git` contains exactly `gitdir: <installed-git-directory>` followed by a newline; private `gitdir` contains exactly `<installed-worktree>/.git` followed by a newline; private `commondir` contains exactly `../..` followed by a newline. These are equality checks against installed topology, not an instruction to resolve untrusted paths. Each control file is at most 8,192 bytes; missing, changed, malformed, oversized, symlinked or non-regular controls produce unavailable results. The ordinary constructor continues to reject this linked form.
- Object commands address the installed common directory directly with `--git-dir`, not a request path or a newly discovered directory. Capture never depends on a worktree's current `HEAD`, branch, dirty contents or index. Validate configuration, object-store exclusions and the verified commit/tree/blob chain in that common directory under the same deadlines, cancellation and size bounds as ordinary observation. Configuration changes or pointer replacement cannot become a fallback to another source.
- Allow a deliberately small passive local-config subset for both repository forms: the existing core format/bare/Boolean keys; `[user]` `name` and `email`; named `[remote]` `url` and `fetch`; and named `[branch]` `remote`, `merge` and `vscode-merge-base`. These keys describe developer tooling; they do not trigger network access, fetching, source mutation or credential discovery. Configuration remains bounded to 16,384 bytes. Accept only unambiguous section/key/value syntax; unsupported escaping, continuation or malformed lines fail closed rather than hiding another directive. Empty lines and full-line comments may be ignored. This is not support for every valid Git configuration.
- Continue rejecting all other configuration, including includes/conditional includes, worktree-specific configuration/extensions, executable helpers, aliases, credential/protocol/URL-rewrite settings and altered core worktree/hook/filter behavior. Continue rejecting shallow/alternate/promisor stores and unsupported object entry types. No clone, worktree registration/removal, fetch, config edit, index update, ref move or recovery action occurs during capture.

Tests must exercise the public application path with disposable ordinary and linked repositories, including passive remote/branch/user configuration, exact selected bytes despite different current/dirty worktree state, verified absence, current access denial, malformed or changed pointer/backlink/common topology, unsupported active configuration and missing/corrupt objects. Compare all source/control bytes before and after captures, and retain existing resource-bound and descendant-cleanup regressions. Fixtures may create and remove their own disposable worktrees; the observer itself must not do so. Successful source tests establish this bounded read capability only, not an installed host or the complete dogfood release.

## Native private continuation profile

**Approved bounded design, not operational qualification or a claim that every operation is implemented.** This continues native intake and committed-source observations for the first software-development application. It does not reinterpret `changekernel.container-candidate-batch@1.0.0`, historical TypeScript records or lifecycle stages. Decision admission, delegation, Work, Checks, publication and completion remain separate capabilities. Private candidates are Change-owned retained material: this low-level custody profile does not implement planning, define a separate proposal entity or fabricate a Work association before the Work contract exists.

### Authority and retention policy

Keep the native intake profile's single authenticated container owner. That owner may revise private intent and prepare or inspect private candidates under the host's current applicable permissions; this grants no execution or approval authority. Source-read permission alone does not authorize keeping a copy. The trusted host must separately authorize retention and historical delivery for the exact source binding, container and paths. These permissions are supplied outside proposal content and are rechecked on every operation, including retries and historical reads. A host may configure a standing grant for the declared scope; this does not require a human confirmation on every call. A missing or revoked permission cannot be replaced by a previously retained grant.

Retain accepted intent revisions, candidates and required grounds in protected durable storage without automatic expiry or eviction in this first profile. Accept only a host policy that permits that retention; expiry, purge, redaction and sharing requirements that this profile cannot enforce are unsupported, not silently waived. Current denial of delivery does not erase protected history or permit disclosure. Host policy unavailability and damaged custody remain unavailable, distinct from an explicit denial. Backup, physical power-loss durability and complete retention administration are not established by this profile.

### Attributable intent revisions

The original intake receipt remains immutable and keeps its existing interpretation and identity. It anchors revision zero. Later revisions retain exact What and optional Why, authenticated actor, request identity, expected prior revision and a stable revision identity. They do not infer an absent Why, normalize text, rewrite the original receipt or claim admission. The existing identifier and text bounds apply. Additional interpretation, commitments and adopted State references are not fabricated from these two text fields. This first profile supports at most 1,024 revisions per Change, including revision zero, so complete lineage verification has a finite bound. At capacity, an exact retry still reconciles; a new append is unavailable rather than evicting history.

An append compares the expected current revision and retains the new revision, head and retry binding atomically. Concurrent different requests against one head have at most one winner. An exact retry returns its retained result even if the head has since advanced; changed input under the same operation-scoped request identity conflicts. Current access is still required. Reads return the current head or an explicitly identified historical revision without replaying work. Missing or corrupt revision/head/retry grounds are unavailable, not reconstructed from a different surviving record. Material revisions cannot silently retarget an existing candidate or carry forward future approval by changing a head pointer.

### Exact file-candidate custody

A private file batch binds one container, Change, exact intent revision, trusted source-binding identity/revision and explicit full Git commit. It contains whole-file proposed bytes and mode, or deletion, for distinct explicitly allowed relative paths. Creation versus replacement follows verified prior presence/absence. Rename is a declared deletion and creation, not an inferred operation. Explicit read-only dependencies may be retained from the same commit; this does not discover all relevant dependencies or prove domain correctness.

Use the native observer's path, file and capture bounds: at most 64 selected paths across effects and dependencies, at most 1 MiB per file, and at most 8 MiB of captured prior file bytes. Proposed file bytes have a separate 8 MiB total bound. Retain exact verified prior bytes/modes/identities or verified absence alongside the immutable proposed values and provenance. Retained grounds must survive loss of the live Git objects; a digest or commit identifier alone is not custody. An unknown, denied, unsupported or corrupt observation is never absence. Source text remains data.

The application obtains grounds through the trusted observation boundary, not a caller's assertion that a `CommittedObservation` value is authentic. The host must version binding identity when its interpretation or resource mapping changes. Historical delivery requires a current authorized binding/grant, but does not reopen Git to reconstruct a missing retained capture or claim that the historical commit is current.

Preparation reads Git outside short database transactions. Before a new batch commits, its atomic store operation verifies container/Change ownership and the expected intent head, then retains the complete batch, grounds and retry binding together. An exact retry reconciles an existing batch before attempting another capture or applying the new-preparation head condition; it returns historical custody, not renewed eligibility. Different input under the same operation-scoped retry identity conflicts. A different request may prepare another immutable batch. No candidate operation writes source files, refs, the index or generic application State.

Inspection returns exact retained material and its bound intent/source versions. A historical candidate remains historical after intent changes; this first custody boundary does not label it currently approved, fresh for publication or executed. Missing retained grounds block delivery rather than trigger recollection. Later guarded effects must recheck current intent, policy, source state, required assessments and authority.

### Shared native persistence boundary

Use one explicit protected SQLite bookkeeping profile for original intake, revision heads/history and candidate custody. The profile is initialized deliberately in an empty store; opening never performs DDL or upgrades. Existing native intake-only stores remain supported as intake-only stores, with richer operations unavailable until a separately supported transition exists. There is no automatic import of historical TypeScript storage or native intake-only data into the richer profile.

The richer schema has its own exact version and full schema validation. Adding capabilities must not make foreign tables, triggers, indexes, partial schemas or unexpected journal changes acceptable. No generalized repository framework, new runtime dependency or separate authoritative task store is implied.

### Change attribution under partial custody loss

Retained candidate file rows must identify their owning Change independently of candidate headers and retry bindings, with relational constraints enforcing agreement. This is a requirement for an explicit successor storage profile, not a claim that the frozen v1 layout below already provides that attribution. Do not fabricate Work ownership before its contract exists or silently upgrade a v1 store.

Recognizable surviving custody for a Change must prevent recreation of its lost original intake under the same request identity with different intent. Required missing history is unavailable to its authorized owner, while intact unrelated Changes remain usable and unauthorized callers remain denied. Preserve retained bytes; do not guess erased relationships, recapture historical grounds, automatically delete remnants or adopt broad container quarantine. This guarantee concerns detectable partial loss, not recovery of completely erased history or protection against arbitrary identity rewriting; qualified backups and operator recovery remain separate concerns.

### Native continuation API and storage v1

The concrete library contracts are in `src/kernel/changes/intent.rs`, `src/kernel/state/file_candidate.rs` and `src/ports/continuation.rs`. These are native library contracts, not a new JSON transport or a reinterpretation of historical TypeScript protocols.

- `SqliteIntake::initialize` keeps the original intake-only format. `initialize_continuation` deliberately creates `changekernel.native-continuation.sqlite@1` in an empty/missing absolute file. `open_existing` recognizes either exact schema and never creates tables or migrates a profile. The richer format retains the four original tables and adds the six exact tables declared in the SQLite intent/candidate modules. No implicit profile upgrade or second authoritative store is allowed.
- Original proposal, retry binding, revision-zero row and initial head commit in one transaction. Origin has no revision-operation request or predecessor; its actor and exact What/Why must match the validated original receipt. A missing origin/head is damage, not an invitation to synthesize it on read or retry.
- Revision identifiers are lowercase SHA-256 hex using the existing native length-prefixed digest framing and domain `changekernel.native-intent.revision@1`. Fields are container, Change, actor, predecessor (empty only at origin), revision request (empty only at origin) and exact What, followed by the existing absent/present Why tag. `IntentRevision::successor` constructs proposed data; it is not a persistence receipt or permission. Current/history reads verify the bounded chain to the original, every retry binding and the absence of detached rows; missing/corrupt grounds are unavailable.
- `ContinuationStore::intent_revision` reads the head or a selected historical member. `check_intent_head` is a read-only preflight, not a lease. Both SQLite writers must repeat the shared `guard_head` inside their own `IMMEDIATE` transaction after exact-retry reconciliation. The revision writer atomically inserts revision/retry rows and advances the head; the candidate writer atomically inserts candidate/path/retry rows. No Git/model calls occur inside those transactions.
- Revision retries and candidate retries each bind `(container, actor, request)` in separate operation namespaces. A retry against another Change or with changed payload conflicts. Existing complete outcomes reconcile before a new-write head/capacity condition; missing retry grounds in otherwise retained records are unavailable. Unknown required retained revisions/candidates are unavailable to an authorized owner; denial remains an authorization result.
- `FileCandidateRequest` contains an ordered nonempty effect list and ordered read-only dependencies. Each `FileEffect` holds a relative path and either `Some(ProposedFile { bytes, executable })` or `None` for deletion. Selected paths are effects followed by dependencies, unique across both lists. Order is part of exact request identity; it is not silently sorted or normalized. Deletion of verified absence conflicts with the declared effect. Present-empty bytes differ from absence.
- A candidate identity uses the existing native digest framing with domain `changekernel.native-file-candidate.id@1` and fields container, actor and request. `FileCandidateRequest::digest` and `FileCandidate::integrity` freeze the binary, length-prefixed request/record encodings in the kernel. Record integrity covers proposed values and retained prior bytes, modes, object identifiers, fingerprints and path order; it is not authorization or independent proof of source truth.
- SQLite candidate path rows use contiguous zero-based `position`, `effect_kind` 0 for dependency, 1 for put and 2 for delete, and `prior_kind` 0 for absence or 1 for presence. Unused value/mode/object/fingerprint columns are NULL; empty present bytes are BLOBs, not NULL. A header's path count must match its complete ordered rows. Verify size bounds, modes, identities, fingerprints, digests, owner/Change/intent bindings and the retry-row/header bijection before delivery or reconciliation; never turn a missing ground into absence or another capture.
- `prepare_file_candidate` takes the host-installed observer and its trusted binding revision separately from the request. New capture must match that installed revision and the observer's container/source/path scope. `SourceCustody::with_authorization` receives actor, exact candidate scope and `RetainAndDeliver` or `Deliver`. The trusted host must hold the current permission valid through the callback, invoke it exactly once only when authorized, and forward its outcome. A scoped runtime policy guard can enforce this; Rust borrowing, a digest or an expired lease cannot substitute for it.
- Candidate preparation authorizes retention/delivery before retry lookup or capture. An exact retained retry needs no live observation or new-head match, but still needs current policy and intact retained custody. Historical inspection authorizes delivery of the retained scope without reopening Git. Generic coordination and exposed data types do not imply that a concrete store implements the write ports, nor do they qualify arbitrary host observers/policy providers. Direct persistence ports belong to trusted host composition, not untrusted request handlers.

The source development handoff records implementation and verification state. Compiler checks own type/borrow/exhaustiveness properties; ordinary runtime tests cover atomicity, authorization, custody, reconciliation and concurrent-head behavior. No protected source file becomes permanently owned by a Change: the Change owns its private candidate and retained grounds, while any future source mutation needs separate current authority and guarded version checks.

## Change-owned multi-entity candidates

**Historical TypeScript profile detail, not a native export or the file-first schema.** The versioned names, limits and stored meanings in this section remain historical contracts, not newly qualified Workspace behavior.

A Change can carry multiple immutable candidate batches, not just one record. Each batch retains the complete declared effects for its step: whole-entity creations, replacements or deletions, explicit relationships, and version-bound dependencies. Existing related entities remain authoritative in their sources; retain only the exact observations needed as grounds, not a second writable current copy. New entity values are durable private candidate material before assessment and become authoritative State only through a later permitted publication.

The bounded `changekernel.container-candidate-batch@1.0.0` contract uses source-qualified entity identities, versioned host-declared entity types, whole values and explicit links. A null expected version means required observed absence. A non-null expected version binds an existing entity; a null proposed value then means deletion. Every proposed link must point to a surviving entity in the batch or an explicit versioned dependency. This checks the declared graph only: it does not discover hidden dependencies, enforce incoming relationships outside that graph, or establish domain or aggregate constraints.

The host installs a bounded type definition with an expected prior digest. This declares draft interpretation, not adopted Check policy, native schema migration or permission to publish. Definitions and candidate grounds remain retained when later definitions change. The first type declaration supports named fields with JSON value kinds; it does not claim full native-schema or nested-domain validation. Canonical input limits reject unsupported values and non-normalized Unicode rather than silently modifying them. Effects and dependencies are sorted and unique; each batch permits at most 64 effects, 64 dependencies and 1 MiB of admitted text, with a separate 1 MiB bound for retained observations.

The SQLite adapter retains the entire batch, its initial authorized observations and retry binding atomically. Retry identity covers container, authenticated actor and request identifier; different Change, values, relationships or dependencies conflict under that identity. A new request may retain another batch under the same Change without erasing or adopting earlier ones. Exact retries return retained bytes even when current observations make them stale. Draft rows do not create or modify rows in the generic entity store or a native source.

Freshness is `current`, `stale` or `unknown`, assessed over the installed definition, source binding identities and the exact observed versions/values. It is not Check success, acceptance, a global snapshot, a reservation or a guarantee that State will remain unchanged until publication. An absent source or revoked source access blocks delivery; an explicitly authorized source returning unknown coverage permits historical retrieval but not a new preparation. Corrupt or missing retained grounds block retrieval, never trigger reconstruction. Trusted host observation bindings are synchronous, bounded and read-only; they must enforce actor and container scope on every call. They are not discovered or invoked from submitted content and provide no mutation capability.

Inspection reports unknown generic coverage before definition installation and observed empty or present generic storage afterward. It says nothing about emptiness of native sources. Candidate inspection advertises no Check or publication capability. The candidate schema is separately versioned and additive to intake v1; incompatible, partial or unversioned draft storage is refused rather than reset or silently migrated. Indefinite retained custody is currently limited by available storage, with no automatic eviction or completed retention/backup policy. Process-interruption tests are not qualification of physical power-loss durability or cross-store transactions.

## Guarded publication

1. Observe relevant State, relationships, constraints and commitments under authorized scope.
2. Prepare a durable exact candidate and any required recovery grounds.
3. Complete applicable assessment and approval outside long-held locks.
4. Enter a short guarded publication step using the binding's supported transaction, conditional update or equivalent admission mechanism; recheck authority, relevant versions and aggregate/relationship conditions.
5. Apply authorized effects and retain a trustworthy outcome receipt atomically where supported, or use an equivalent qualified outcome protocol.
6. Reconcile and record the outcome in the Change Trace log, then obtain observations needed for Review.

Sharing a database is not enough: native handlers and receipts must actually share a transaction for an atomicity claim. A file append and an unrelated native mutation do not gain a shared transaction by co-location. Do not approve prepared effects and then rerun an unconstrained program against live State assuming identical effects. Private draft persistence, requests and Work can have earlier transactions with their own rules; publication is not the first possible write.

Row versions alone do not guard collection membership, aggregate budgets or semantic conflicts. Bind relevant dependencies and use supported locking, constraints, reservations or equivalent guards. Planning may coordinate aggregate commitments when the qualified boundary controls relevant writes and serializes admission; native reservation tables are not universally mandatory. Three €400 commitments exceed a €1,000 limit even when individual assessments pass. Independent approvals against stale State are a race, and Workspace/fork IDs do not isolate the underlying resources. Outside writers require source cooperation/guards or explicitly weaker supported coverage. Worker leases are not authorized resource commitments. Long-running Changes do not hold months-long transactions or broad locks.

## Separate stores and uncertain outcomes

Where mutation and ChangeKernel storage cannot commit together, durably retain intent, candidate and recovery grounds first. The source mutation and a trustworthy source-side receipt must commit atomically, or the binding must provide an equivalent qualified outcome protocol. ChangeKernel then records the receipt reference. Reconcile that operation identity before any retry after a lost response.

A [transactional-outbox-style](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) receipt does not require a message broker. Without trustworthy outcome lookup or equivalent protection, no metadata sidecar can promise safe automatic replay. Unsupported guarantees remain explicit. Workspaces, co-located files and Git commits do not make unrelated stores one atomic transaction; external effects need their own outcome and recovery protocols.

## History, protection and recovery

Git-inspired immutable identities, versions, candidates, differences and guarded references are useful mechanisms, not a mandate to put every resource in Git. A Change can span many attempts, transactions and external effects. History supports recovery from a bad Change; backups address storage loss. Protect both against ordinary worker mutation and test restoration.

Recovery normally makes a new guarded transition. Reverting a budget should preserve a later valid rename where possible, then reassess dependent constraints. Bind covered failures, retention, concurrency assumptions and exclusions. Restoring data, compensating an external action and containing further harm are different outcomes. The following recovery obligations apply to the declared binding, not every possible outside consequence.

## Recovery and continuation obligations

Declare covered resources/effects, failure assumptions, retention, concurrency conditions, backup/restore support and exclusions. Protect required grounds before effects and preserve independent recovery/operator access when work can disable its controller. Whole-database restoration can destroy later valid work even within one Workspace; conflicts with later changes require investigation or authorized choice, not blind inverse patches.

Distinguish authorization, launch, observation, retained execution result, attempted write, committed receipt and observed State. Reconcile source outcomes and live process/provider custody separately. An expired lease, absent process-local tracking or a worktree is not proof of quiescence. Unsupported outcome lookup prevents claims of safe automatic replay. Record original failure, attempted repair, actual resulting observations and unresolved consequences; recovery success need not complete the original goal.

A fresh worker recovers intent and purpose, relevant definitions/policy, exact assessments, candidates, commitments, Work, outcomes and adopted guidance. Verify current access and freshness before continuing. Historical retrieval does not adopt policy or launch missing work. Missing, private, expired or corrupt grounds limit assurance; never recreate them by rerunning models or effects.

Initial adoption of an existing source records an honest baseline, not fictional prior Changes. Supported outside writes are drift. Synchronization binds source-specific versions, scope and coverage; it does not turn unrelated stores into one transaction. Git bindings retain required objects/refs and account for history rewriting or missing remote metadata. A host merge flag is not semantic acceptance, and incoming artifacts need assessment of the actual combined candidate. Reads do not silently repair State; remote disclosure, publication and deployment require their applicable authority.

Retain exact Evidence subject, source/version/passage, method, observation time, assumptions and limits. Trace references need durable authorized custody; export cannot copy private execution storage indiscriminately. Authorized redaction/deletion can limit later verification and must be reported honestly. Rebuildable indexes or embeddings cannot recreate missing source bytes. Assessment reuse follows the [Check contract](checks.md#efficient-evaluation-and-reuse), not merely byte equality or the presence of a favorable citation.

The richer source, intent-revision and memory contracts above describe desired behavior, not capabilities silently added to the current adapters. The retired TypeScript reference intake used an application-supplied SQLite file, separately from its candidate-batch interface. Its implementation and tests remain in Git history, not the current package. `changekernel.container-intake@1.0.0` retains an explicit owner, exact What/Why text and one retry-bound proposal per request. Its `awaiting-assessment` state is not Decision approval, a managed value or a publication receipt. Transactions bind intake and its retry identity in one row; reopening never clears it. The host authenticates the actor for each call and protects the file; no self-asserted actor or inferred membership grants access. This is not a generalized native-source adapter, qualified physical crash guarantee, complete retention policy or engine-wide store selection. Other storage interfaces, upgrades and broader transaction integration remain unselected and unqualified. This document does not generalize existing Git-shaped ports by name alone. The [primary design](../../product/changekernel.md) owns the overall model; [execution](agent-execution.md) owns worker custody and [release qualification](package.md#qualification) owns the required proof.
