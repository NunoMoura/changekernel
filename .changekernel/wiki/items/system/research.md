# Research and Hypotheses

This page retains inspected evidence, counterexamples and candidate mechanisms. It does not define the intended product or release permission. [Product intent](../product/changekernel.md), the four component contracts and the [phased plan](../product/plan.md) own those decisions. Research acceptance means that a bounded report was reviewed; it does not establish implementation, adoption, runtime qualification or deployment authority.

## How to use evidence

Separate four claims: **wanted** (the user selected an outcome), **hypothesized** (a mechanism may deliver it), **observed** (a specified experiment or inspection supports a bounded statement), and **qualified** (the exact supported release/profile passed its applicable acceptance). User intent is not proved by an experiment, and a source counterexample is not a complete runtime evaluation. Record the exact subject, assumptions, useful positive case, consequential negative cases, observed result, limits and independent verdict. A falsified hypothesis is a useful result: narrow, replace or reject it before dependent work proceeds.

The plan owns tests for the current core hypotheses. The research below is retained for future capability choices; none is a prerequisite merely because it was investigated. Do not repeat broad surveys or start privileged/runtime experiments without a concrete consuming capability and the required authorization.

The local Pi package identifies itself as 0.87.1; upstream tag `v0.87.1` resolves to commit [`f07218c4d4bbc12bef056a7058c3dd49dfe41abe`](https://github.com/earendil-works/pi/commit/f07218c4d4bbc12bef056a7058c3dd49dfe41abe). The observations below concern that pinned upstream source, not a reproducibility claim about the installed binary or its extensions. Read the [format specification](https://github.com/earendil-works/pi/blob/f07218c4d4bbc12bef056a7058c3dd49dfe41abe/packages/coding-agent/docs/session-format.md), the complete [SessionManager implementation](https://github.com/earendil-works/pi/blob/f07218c4d4bbc12bef056a7058c3dd49dfe41abe/packages/coding-agent/src/core/session-manager.ts), and selected upstream test source; no Pi test suite, crash experiment, package installation or imported upstream implementation was run. This is a source comparison, not independent runtime qualification or a new acceptance verdict.

### Transferable patterns

- **Typed, addressable records with explicit format versions.** Pi has a versioned session header and typed entries with `id`/`parentId` lineage. Its shape illustrates how a readable JSONL file can support inspection and replay without a database. The particular chat entry types, ID generator and conversational tree are not ChangeKernel contracts. An entry ID identifies a record; it does not supply original-request idempotency or authority.
- **Keep recorded grounds separate from the view built from them.** `buildSessionProjection()` returns both the selected source entries and their model-visible contributions. Compaction and `context_edit` records alter future context without replacing the targeted raw entries. This is a useful model for provenance-preserving Views: a summary can help navigation, but cannot replace accepted intent, receipts or evidence. Pi's compaction prompt/tool checkpoint is a context snapshot, not a durable-acceptance checkpoint.
- **Rebuild navigation indexes from records.** `_buildIndex()` reconstructs entry and label maps and the current leaf on load. Derived indexes need not become another authoritative history store. ChangeKernel still has two authoritative domains: native application State and accepted Change Trace records; custody/acceptance controls and evidence support the latter.
- **Separate operations from raw storage primitives.** Pi exposes distinct append methods and context/navigation methods. For ChangeKernel, keep the typed producer, accepted-record decoder and projection consumer cohesive, but do not expose Pi-style arbitrary custom entries or raw append as a client authority path. Existing closed request/result semantics remain binding.

### Behaviors not to inherit as Change acceptance

| Observed Pi behavior at the pinned source | Consequence for Change Traces |
| --- | --- |
| `newSession()` creates in-memory state and a prospective filename. For a new, unflushed session, `_persist()` defers the first disk write until an assistant message exists. Already-flushed sessions, including explicit empty-file initialization, follow different paths. | Capturing human intent cannot depend on a later model response. Opening must establish the selected durable grounds before an acceptance-bearing response; a session filename or in-memory entry is not a receipt. |
| `parseSessionEntryLine()` skips malformed JSON; `loadEntriesFromFile()` keeps later valid entries and can append a newline to an unterminated tail after validating a session header. Parsing uses ordinary `JSON.parse`, not duplicate-member rejection or full record-schema validation. | Do not silently salvage corrupted accepted history or promote a syntactically complete line to acceptance. Validate exact accepted bytes and the closed schema, reject duplicate members, and distinguish damaged accepted grounds from an unaccepted suffix using the independent control relationship. Only the selected protocol may authorize repair or continuation. |
| `_persist()` uses `writeFileSync`/`appendFileSync` and JSON serialization. That module does not implement the selected accepted-prefix checkpoint, digest and explicit file/parent-directory synchronization protocol. `_appendEntry()` updates memory before attempting persistence. | Synchronous JavaScript I/O is not the Change acceptance boundary. | `_loadEntries()` can migrate old entries and `_rewriteFile()` opens the session with `"w"` and reserializes it. `SessionManager.open()` can initialize an empty file or prepare a new session for a missing path. | Inspection/reopen must not silently rewrite accepted history or treat lost custody as first use. The independently granted provisioning path is distinct from reopening an existing Change. Later format migration requires its own exact compatibility and recovery decision. |
| `appendMessage()` generates a new entry ID on each call. `branch()` changes the active leaf; `getTree()` can display orphaned entries as roots. | Addressability and conversational branching do not prove exact original-key retry, accepted-chain completeness or rollback of native effects. A different conversation path cannot erase a real action. Do not introduce a branching engine or accept orphaned grounds merely to resemble Pi. |
| The loader reads fixed-size chunks but accumulates a pending line and the parsed entry set; a discovery scan limit is not a complete input-memory bound. | Keep explicit input/record/capacity bounds. Chunked I/O alone does not establish bounded decoding; broader indexing/discovery optimization is not part of the single-slot increment. |

These tests were read, not executed, and their expectations are not copied into ChangeKernel's acceptance suite.

**Disposition.** Borrow the record-to-projection separation and inspectable versioned structure as reference ideas. The [consumed opening profile](components/state.md#consumed-opening-profile) already supplies the stricter acceptance, custody, authorization, canonical-decoding and retry requirements; this comparison does not amend them, adopt Pi/Node dependencies, qualify the new Rust writer or add a third History subsystem. Use the counterexamples when reviewing the actual opening → inspection → fresh-process reopen → original-key retry implementation. Defer conversational trees, context compaction and discovery infrastructure unless a later consumed capability needs them.

## Repository-contained worker sandbox: Rust Landlock direction

The prior Linux containment investigation selected **a Rust-owned launcher using upstream Rust Landlock** as its baseline candidate, under the [State-access and Change-authorization model](../product/changekernel.md#state-access-and-change-authorization). This mechanism is now deferred; it is not the first core implementation assignment. Reuse existing native resource permissions and narrow them for the admitted Work; do not maintain competing filesystem ACLs or change repository ownership to simulate delegation. Prefer upstream integration. Consider a maintained fork only for a demonstrated library defect or missing binding that cannot reasonably be resolved upstream; review the exact change, license, maintenance and tests first. A library fork cannot add a missing kernel enforcement capability.

Required restrictions are hard requirements: unsupported rights, incomplete enforcement or failed setup must prevent untrusted execution, with no unsandboxed or best-effort fallback. Select the exact crate/dependency closure, supported kernel features, launch subject and operation profile through component review and qualification; these are not established by Rust memory safety, an installed LSM name or successful ruleset creation. Apply restrictions before untrusted code or authority handles become reachable and cover all execution threads and descendants. Filesystem enforcement alone is not credential, process, IPC, network or resource containment.

This direction concerns untrusted worker execution, not authentication of a privilege-changing source helper. The BPF-LSM admission investigation below is retained evidence, not the selected worker sandbox or an automatic dependency of Landlock. No further BPF/artifact follow-up is implied. At the time of this investigation, excluding unrestricted same-account history tampering was not adopted for that stronger host guarantee. The current first trusted-host profile explicitly has a narrower threat model; it does not satisfy the older service contract or invalidate this counterexample. A sandbox result cannot resolve source authentication or [custody/recovery](components/state.md#file-first-change-trace-custody) by itself.

Do not generalize an old Landlock implementation's socket gap to every kernel/library. Codex's inspected [legacy function](https://github.com/openai/codex/blob/60947e234156ac12bdb7fba2477d3965f166bd34/codex-rs/linux-sandbox/src/landlock.rs#L147-L173) uses ABI V5, best-effort enforcement and a read grant for `/`. Current [kernel documentation](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/Documentation/userspace-api/landlock.rst) includes newer pathname-socket restrictions as well as abstract-socket/signal scoping. Required rights must be matched to an actual qualified ABI. Files opened or received before restriction retain their properties; applying a ruleset does not close or revoke those capabilities. Namespaces, native credentials/groups, special filesystems, metadata operations and object aliases still require their own coverage.

The required policy direction bounds worker source access to the assigned repo and explicitly declared dependencies, with protected subpaths; required tools/libraries are selected read-only exceptions, and scratch/cache is per-job private storage. Other repositories, credentials, custody/history/control files and installed controller settings must remain outside the worker's permitted access. An entire repository is a maximum possible scope, not an automatic grant when Work delegates only a smaller part. Distinguish read containment from write containment: granting reads over `/` is insufficient. Landlock restricts supported operations; it does not construct an empty mount view or automatically hide every filename/metadata observation. The exact confidentiality and mutation surface must be stated and proved rather than advertising namespace invisibility. Repo-contained secrets need explicit protection. Existing hardlinks/shared objects, symlink or mount aliases, missing protected paths and linked-worktree Git metadata must not accidentally broaden access. The exact supported operating profile and public format remain unsettled.

Writable scope authorizes bounded preparation, not arbitrary semantic success. Before direct writes, establish whether the exposed tree is permitted candidate material or an authoritative publication target and which effects are admitted. Do not give an untrusted producer a raw path that bypasses the promised guarded publication route. OS access decisions cannot distinguish an approved refactor from destructive edits inside the same writable tree; the engine's candidate, Check, publication and outcome responsibilities remain independent.

Every untrusted filesystem route must enter the boundary before authority or secrets are exposed. Wrapping a shell alone does not sandbox an unsandboxed editor tool or generated code running in the trusted host. Close unintended descriptors, terminal-control and host-process/socket routes; any retained broker channel permits only typed current delegation, not arbitrary unsandboxed commands or file requests. Keep model-provider and SSH credentials outside the worker. Network/package/remote access is an explicit separate policy, not inferred from repo access. Recursive workers inherit the same or narrower policy, and cancellation/result acceptance covers descendants rather than only the first process exit. Setup failure, missing required features or unsupported context refuses before execution; no silent unsandboxed fallback or best-effort weakening.

The Rust/Jaz-inspired runtime can coordinate bounded reasoning and expose authorized history projections while routing untrusted tool/code execution through the qualified launcher. This does not embed Python Jaz or expose the private Trace folder. The backend still validates typed operations and owns accepted records; filesystem containment proves neither correct intent, truthful outcomes nor safe modifications within the writable repo. It can help prevent worker API bypass only after all file/descriptor/process/IPC routes qualify; it does not prove custody freshness, source continuity or immunity from an unrestricted owner outside the sandbox.

Passive host inspection found `/usr/bin/bwrap`, package `bubblewrap 0.12.0-1`, enabled user-namespace indicators and active Landlock on kernel `7.2.5-4-omarchy`. These are availability indicators, not actual namespace/ABI/policy enforcement or installed-source correspondence. The research ran no sandbox, namespace or Landlock syscall experiment, installation or build and changed no dependency. That historical direction approval permitted bounded contract preparation, not an installed sandbox claim. It is not a current assignment or authorization to resume experimentation. Settle exact read/write/tool/scratch/control and linked-worktree policy, then separately authorize disposable external nonsecret qualification covering allowed repo operations, denied outside access/mutation, aliases, descriptors, host channels, descendants/cancellation and unsupported/setup failures. Broader execution, dependency locking, privileged experiments and release/controller actions retain their applicable gates; no worker may infer them from this design choice.

### Landlock coverage limits and required composition

The inspected Landlock-only construction cannot satisfy the complete repository-containment requirement. This is a concrete kernel-coverage limit, not evidence that the Rust direction should be abandoned or that a Rust wrapper fork can supply missing kernel enforcement.

**Metadata operations are the first gap.** The inspected [UAPI warning](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/include/uapi/linux/landlock.h#L405-L413) and [filesystem hook table](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/security/landlock/fs.c#L2085-L2111) do not provide scope enforcement for the chmod/chown/xattr/timestamp families or universal metadata visibility. If native policy permits a user to chmod an owned file outside the admitted tree, a ruleset handling every exposed filesystem right with no outside grant does not add a chmod prohibition. Other native policies may still deny it. Rust's [`FullyEnforced`](https://github.com/landlock-lsm/rust-landlock/blob/3dd4c82bf0a852086747e434aae9aa4b8ffe590d/src/ruleset.rs#L43-L89) describes requested Landlock restrictions, not complete task-scope enforcement. The counterexample is source-backed under stated native rights; it is not a demonstrated installed escape.

**Broad parent grants do not implement protected child names.** Within one layer, [matching allow rules combine](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/Documentation/userspace-api/landlock.rst#L350-L364); a reduced child rule is not a subtractive deny. More importantly, [same-parent rename checks the parent's structural rights without requiring Refer](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/security/landlock/fs.c#L1224-L1288). Granting a repo parent `MakeDir | RemoveDir` can permit renaming its protected directory to a sibling name. Extra layers do not distinguish two sibling names when both operations require the same parent rights. The launcher must reject an unrepresentable exclusion or use a separately reviewed boundary. Withholding structural rights on protected parents and preparing candidates in separately admitted writable areas is one possible composition, not an adopted repository relocation, mount profile or replacement for necessary root publication operations.

A complementary native syscall filter is a possible way to deny unsupported mutation families globally. It is not a selected dependency or complete solution: ordinary [seccomp cannot dereference pathname pointers](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/Documentation/userspace-api/seccomp_filter.rst#L17-L38), so it cannot implement a safe pathname-specific chmod exception. Any proposal must cover architectures/compat entry points, descriptor/at variants, relevant ioctls and alternate submission paths such as io_uring. Required metadata operations must use a separately qualified scoped operation or make the requested tool/profile unavailable; silently breaking them is not full tool support. No filter, broker, kernel change or renewed privileged BPF admission investigation is authorized by this finding.

Use the upstream crate's strict mechanisms correctly: set [`HardRequirement` before affected builder calls](https://github.com/landlock-lsm/rust-landlock/blob/3dd4c82bf0a852086747e434aae9aa4b8ffe590d/src/compat.rs#L555-L590), prohibit per-rule weakening, propagate every failure and verify the actual restriction status and `no_new_privs` before payload execution. Do not use [`path_beneath_rules`](https://github.com/landlock-lsm/rust-landlock/blob/3dd4c82bf0a852086747e434aae9aa4b8ffe590d/src/fs.rs#L607-L627) for required anchors without accounting for its silently skipped opening failures. An O_PATH anchor establishes neither current source authority nor alias-safe identity. A verified single-thread setup path or hard-required all-thread enforcement is needed; a failing partially configured child exits rather than running a fallback or mutating the trusted parent into its launch context.

The inspected crate exposes filesystem/domain features through ABI v9 and [TCP network rights](https://github.com/landlock-lsm/rust-landlock/blob/3dd4c82bf0a852086747e434aae9aa4b8ffe590d/src/net.rs#L33-L65); the inspected newer kernel describes [UDP rights from ABI v10](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/Documentation/userspace-api/landlock.rst#L797-L808). A missing Rust binding is a different problem from missing kernel enforcement. Neither TCP denial nor the crate's version alone qualifies an offline profile or selects a kernel minimum. Required network, descriptor, IPC, process, credential, alias, resource and descendant-cleanup controls still need complete composition. Less-restricted outside processes are not excluded from tracing a worker merely because the worker entered Landlock; its domain-directional policy is not protected-reader provenance or same-account custody protection.

Before implementation release, resolve these specific gaps and the [source-result evidence boundary](#native-enforcement-and-source-result-evidence), then qualify exact positive and negative cases in an explicitly authorized disposable nonsecret trial. Include allowed candidate operations, outside content and metadata attempts, protected-parent rename, aliases, inherited/transferred handles, linked Git topology, setup failure before payload, descendants and cleanup. The bounded investigation did not install/build/run a fixture, select a filter or fork, or qualify a complete operating profile. Refusal of every task is not evidence that ordinary supported work succeeds.

### Native composition versus a microVM challenger

A complete native candidate can combine Landlock and scalar syscall restrictions with a closed preparation filesystem view, read-only imports, native ownership protecting every reserved-name ancestor, and protected resource/descendant supervision. Linux's [sticky deletion checks](https://github.com/torvalds/linux/blob/551c722f40809618230001baccf219193e22fc5a/fs/namei.c#L3645-L3719) can distinguish protected children from ordinary writable siblings where Landlock parent grants cannot. This is a proposed composition, not an adopted mount/ACL layout: the reviewed recipe requires privileged setup in the initial user namespace, protected bootstrap/reaper artifacts and faithful original-context admission. It does not change ownership of the authoritative repository, make a root reader a substitute for the native source subject, or close the earlier helper-admission gap. Workflows requiring mutation of a reserved ancestor must be rejected unless separately represented and qualified.

Useful tool behavior must constrain the policy as well as negative cases. For example, Rust 1.88's [process-spawn fallback](https://github.com/rust-lang/rust/blob/6b00bc3880198600130e1cf62b8f8a93494488cc/library/std/src/sys/process/unix/unix.rs#L58-L141) uses an anonymous socket pair whose [read path calls `recv`](https://github.com/rust-lang/rust/blob/6b00bc3880198600130e1cf62b8f8a93494488cc/library/std/src/sys/net/connection/socket/unix.rs#L284-L303). Allowing socketpair creation while denying every socket-receive route can break ordinary subprocesses. Any exception depends on the exact architecture/libc path and proof that all reachable socket descriptors are confined private channels; a syscall name or recycled FD number is not that proof. Freeze and exercise the consumed launcher policy, not an unused plan validator. Published package bytes and repository snapshots also remain distinct subjects: published Landlock 0.4.7 declares [commit `62fec0f1521e4ab7f697752c1f324b725fe643d5`](https://github.com/landlock-lsm/rust-landlock/blob/62fec0f1521e4ab7f697752c1f324b725fe643d5/Cargo.toml), whose ruleset body differs from the earlier inspected repository snapshot.

Microsandbox 0.7.5 remains an unadopted alternative for bounded candidate execution, not a replacement for native source authority or ChangeKernel review/intake. Its [Rust SDK](https://github.com/superradcompany/microsandbox/blob/b6de129d5d0bc7c6b3c61997b24236fbb8d7bd38/sdk/rust/Cargo.toml) supports a proposed local-only, defaults-disabled selection, but the separately provisioned runtime, firmware, guest/kernel/tool image, KVM access and protected host controller still require exact-subject qualification. Defaults and [build-time acquisition](https://github.com/superradcompany/microsandbox/blob/b6de129d5d0bc7c6b3c61997b24236fbb8d7bd38/sdk/rust/build.rs#L13-L151) are not permission to download or execute artifacts. No selected dependency closure, Rust 1.88 build, license closure or operating-profile pass follows from source inspection.

A VM still needs a useful and protected guest layout. A root payload, uniformly writable candidate tree or the upstream Restricted label does not protect the guest agent, evaluator, control devices or reserved ancestors. Offline must cover separate [host-vsock routes](https://github.com/superradcompany/microsandbox/blob/b6de129d5d0bc7c6b3c61997b24236fbb8d7bd38/crates/runtime/lib/runner/vm.rs#L2440-L2490), not just disable a NIC or proxy. Guest-local IPC need not mean external access. A wholly read-only guest root also conflicts with the inspected unconditional [boot-time `/etc/hosts` write](https://github.com/superradcompany/microsandbox/blob/b6de129d5d0bc7c6b3c61997b24236fbb8d7bd38/crates/agentd/lib/network.rs#L534-L575); any writable boot-state exception must remain isolated from payload authority. Guest termination, SDK drop and a synthetic exit status are not observed whole-runtime cleanup. These are concrete composition costs, not evidence of a demonstrated VM escape.

Compare either route against the same editor/Git/offline-Cargo positive workflow and outside-access, metadata, topology, handle, process, network, setup-failure and lifecycle cases. Keep native ingress, exact-subject Check, guarded publication, current disclosure and original-key recovery separate: the inspected [passthrough host I/O](https://github.com/superradcompany/microsandbox/blob/b6de129d5d0bc7c6b3c61997b24236fbb8d7bd38/crates/filesystem/lib/backends/passthroughfs/unix/file_ops.rs#L28-L175) does not authenticate the original host-native reader from guest context. Neither containment option resolves that common prerequisite. At that comparison checkpoint the Rust/Landlock direction and Jaz-inspired execution were unchanged; the comparison adopted no new evolution layer, backend dependency, privileged profile or experiment. The current core-first plan defers both mechanism choices without claiming to have qualified them.

## Ordinary-client host direction

This historical host proposal targeted the [ChangeKernel-owned Rust terminal client](../product/changekernel.md#operator-console-for-development), separate from eligible worker harnesses and using the shared backend. Preserve ordinary user workflows and existing repository locations where the qualified binding can support them. Pi remains the source-development harness and a retained integration adapter; compatibility with an ordinary Pi client does not make Pi the product frontend or a required engine dependency. This is the preferred design direction, not a claim that arbitrary sessions, filesystems or execution environments are already supported. Before requiring a managed login, repository relocation or a permanent UID-nonreuse policy, identify the concrete unsatisfied guarantee, assess a narrower mechanism and expose any unavoidable workflow cost. An administrator-installed custody service and a bounded local recovery limit were the selected premises for this investigation. They are now a deferred stronger profile, not core delivery prerequisites. The findings select neither a privileged helper implementation nor deployment permission.

### Separate the frontend from trusted execution

A frontend submits bounded typed input and displays authorized results. It need not be the source of authenticated owner identity, source-permission evidence, accepted assessments or effect receipts. The backend obtains those through protected native authority and custody paths. Therefore, protecting the writer does not by itself require replacing the user's login or trusting the entire frontend process. The existing [packet adapter](components/native-profiles.md#linux-local-packet-ingress) supplies only its documented peer/byte observations; it does not establish enrollment or human intent.

Preserving an existing frontend also does **not** qualify its unrestricted shell, extensions or generated code as a governed worker. Protected Work needs a separately admitted execution boundary and attributable results. An ordinary client must not be able to launder a restricted worker's request into broader owner authority: the worker must lack access to owner credentials, owner-command IPC, client process/handle control and any forwarding path that would grant that authority. A worker route carries its protected Work/delegation scope and cannot choose the owner route using payload fields. The exact worker mechanism remains a prerequisite. Do not silently change a same-UID worker into a trusted owner process merely to preserve session reuse.

The preferred composition keeps three roles distinct:

| Role | Responsibility | Forbidden substitution |
| --- | --- | --- |
| Ordinary client | Submit intent/typed requests and inspect authorized views through the protected endpoint. | Client code, PID, session name or claimed actor is not a trust grant; client observations are contributions until independently established. |
| Native source-access helper | Perform a bounded operation under a freshly established, faithful native authority context and exact source binding; return attributable observations/outcomes over a protected channel. | No custody handles, generated code, arbitrary shell or source access under the service's greater rights. |
| Custody writer | Authenticate current enrollment/disclosure, enforce domain controls, reconcile exact retries and durably accept results under the recovery protocol. | No second authoritative helper history or privileged re-open that replaces the helper's native permission check. |

A short-lived protected helper per operation is a narrower candidate than a managed interactive login. It still needs a concrete trusted launch, credential acquisition, process/IPC protection and revocation protocol. It is not implemented by accepting a client's assertion that it ran a fixed binary. Ordinary client workflows and a protected helper are compatible design goals, not proof that the helper exists.

### Native credentials: useful observations and rejected shortcuts

Keep the actual primary and complete supplementary groups, filesystem IDs, relevant namespaces, capabilities and security restrictions in the authority analysis. Removing groups can broaden DAC/ACL access: for another owner's file in group `G`, mode `0604`, a supplementary member of `G` is denied while a nonmember receives `other` read access. Mode `0640` exercises the converse group grant. A fresh account-database lookup is not a capture of the requesting task's credentials; a different LSM subject is not automatically narrower. Any additional confinement must be proved to restrict, rather than replace, the required native authority.

| Candidate shortcut | What it establishes | What remains missing |
| --- | --- | --- |
| `SO_PEERCRED` plus per-message `SCM_CREDENTIALS` | Kernel-checked connected/sending PID and UID/GID under the adapter's constraints. | Supplementary groups, filesystem IDs, per-thread restrictions, durable account incarnation and source authority. |
| `SO_PEERGROUPS` and `SO_PEERPIDFD` | Supplementary groups from the socket's saved peer credentials and a reference to its saved peer process, respectively. | Not an atomic current sending-thread authority snapshot; no reproduction of filesystem IDs, Landlock/LSM policy, namespace view or later revocation. Reconnecting alone does not fill those fields. |
| `/proc` reads, PID pinning and before/after comparisons | Particular process observations, with lifetime pinning where correctly used. | No general proof that a task/thread did not change authority between observations and access. A pin protects process identity, not immutable permissions. |
| User-launched fixed helper or caller-opened source FD | A possible execution/descriptor path. | Trusted launch and resistance to preexisting tracing/injection; exact credential transitions; current permissions and freshness of the open. A descriptor may outlive revocation or have been transferred. |
| Service-side `initgroups`/UID switch | A newly constructed account context. | Faithfulness to the required acting context. It must not discard restrictions or exploit the group-deny/other-allow counterexample. |

A complete source-access contract must specify which native subject authorizes the operation and how that subject is obtained without client assertions. If proposing a separately authenticated user context instead of the calling task, justify its authority and preserve worker/delegation restrictions explicitly; do not silently redefine “acting user” to mean whatever context the service can create. Unsupported contexts make the source-dependent operation unavailable. Private historical delivery has its own current enrollment/disclosure checks and does not need a fabricated source context.

The source-helper path must bind current principal/enrollment, exact request and source/binding revision, operation/scope and response identity; observe credential and policy withdrawal at the required points; and keep its executable, launch configuration, descendants and result channel outside client/worker control. An independent result cannot be replaced by a typed Rust value constructed by the caller. Holding an enrollment guard cannot serialize arbitrary native ACL or namespace changes; supported observation/effect semantics still need their own point-of-use rules.

### Exec-mediated helper admission limit

A fixed set-ID helper cannot establish a faithful **pre-exec calling-thread** source context through post-exec credential checks alone. Linux v6.12, commit `adc218676eef25575469234709c2d87185ca223a`, resets saved and filesystem IDs to the effective IDs in [`prepare_exec_creds`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/cred.c#L254-L279), then assigns them again after set-ID handling in [`cap_bprm_creds_from_file`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/security/commoncap.c#L886-L973). The earlier values are not authenticated by observing the resulting helper IDs.

A concrete counterexample uses real/effective/saved group IDs `P/P/G`, with supplementary groups excluding `G`. Assume UID fields `U/U/U`, FSUID `U`, initial namespaces, a non-idmapped filesystem and no ACL, capability override or additional LSM denial. After a legitimate earlier set-GID transition, modern [`setegid`](https://man7.org/linux/man-pages/man2/seteuid.2.html) can restore effective group `P` without discarding saved group `G`; [`setfsgid(G)`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sys.c#L916-L955) is then permitted without `CAP_SETGID`. Compare that entry with an otherwise identical thread whose FSGID is `P`. Executing a UID-only helper under a distinct non-root protection identity produces FSGID/saved GID `P` for both, also indistinguishable in these fields from an ordinary `P/P/P` entry. Retaining supplementary groups and checking aligned IDs after exec does not distinguish them.

For another owner's file in group `G`, mode `0604`, entry FSGID `G` selects group denial; reconstructed FSGID `P` selects `other` read. Restoring the caller's real UID for filesystem access therefore grants a read that the original point-of-use context denied. Mode `0640` gives the converse result, so guessing or adding `G` is not uniformly conservative either. The [permission-class selection](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/namei.c#L345-L382) and [filesystem/supplementary group test](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/groups.c#L227-L235) are kernel behavior, not account-database inference. An owner-file-only restriction is insufficient too: entry UID tuple `U/U/D` with FSUID `D` can select `D` using its [saved-UID permission](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/sys.c#L874-L904); restoring FSUID `U` after exec reads a `U`-owned `0600` file that this entry context denied.

This is a logical counterexample to faithful current-subject authorization, **not** a claim that FSGID/FSUID alone confines a malicious worker: those example tasks retain IDs they could select themselves. It is not an installed vulnerability, a privileged experiment, erasure of Landlock restrictions or an impossibility result for every helper. Refusing unsupported entry contexts remains valid, but post-exec alignment cannot prove that the entry was supported. Caller assertions, account reconstruction or a PID/socket observation do not recover the lost proof.

A possible narrower repair is trusted admission before exec loses those fields, atomically bound to the actual executing thread and fixed installed image. Kernel/LSM-mediated admission is an identified candidate, not a selected API, policy, kernel minimum or deployment dependency. It would require privileged policy custody, support/version qualification, fail-closed installation/removal and explicit refusal of unsupported contexts; complete startup, namespace/restriction preservation, IPC, revocation and worker anti-forwarding still need proof. Do not silently impose that cost. Separately authenticated owner authority is a different subject and requires an explicit authority/authentication contract, not a reinterpretation of this failed caller-context path. Account lifecycle, source continuity and recovery remain independent gates.

The mixed-ID helper also has a distinct IPC obligation: [`SO_PEERCRED`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/core/sock.c#L1654-L1666) exports saved peer effective IDs, while [automatic SCM credentials](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/include/net/scm.h#L91-L103) use sending real IDs. At real UID `U`/effective UID `H`, those observations differ and the existing packet adapter must reject their mismatch. Linux permits [explicit SCM credentials](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/core/scm.c#L47-L65) naming a sender's effective/saved ID, but that fact neither selects a new helper protocol nor authenticates durable user enrollment. The accepted packet contract remains unchanged.

### Pre-exec BPF admission candidate, not an adopted dependency

Read-only Linux v6.12 inspection identifies a concrete admission point: [`bprm_creds_from_file`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/exec.c#L1667-L1674) runs at the start of [`begin_new_exec`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/exec.c#L1222-L1248), before installation of the new credentials. A system-wide `BPF_LSM_MAC` program at that hook could inspect the **executing thread's old `current->cred`**, obtained through [`bpf_get_current_task_btf`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/trace/bpf_trace.c#L771-L782), rather than the already-normalized proposed `bprm->cred`, a group leader or a client snapshot. The old credentials remain current until [`commit_creds`](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/exec.c#L1374-L1399). This avoids the specific R13 information loss; it does not itself reproduce every native restriction or authenticate enrollment.

A narrow **candidate** entry profile would require aligned real/effective/saved/filesystem IDs, no capability-based widening, an exactly supported namespace/root and LSM configuration, and no unsafe tracing, shared filesystem context, seccomp or `no_new_privs` condition. It would preserve the complete inherited supplementary groups, not rebuild or subtract them. Unsupported entries would be refused, not launched with fewer restrictions or forwarded into an owner session. The aligned-ID check must occur on the old thread credentials: applying it to `bprm->cred` or helper startup state repeats the accepted counterexample. These profile restrictions are proposed costs, not selected product requirements. Any LSM domain transition must separately be shown faithful or narrowing; a BPF denial hook cannot establish that for arbitrary policies.

The hook supplies the actual file object used to derive exec credentials. Binding must cover that protected, lifetime-held object and exact installed bytes, mount context and policy version—not a pathname, `argv[0]`, numeric inode pair or caller-provided digest. A qualified static ELF helper is a narrower candidate than trusting a caller-visible loader path: the [ELF implementation](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/fs/binfmt_elf.c#L860-L903) opens `PT_INTERP` in the execution filesystem view. Static format, absence of generated code and protected installation must be established from the exact artifact, not asserted by the client. The helper still needs protected startup, descriptor cleanup, bounded request handling and process protection before source access.

**A dynamically attached denial program alone is insufficient.** The [unattached BPF hook](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_lsm.c#L20-L30) returns its default, which is [zero for the exec-admission hooks](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/include/linux/lsm_hook_defs.h#L52-L56). Other enabled policy can still deny exec, but this absent gate supplies no refusal. The [last link reference releases its program](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L2995-L3054); LSM links use the [tracing release operation](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L3215-L3275). An unpinned loader can therefore die while the installed helper remains executable. A helper launched through that gap can outlive reattachment with its original fields already lost. Checking that a gate is attached only when the successor accepts a connection does not prove that this helper passed it. Neither the `CONFIG_BPF_LSM` flag nor a bpffs filename is positive per-exec admission evidence.

Existing task-local storage suggests a narrower positive-evidence composition; this is **not** a frozen receipt schema or an implemented protocol:

| Boundary | Candidate mechanism and required refusal |
| --- | --- |
| Original thread and image | The protected exec hook checks the old credentials and fixed file, then records bounded pending admission in that task's storage under an exact policy epoch. Allocation/read failure or an unsupported context denies admission. Other BPF/LSM denials must remain denials. |
| Credential commit | The [committed-credentials hook](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/security/security.c#L1317-L1331) can finalize entry evidence, but is not successful userspace startup or source/effect evidence. Failed exec must leave no usable authorization; new exec must invalidate or replace old evidence. Coherent publication/lookup and nonleader-thread exec must be proved. |
| Kernel subject lookup | [Task-storage lookup accepts a pidfd key](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_task_storage.c#L90-L122); it is not a PID-number map. A fresh, single-threaded helper connection could provide a [kernel-saved peer pidfd](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/core/sock.c#L1856-L1887), paired with the actual message sender and current exec evidence. Opening a PID from an earlier packet, accepting a supplied pidfd or transferring a socket cannot substitute for this binding. |
| Receipt custody | Only the protected gate may create usable evidence. A compatible plain-value map could be [frozen against userspace writes](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L2060-L2093), with [syscall write permission removed](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L838-L849). Do not add `BPF_F_RDONLY` to task-storage creation flags as a substitute for freezing: its [creation mask](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_local_storage.c#L18-L18) and [allocation checks](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_local_storage.c#L671-L695) restrict flags, require `BPF_F_NO_PREALLOC`, BTF and bounded values. The [freeze interface](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/include/uapi/linux/bpf.h#L604-L614) explicitly permits subsequent BPF writes. Exact map/value compatibility and freezing still require qualification. Client/helper/worker access to program, map, link and pin handles is forbidden. |
| Fork, restart and policy replacement | A [new task starts without task-local storage](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/fork.c#L2338-L2341). Fork does not itself grant a receipt. Replacement policy/map epochs must reject surviving old receipts; missing, pending or stale evidence blocks source access. Pins may retain object references across loader failure, but supply neither reboot continuity nor a replacement policy's authority. |
| Writer and source operation | The helper must receive protected authorization for the exact current request/source/operation before any source-dependent work. The writer retains and verifies the exact approved links, maps and configuration through the operation/delivery guard. Missing or withdrawing policy closes admission before releasing those guards; uncertainty after an effect enters the existing recovery/reconciliation rules. Current enrollment, source permissions and worker scope remain separate checks. |

The [packet adapter](components/native-profiles.md#linux-local-packet-ingress) exposes neither a peer-pidfd admission receipt nor a helper authentication protocol, and mixed-ID automatic message credentials still do not match its existing contract. No API change follows from inspecting these kernel facilities. A kernel receipt would prove only the checked exec entry in its policy epoch—not human intent, account incarnation, permission freshness at a later file access, exact source identity or an accepted result. The helper must use the inherited faithful source context at point of use; it must not read as its protection identity or the writer.

This candidate adds a real operating prerequisite: supported BPF-LSM hooks enabled in the active [LSM order](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/security/Kconfig#L265-L277), appropriate [kernel configuration](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/Kconfig#L92-L102), BTF/verifier compatibility, a protected privileged policy loader, protected artifact/map/link custody, and fail-closed boot, restart, removal and update handling. BPF build and GPL-compatible program requirements also belong in exact-artifact qualification, not an invisible new dependency. Sandboxed sessions whose `no_new_privs` forbids the protection-identity transition cannot be made supported by clearing the bit or forwarding into a less restricted frontend. The support/refusal profile needs user approval. A built-in gate trades this dynamic-policy lifecycle for kernel build/distribution custody; it is not a free repair or a selected alternative.

No BPF program was compiled or loaded and no policy, helper or kernel was installed in this assessment. Source inspection is not verifier, installed-kernel, protocol or release qualification. The user previously approved a bounded design-only follow-up on exact admission evidence/lifecycle, supported/refused contexts and administration costs. Its result is retained below. That completed authorization is not permission to resume investigation, adopt its restrictions or install an operating dependency. The mechanism and its limitations must return for review before adoption or implementation release; installation, privileged experiments and deployment remain separately gated. Ordinary frontend workflows and repository locations remain goals, not proof of this candidate's compatibility. Separately authenticated owner authority was a different, unselected contract in this investigation. The current core profile explicitly selects trusted host-established context instead of claiming faithful reconstruction of an arbitrary caller; it does not qualify this BPF proposal. The stronger profile's anti-forwarding, account-lifecycle and reboot-continuity questions, and the separate native-analyzer gap, remain unresolved.

#### Positive-evidence composition and first artifact gate

The approved design-only follow-up produced one conditional composition, not an adopted dependency, support profile or implementation. Its first missing input is **exact installed-artifact protection**. The kernel's [FD-based inode-storage update](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_inode_storage.c#L90-L104) resolves the loader's actual file descriptor; the exec gate can use [inode-local lookup](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_inode_storage.c#L132-L162) to recognize that same live object. This is stronger than a client pathname or inode tuple, but it does not establish approved bytes, static format or an immutable active epoch. A tag can survive an in-place change to the inode before execution, and holding a read descriptor alone does not prevent the change. The marker-only variant is insufficient. Qualification must independently verify the exact held artifact and protect its bytes/configuration throughout the epoch; an administrator's update must withdraw old authority and stage a separately verified object rather than modify the active marked inode. No concrete installation/protection scheme is selected by this finding.

The candidate would use five private objects: an inode-local asset map, frozen configuration, a protected per-epoch ticket counter, and separate task-local **ENTRY** and **COMMIT** maps. These names describe reasoning roles, not a public schema. All syscall-write surfaces would be frozen before attachment. Only the exact approved bytecode could create the complete task records; it would never mutate, delete/recreate or upgrade published values. Tickets would be unique within the held epoch, never reset/wrap/reused, and supply correlation rather than a principal, secret or second authoritative history. Complete supplementary groups must fit the qualified bound or admission refuses; truncation is forbidden. Local storage's required `max_entries=0` is not a global memory cap, so allocation failure and rate/memory-exhaustion control remain separate obligations.

This separation addresses a concrete publication risk, conditionally: [element initialization](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_local_storage.c#L75-L107) precedes [publication](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/bpf_local_storage.c#L610-L638), while [syscall lookup](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L243-L263) copies under RCU. RCU is not a transaction with arbitrary later BPF stores. Separately initialized, subsequently immutable records avoid a changing multi-field `pending → committed` snapshot only if the exact program/handle closure enforces that immutability. A spin-lock-bearing value is not a freeze workaround: the inspected [freeze path](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/bpf/syscall.c#L2060-L2093) rejects nonempty special-field BTF records, and freezing still permits BPF writes. Exact BTF, layout, helper, atomic-ticket and verifier compatibility remain unqualified.

| Boundary | Conditional ordering and limitation |
| --- | --- |
| Bootstrap | Freeze all configuration/asset/task/counter maps before hooks can publish; attach the commit and repeat-exec-denial hooks before the final-file gate. Keep source authorization closed until the writer holds and validates the entire exact program/map/link/artifact/root/namespace closure. Installation and custody initialization remain distinct; kernel readiness is not virgin-custody or storage-health evidence. |
| Entry | The final-file gate validates the actual old current-thread context, both relevant executable objects and the exact supported mount/root view, reserves a fresh ticket and creates a fully initialized immutable ENTRY. Read/allocation/limit failures or existing mismatching evidence deny. A later policy denial can leave pending evidence but no source grant. |
| Commit and startup | The void committed-credentials hook can create immutable COMMIT only after checking ENTRY and actual installed credentials. Failed allocation/check cannot undo credential commit; the writer must refuse missing COMMIT. Credential commit is not userspace startup. A separately qualified fixed-helper startup handshake precedes any source grant. |
| Peer and sender | A fresh connection supplies kernel peer and per-message pidfds. Task-storage lookups through both must yield the same complete epoch/ticket-bound ENTRY/COMMIT pair. Bare PID equality, supplied descriptors or a saved socket alone are insufficient. [SCM validation](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/net/core/scm.c#L47-L65) can permit non-own PID assertions under `CAP_SYS_ADMIN`; a kernel-generated SCM pidfd is therefore not unconditional proof of the actual sender. The protected one-shot protocol and excluded impersonation privilege must be established. |
| Lifetime and publication | A proposed ENTRY → COMMIT → ENTRY read/equality check is over immutable objects, not a generic seqlock. The fixed helper performs no further exec, fork or thread creation; marked tasks are denied repeated exec while the exact early-hook reference is held. Exit/missing evidence refuses delivery. Snapshots are not continuous liveness/current-image or source-permission oracles. |
| Operation and delivery | Current enrollment/Work/delegation, original typed key/input, exact source/binding/scope and disclosure guards remain mandatory. A protected challenge correlates the writer instance, epoch/ticket and operation; it creates no new principal authentication. The helper retains all groups and uses its verified original filesystem IDs for native source access, not its protection identity or the custody writer. Recheck current guards/evidence before acceptance-bearing delivery. |

The accepted packet library cannot implement this composition unchanged. `serve_one` exposes only peer credentials and bytes to one callback, then releases the connection after one reply; it supplies no peer/message pidfd custody. Its receive path rejects and closes `SCM_PIDFD`, and automatic real-ID messages from a real-UID `U`/effective-UID `H` helper do not match its saved effective peer identity. A separate, manager-owned private host contract would need protected accepted-connection and ancillary-handle custody plus challenge → grant → result → acknowledgment lifetime. No signature, public protocol, byte bounds or error contract is frozen or changed here. The source reader must also be descriptor-bound and in-process under the qualified faithful context: a preliminary helper check does not qualify the existing path/subprocess observer, whose exec would normalize filesystem IDs again. Credential transitions can [reset dumpability](https://github.com/torvalds/linux/blob/adc218676eef25575469234709c2d87185ca223a/kernel/cred.c#L405-L425), so startup process protection cannot rely on a one-time dumpability setting.

The proposed context matrix remains conditional, not installed support:

| Context | Proposed disposition and visible cost |
| --- | --- |
| Non-root caller, aligned original real/effective/saved/filesystem IDs, complete bounded supplementary vector | Eligible only after exact original-thread checks and every later gate. Unaligned/root/service-identity entries and unreadable/over-bound groups refuse; groups are never subtracted or rebuilt. Native group-deny, group-grant, ACL and ancestor rules still apply. |
| Capabilities and namespaces/root | Require empty permitted/effective/inheritable/ambient capability sets, retained actual bounding set, known securebits and an exactly qualified native view bound to held root/namespace references. Unknown/idmapped/custom views or unexpected computed privileges refuse or remain unproved. Inode membership alone does not authenticate a mount alias. |
| Entry seccomp/`no_new_privs`, Landlock and other LSM transitions | Seccomp/NNP entries refuse in this candidate. Landlock inheritance is not erasure; NNP absence does not establish absence of a privileged-installed domain. Other old → new → filesystem-ID transitions need independent faithful/narrowing proof. No active LSM profile is selected. |
| Shared/multithread entry, interpreter or unverified startup | Refused or unproved. Conservative no-shared-memory checks can reject `vfork`/`posix_spawn`, creating a possible fork-based frontend-launch cost. Static ELF, exact bytes and trusted startup are prerequisites, not assertions supplied by an image tag. |
| Restricted worker, enrollment/account replacement, source/reboot continuity | Independent unproved gates. A receipt or same UID does not prevent owner-frontend forwarding, authenticate an account incarnation or establish persistent source identity. No managed login, new principal secret, permanent UID ban or repository relocation is adopted. |

Administration would require a protected privileged policy loader/supervisor, a helper protection identity distinct from source caller and custody writer, exact kernel/BTF/hook/LSM-order and GPL-compatible build/verifier support, protected artifacts and all-epoch native handle custody, admission resource control, and coordinated boot/update/removal. Privileged loading does not authorize root or writer repository operations. A loader dying before complete handoff leaves source access closed; after handoff, actual held link/map/artifact references matter, not pin names. Withdrawal closes new grants first, fences/drains helpers and retains old references until supported termination/outcome reconciliation; started syscalls/effects cannot be declared absent by releasing a link. New policy or reboot uses fresh objects and never copies old task receipts. The original retry key and [one-writer recovery limit](#first-local-recovery-admission-protocol) remain unchanged. Historical delivery retains its own current disclosure/accepted-prefix grounds rather than fabricating fresh source access.

No source publication/effect capability or arbitrary chmod-atomic revocation is established by this admission design. The exact artifact/protection gate, composed BPF program/publication, helper/startup/IPC, native reader and present source/disclosure semantics still require proof. All operating contexts of this candidate remain unavailable until their dependencies qualify. The bounded design investigation is complete; further exact-artifact design, dependency/profile adoption, implementation, installation and privileged experiments need their applicable scope/authority decisions. This evidence neither adopts those costs nor disproves other helper designs.

### Account retirement without assuming a permanent UID ban

A numeric UID and username identify neither a person nor a durable enrollment incarnation. Minting a protected principal ID does not solve authentication if delivery still maps any holder of the same UID to that principal. Even identical `/etc/passwd` fields before and after a delete/recreate can conceal a new account. A watcher or cached account hash is not an interlock.

Two bounded alternatives must be assessed before selecting a permanent UID-nonreuse commitment:

- **Enrolled-account lifecycle interlock:** fence the old enrollment and outstanding delivery/execution authority before account deletion or reassignment, retain that retirement, and require distinct enrollment for a later account. Integrate every supported administrative route; an advisory uninstall hook or best-effort watcher is insufficient. This need not reserve all host UIDs forever, but it does require enforceable coordination for enrolled accounts and safe crash/reboot ordering.
- **Independent principal authentication:** authenticate an enrollment-specific credential in addition to native UID eligibility, with explicit enrollment, revocation, recovery and custody. A token left in files inherited by a replacement UID is not independent proof. This introduces a real secret-management or unlock cost and must not be selected invisibly as “ordinary login.”

Neither alternative is selected or qualified here. Losing the required enrollment/lifecycle proof blocks old-history delivery; it never transfers history, creates a replacement principal or authorizes deletion of retained grounds. Account retirement must reconcile outstanding Work separately from closing a client window. The host/administrator trust boundary does not excuse an unhandled ordinary account-replacement path.

### Evidence and qualification boundary

These findings use [Linux credentials](https://docs.kernel.org/security/credentials.html), [unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html), the Linux v6.12 [`SO_PEERGROUPS`/`SO_PEERPIDFD` implementations](https://github.com/torvalds/linux/blob/v6.12/net/core/sock.c) and [saved UNIX peer credentials](https://github.com/torvalds/linux/blob/v6.12/net/unix/af_unix.c), [Landlock inheritance and descriptor semantics](https://docs.kernel.org/6.12/userspace-api/landlock.html), [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html) and [passwd(5)](https://man7.org/linux/man-pages/man5/passwd.5.html). Kernel credential and Landlock restrictions can be per-thread; saved socket groups and a process handle do not export a complete current authority context. Documentation/source inspection selects no kernel minimum, LSM, service manager, authentication package or new adapter API, and is not an installed test.

Before freezing the host, challenge group-deny/group-grant and ACL ancestors; sending-thread versus leader credentials; restrictions applied after connection; transferred/stale handles; helper tracing/exec/namespace substitution; restricted-worker forwarding; revocation before reply; account deletion/reuse with unchanged public fields; and interrupted retirement/enrollment. A credential-snapshot value cannot by itself satisfy host authorization.

### Native enforcement and source-result evidence

Native permission enforcement and service-authenticated evidence are different responsibilities. The OS can refuse a user-context task's unauthorized read, but a separate custody service cannot infer from that task's response bytes, Rust type, digest or successful sandbox launch that the claimed read occurred. A client can construct the same result without performing the required operation. The selected host therefore needs a protected source path whose admission, exact reader image/startup, native acting context, request/result channel and actual subject/version are independently established. Landlock constrains a worker; it does not authenticate that source path or its output.

Keep these operation boundaries distinct:

| Operation | Required separation |
| --- | --- |
| Query | Use qualified native access and current scope/disclosure. An authorized inspection need not become a transformation. A client-only observation remains a contribution until independently established; missing provenance cannot be relabeled as authoritative source truth. |
| Candidate preparation | Admit preparation for the exact intent and scope; distinguish producer-supplied candidate bytes from independently established prior-source grounds. Writes target only admitted preparation material, without aliases to protected publication targets, custody, credentials or other Work. Existing grounded candidate operations may require prior reads even though native writing does not universally require reading. |
| Publication | A trusted bounded effect path checks exact candidate and applicable Check subjects, current Change/Work authority, native mutation rights including affected parents, competing-write/identity guards and actual outcome or reconciliation. Untrusted editors and brokers receive no raw writable route around that boundary. |
| Trace acceptance | Only the protected writer constructs authoritative records and returns accepted results after current guards and durability. Source evidence is an input, not a raw append grant. Opening still needs complete origin/activation/control semantics; typed library ports are not automatically IPC endpoints. |
| History and exact retry | Validate retained accepted-prefix/result grounds and current disclosure under the recovery protocol. Source revocation can block new source-dependent progress while an independently authorized old result remains deliverable. Resolve the original key and compare exact original input before new capture or identity allocation; do not regenerate the result, advance its original reference/head or replay effects. |

A native-allowed effect with denied Change authority is refused, as is a Change-admitted effect with native denial or insufficient Work scope. The exact all-allowed operation remains the positive case; its result still needs attributable evidence and custody guards. Withdrawal fences future admission and unauthorized delivery and requires reconciliation of already-started effects/held handles; a startup scope is not a perpetual lease or instantaneous revocation mechanism. Known denial, stale/conflicting input and missing native proof/storage uncertainty must retain their distinct meanings rather than collapse into a permission Boolean.

Every route must obey the same boundary, including shell commands, editor tools, generated code/plugins, recursive workers, trusted source readers and backend brokers. An unrestricted in-process file tool is not confined by a sandboxed shell. A broker is not a generic host file/command proxy and cannot rescue denial with its own greater native rights. Protected Work cannot choose an owner route through payload fields. For targets promising guarded publication, the worker's preparation area cannot be that target under another name; ordinary external owner writes remain drift, not governed publication.

The [faithful calling-context requirement](#ordinary-client-host-direction) remains unresolved for this deferred stronger profile. Post-exec alignment has the accepted information-loss counterexample, and the earlier BPF candidate has no qualified artifact/admission/startup/result composition. To keep that subject, provide concrete protected evidence of the original context and operation. Using a separately authenticated owner/source subject instead would require an explicit changed authority contract with its real enrollment/restriction/workflow costs; it is not implied by reuse of native ACLs. This research did not adopt a managed login, principal secret, UID ban, relocation or same-account exclusion as a repair of that stronger claim. Its source-dependent operations remain unavailable until the stronger evidence path qualifies. The first trusted-host profile is an explicitly different capability claim, not a qualification of these mechanisms.

This composition does not change frozen SQLite/library retry semantics, the packet adapter's opaque-byte/descriptor-rejection behavior or the current path/subprocess observer's supported premises. A preliminary check cannot upgrade those implementations into the new protected reader or file-first host. The [versioned interface boundary](components/state.md#file-first-domain-interface-boundary) and complete protocol review still precede implementation; no new error enum, key grammar or persisted schema is frozen by this clarification.

### In-place source enrollment and continuity

The [ordinary-client host direction](#ordinary-client-host-direction) prefers keeping repositories in their existing locations. Protecting custody directories and identifying application-source directories are different responsibilities: the former require an independently protected writer boundary; the latter require qualified native identity, scope and access. Do not infer a requirement to move every repository under administrator-owned parents from the custody requirement. Equally, retaining a pathname does not prove that its source stayed the same.

A candidate in-place binding keeps the approved native locator and exact repository topology in protected service controls, not in a user-writable marker claimed to authenticate itself. It identifies the native repository objects separately from their content/version and from the Workspace/Change IDs. The narrower identity route to assess is:

1. During explicit enrollment, a protected helper freshly opens the proposed source under the qualified native authority context. Establish source/ancestor and filesystem/mount-view identity before recording the binding. A client supplies a proposed locator, not an authenticated object or permission receipt. A linked Git worktree requires separate binding of the worktree, private Git directory and common object directory; matching `.git` text is not that identity proof.
2. For each later source-dependent operation, resolve the current locator afresh under current native permissions, compare the opened object and topology with the enrolled binding, then constrain the actual operation to those verified objects. A retained root FD is an identity anchor, not continuing authorization. A check followed by a pathname-based reopen can race and is not the protocol. Relative descriptor traversal must preserve the declared scope and native checks, including supported mount crossings, symlinks, ancestors and concurrent rename behavior.
3. Same-lifetime pinned object references can assist comparison without trusting a replaceable name. After restart/reboot, require a qualified persistent filesystem/object identity or an explicit supported continuity procedure. A candidate is a native file handle combined with authenticated persistent filesystem identity and current mount-view validation; neither inode numbers nor mount IDs alone suffice. Filesystem support, handle stability, stale/reused identities, copied filesystems and remounts must be qualified for the actual supported profile before selecting a descriptor grammar.
4. Replacement, unknown topology, stale identity or unproved continuity blocks dependent source work. Do not automatically enroll a same-path replacement, mint a new source identity during retry or rewrite immutable Change origin. An authenticated user choosing a new binding is not proof that the old object continued. Current private historical delivery and original-result reconciliation remain separately available only where their own accepted-prefix and disclosure grounds survive.

Linux [openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html) supplies constrained lookup, not a transaction holding a pathname tree fixed after return. [`name_to_handle_at(2)`](https://man7.org/linux/man-pages/man2/name_to_handle_at.2.html) documents filesystem-specific handles, stale-handle failure and the nonpersistent nature of mount IDs. These offer an identity candidate, not generic reboot continuity or rollback detection. `open_by_handle_at` requires `CAP_DAC_READ_SEARCH`; it must not replace a fresh authorized path open or turn the custody service into a source-permission proxy. An administrator's assertion, filesystem UUID, Git commit hash or copied descriptor alone cannot authenticate continuity against every replacement/restoration. Explicit restoration retains its separate recovery gate.

There is still a material distinction between **observation** and **guarded publication**. Capturing exact authorized objects/versions does not lock other writers out, preserve the current pathname meaning forever or make a multi-file effect atomic. Existing [committed-source observation](components/native-profiles.md#native-committed-source-observations) requires host-protected topology for the duration of capture; adding a preliminary root check does not qualify its path-based subprocess access against mutable ancestors. A concrete descriptor-bound reader or qualified source guard is needed before claiming that support. Publication additionally needs serialization against relevant competing writes, exact expected targets, current native authority and outcome/reconciliation evidence. Without source cooperation, outside writes remain separately observed drift, not governed effects. If the eventual publication contract requires a protected target boundary or working arrangement, explain that specific cost rather than impose relocation on all observation/history operations.

Qualification must cover replacement by an equal-content repository; rename/symlink/mount races before and during actual reads; linked-worktree pointer substitution; parent search-permission withdrawal; stale descriptors after revocation; inode reuse; ordinary restart/reboot with unchanged source; unsupported filesystem handles; and explicit restore/clone. Missing mechanisms remain engineering blockers, not approval requests for a weakened guarantee. This is an in-place design candidate, not adoption of a handle codec, a new filesystem dependency, a changed observer contract or permission for privileged experiments.

### First local recovery admission protocol

**Retained protocol proposal, not the current Phase 1 implementation contract.** This logical sequence was developed for the protected standalone host. The new trusted-host path must settle and test its actual consumed encoding, initialization and commit/recovery protocol; shared safety principles do not automatically adopt this inventory or host machinery.

This selects the logical recovery protocol for the approved local profile, not a storage codec, installed host or implementation release. The complete control inventory, byte grammar and host identity/enrollment contracts must be frozen together before dependent source work. The earlier witness-dependent `VIRGIN`/`DIRTY`/`CLOSED` proposal is not this protocol. Routine process exit is not itself a storage incident; a missing previous clean-close marker does not refuse every successor. No witness, new database or second authoritative history is introduced.

**One writer and observation boundary.** One protected service process owns all custody syscalls: root/registry enumeration, control and Trace reads/writes, exclusive creation, replacement, barriers, cleanup, errors and acceptance-bearing delivery. Opening the root is already observed I/O; an in-memory incident latch exists before that first syscall. Parsing and domain logic receive bounded values, not writable custody handles. There is no separate host-control writer whose error can escape the Trace gate. Mutations and deliveries serialize under the current policy/enrollment guard and permanent deployment lock; per-Change locks follow the deployment lock. Retained lock objects are never removed or replaced to gain admission.

A successor needs both qualified process/handle fencing and the exclusive lock on the verified original lock object. A PID, idle timeout, socket disconnect, matching lock-file contents or lock acquisition alone does not prove that an old writer or descendant retaining a writable handle is fenced. The selected supervisor must establish predecessor termination and exclusion of surviving writable/lock handles under the process-isolation contract. Missing fence or lock identity leaves custody unavailable. No storage descriptor passes to clients, checkers or workers; close-on-exec alone does not prove exclusion of fork inheritance. The concrete supervisor/handle proof remains a host prerequisite, not a receipt reconstructed from Trace.

**Initialization differs from reopen.** Administrator provisioning establishes installation/root identity, protected ancestors and independently justified first-use state before custody initialization. Under the same fencing/observation boundary, the writer exclusively creates every permanent lock, required parent and control, synchronizes each control and each parent whose namespace changed, then validates the complete initialized inventory before requests. The installation handoff must distinguish unused custody from failed or previous initialization. Empty, partial, missing or restored custody is never inferred virgin from absence; retry never creates a replacement deployment identity. Failed initialization remains unavailable until its same-identity state has a qualified outcome. Provisioning-record encoding, placement and handoff remain host dependencies; an unencoded “virgin” flag is not authority.

**Reopen ordering:**

1. Establish current installed deployment identity, protected ancestors and predecessor fence; acquire and verify the permanent lock. Do not create missing locks or root controls during reopen. Establish current enrollment/disclosure authority before private delivery; inability to authorize one principal must not become permission for anonymous delivery or automatic damage to another principal.
2. Read the bounded complete control/namespace inventory through the writer. Check versions, types, permanent identities, associations, capacity and incident evidence before treating a lookup as absence. Unknown entries, conflicting identities or missing required controls are damage, not capacity, a new principal or a new root. Enumeration and hashes cannot detect an internally consistent whole-domain rewind; that remains outside this profile's guarantee.
3. Retained incident evidence blocks affected custody. Genuine or unscopable storage incidents fence the deployment. Independently classified logical damage may fence only its attributable Change, leaving unrelated intact Changes deliverable. Malformed/unreadable incident controls cannot mean “no incident.” Incident evidence is never a routine temporary file deleted at startup.
4. For an otherwise admissible Change, decode its intact protected checkpoint and validate exactly its selected prefix: deployment/Workspace/Change/source associations and generation, framing and lengths, sequence and predecessor chain, accepted head/end coordinates, typed event/result envelopes, and required delivery/retry grounds. A longer plausible Trace does not select a newer head. Missing checkpoint or grounds cannot be rebuilt by scanning the log. An active creation control without its matching accepted origin is unavailable.
5. Complete fresh barriers for the validated Trace, checkpoint and authoritative namespace parents needed by that prefix before acceptance-bearing delivery. Recheck exact checkpoint/prefix identity and current disclosure authority under the held guard. These barriers establish current durability under the approved profile; they do not prove an earlier acknowledgment, clear retained incidents, settle effects or detect rewind. A new storage error takes the incident path, not a retry loop that erases it through later success.
6. Admit only operations justified by that state. A healthy exact end may admit append once the full operation contract is frozen. Bytes beyond the checkpoint, interrupted control replacement and private origin preparation are not automatically accepted. A validated accepted prefix may be delivered with append blocked only when the suffix/control condition is independently classified, disclosure/retry grounds remain intact, no retained incident applies and fresh barriers succeed. Otherwise the Change is unavailable. Do not truncate, promote, rewrite or execute the suffix to gain admission.

**Commit and acknowledgment.** For an already active Change, validate current authorization and the original operation key/subject/input under the guard before new work. A new append writes its canonical record, synchronizes Trace, writes and synchronizes a unique same-directory checkpoint temporary, atomically replaces the checkpoint and synchronizes its parent. The writer validates the installed checkpoint/prefix and retained grounds, rechecks delivery authority and releases the exact accepted result/reference. Trace bytes or successful rename alone are not acknowledgment. A temporary checkpoint never substitutes for the installed checkpoint. Creation additionally requires the still-unfrozen pending reservation → private origin preparation → active association → final certification contract; ordinary append does not close bootstrap.

Resolve the original retry key before new source observation, identity minting or initialization. An accepted exact retry compares the complete original typed subject/input and returns its retained result plus original derived reference/head under current disclosure rights. It does not regenerate results, advance expectations or rerun effects. Historical private delivery can survive current source unavailability where its own grounds survive; source-dependent continuation requires fresh source authority. An occupied, damaged or uncertain key cannot become a new Change or operation under another identity. Source-effect uncertainty needs its own reconciliation; custody barriers cannot settle it.

**Incident handling is monotonic within a writer lifetime.** A short write, uncertain barrier, genuine I/O failure or unclassified storage outcome latches refusal before further acceptance-bearing reply. The writer attempts bounded incident retention through the same protected route, preserving observed failures; retention failure does not clear the live latch. Expected exclusive-create contention and justified absent lookup are not automatically device incidents; unexpected absence of authoritative control remains damage. Later successful syscalls, reopen or administrative deletion cannot clear retained incidents. Incident scope/classification and persistent grammar remain part of the full inventory freeze.

If the writer disappears before incident evidence survives, a successor cannot recover the lost observation. It may use the validation/barrier protocol only under the approved lost-incident limit; it must not claim “no previous error,” complete recovery of earlier acknowledgments or witness-certified health. A new root marker cannot remove that limit without independently surviving authority, and none is selected.

Qualification must challenge clean process restart/reboot; competing successors and inherited/stale handles; every file/parent barrier and checkpoint-replacement cutpoint; lost reply; retained incidents and failed retention; unknown/missing controls; accepted prefix with unaccepted suffix; exact retry after source revocation; active association without accepted origin; and scoped logical damage versus deployment-wide I/O failure. Same-UID unit tests cannot establish installed isolation, physical persistence, account lifecycle or effect recovery. The [package testing and qualification policy](components/package.md#testing-policy) remains binding.

The syscall premises are narrower than the operational claim: [fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) requires separate directory synchronization and documents write-back errors; [flock(2)](https://man7.org/linux/man-pages/man2/flock.2.html) is advisory on the supported local profile and shares locks through duplicated/forked file descriptions; [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html) supplies namespace replacement, not durability certification. These premises justify barriers and handle fencing. Documentation lookup is not installed qualification.

## Persistence references

A retained version identifier is not necessarily retained historical content. Earlier design cited PostgreSQL's [removal of obsolete row versions](https://www.postgresql.org/docs/current/routine-vacuuming.html) and [transaction identifiers](https://www.postgresql.org/docs/current/transaction-id.html) as a counterexample to treating an ID as an archive. A future binding must retain the values/differences required for its claims or rely on qualified native history; it need not mirror every version of the application.

A [transactional-outbox-style](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) native receipt is one possible way to link an effect and its outcome identity. It does not require a message broker and is not a selected universal backend. Where the native mutation and Trace cannot commit together, the consumed binding must demonstrate an equivalent outcome/reconciliation protocol or expose uncertainty and refuse unsafe repetition. Co-located files, a Workspace name or a sidecar do not create a transaction.

- [Miri](https://github.com/rust-lang/miri/blob/master/README.md) detects supported undefined behavior in executions, not general correctness. [Nextest](https://nexte.st/docs/design/how-it-works/) changes execution scheduling and process isolation; it does not supply missing test cases. These are options, not an adopted toolchain expansion.
